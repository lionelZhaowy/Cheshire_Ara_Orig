# Agent 文档定位与历史检索指南

本页用于快速找到有效结论和历史依据，不替代[根 AGENTS](../AGENTS.md)、源码或测试。更新：2026-10-17，补充既有图稿修订与验收要求；原文档路由保留。

## 1. 最短接手路线

1. 读 [PROJECT_STATE](PROJECT_STATE.md)：当前方向、已确认需求、未验证项。
2. 读 [AGENT_TASKS](AGENT_TASKS.md) 对应任务行及其主题交接，确定本次范围；任务表不是授权或文件锁。
3. 根据下表只读需要的正式文档，再定位定义、实例及消费者；执行前核对 HEAD、git status 和涉及文件。
4. 只有缺少决策依据或需要复核过去结果时，继续追溯交接、维护报告和原始证据。不要默认通读 handoffs、扫描整个 .bender 或重跑旧 Prompt。

## 3. 有限范围检索示例

在仓库根执行，只读查询：

```sh
# 先找任务主题，而不是把所有日志全文读入上下文
rg --files docs_codex/handoffs | rg '/(M01|P01|S01|V01|E01)_'

# 定位某个决策/缺陷的记录，再打开命中章节及其引用
rg -n 'S01-B01|Platform ROM|返回路径' docs_codex/PROJECT_STATE.md docs_codex/AGENT_TASKS.md docs_codex/handoffs
rg -n 'GB|主Xbar|256|用户确认' docs_codex/engineering/IP_DDR_Interface_Contract.md docs_codex/handoffs/M01_*.md

# 查看当前版本和待修改文件；不要用还原/清理消除已有改动
git rev-parse HEAD
git status --short
```

文件名改过时先查映射：

- [handoff 名称迁移](handoffs/name_migrations.json)：日期前缀 → 任务主题名。
- [教材维护报告迁移](maintenance/L01/path_migrations.json)：原顶层 L01/03–08 文件 → 分类目录。
- [本次图稿与入口精简](maintenance/L01/archive/documentation_organization/manifest.json)：B/C 资产的原路径、哈希、归档成员和恢复来源。原始检查中的路径通过该清单追溯。
- [工程参考迁移](engineering/path_migrations.json)：原 M01/P01 顶层文件 → engineering。

原始日志/哈希快照里的旧路径是当时记录，不能为匹配新目录而改写验证输入。映射只解释“今天文件在哪里”，不证明当前内容仍等于历史被测版本。三个 handoff 旧名符号链接仅为归档导航兼容，新文档不要继续引用旧名。

## 4. 怎样判断结论是否仍有效

- 优先当前明确需求；实现事实以当前源码和匹配配置的测试为准。正式文档是检索入口，不天然比旧记录更正确。
- 对照记录的输入 HEAD、未提交变更、配置、日期及作者/独立评审身份。文件名新旧、修改时间或“完成”二字都不能代替核实。
- 作者实施报告、独立评审、主管验收分别说明各自范围；不能将作者自查当独立通过，或把网页检查当 RTL/板测。
- 遇到冲突，记录两边来源、当前源码证据和仍缺的测试；已修正的结论标明替代关系，不为一致而删除原失败日志。
- 只读需要的片段和直连证据；确认版本差异后再做定向复核，不重复全仓审计。

## 5. 新内容写在哪里

| 内容 | 位置与规则 |
| --- | --- |
| 用户需要长期查阅的解释 | 正式教程/参考文档，同主题更新，保持单一主要说明 |
| 接口条件、设计约束和实施输入 | engineering 或现有 02/03 专题，保留任务归属与未决状态 |
| 变更、决策、缺陷、验证、阻塞 | handoffs/<任务ID>_<主题>.md；头部追加修改记录，不逐轮新建 |
| 复杂教材规划/评审/实施对照 | maintenance/<任务ID>/planning、reviews、reports；handoff 只链接 |
| 原始验证产物 | 对应 evidence/reviews 的独立输出，保留输入身份，不覆盖旧证据 |
| 纯重复解释 | 无需新增 handoff；若纠正事实，更新正式说明及必要的主题记录 |

共享状态只概述重要变化并给链接，不再复制整份报告。历史 Prompt 和任务表中的待办不能自动转化成执行授权。

## 6. 既有图稿修订：接手、实施与验收

2026-10-17，用户要求将 SoC 全景图反复返工的教训落实为新对话 Agent 的工作要求。本节约束后续修订流程，不授权重绘旧图、修改 RTL 或实施其他任务。原输入、失败及补修证据见 [L01 GB 主题交接](handoffs/L01_global_buffer_cpu_access.md)和[图稿 README](diagrams/2026-10-16_soc_landscape_m5_gb/README.md)。

### 6.1 先确定范围和对象

1. 按当前请求判断本轮是答疑、只规划还是实施。“下一版作为第 N 页，现在规划”不授权写入该页；“开始实施”承接此前具体方案。用户已明确授权的工作继续完成，不因本流程重复请求确认。
2. 核对实际输入的页数、哈希、主题依赖和未提交修改。写下“目标对象/属性 → 预期结果 → 保留项”；备份即将覆盖且无可靠恢复来源的文件。用户指定沿用当前目录时，保持该目录，不自动再建日期图稿目录。
3. 以当前最终 PPT/SVG 为修改基线，读取命名对象及其样式。历史生成脚本可能少了后续补丁，不能直接重跑并覆盖当前文件。复制旧页时明确源页、目标页及原页保护要求。
4. 用户说“LVDS TX 的虚线”时，先区分输出子系统外框、内部 TX 功能框、VDMA 的 AXI 接口和像素流；不能未经核对就断言某个框应如何修改。能从图和上下文定位就继续，仍影响修改范围的歧义才简短询问。

### 6.2 分别记录连接语义和视觉属性

检查清单不必另建文件，可放在本图 README 或现有交接中。至少区分以下维度，不能把它们合成一个“箭头正确”结论：

| 维度 | 要核对的内容 |
| --- | --- |
| 连接语义 | 发起者、目标、端点，单箭头表示请求还是数据流，双箭头如何表达请求/响应；共享服务是否被误画为独占通路 |
| 连线样式 | 虚线/实线、颜色、线宽、两端箭头和跳线，逐项独立继承 |
| 框与层级 | 子系统外框、内部模块框、端口标签各自的填充/边框；不要把一层约定强套到所有层 |
| 页面与主题 | 位置、尺寸、字号、主题色及亮度修饰、母版/布局引用；跨 PPT 复制后核对最终效果 |

本次具体遗漏：第 6 页恢复 F1/F2 虚线后，漏查同属新增规划通路的 F3；补修后 F1/F2/F3 为深蓝双向虚线，F0 与四条下游 DDR 接口仍为双向实线。ROI 输出子系统外框为虚线，内部功能框保留实线。**这是该图约定，不是 AXI 协议要求，也不是硬件已实现/已验收状态。** F2 反向箭头表示 B 响应，F3 表示 R 返回，不能由双箭头推导 DMA 增加了读或写能力。

局部修订直接修改对应原生属性，保留其余对象；需要重排时也只处理授权范围。检查相关同类通路及沿途连接，发现范围内同类遗漏一起处理；范围外的问题另行说明。检查范围可以扩大，写入范围不能随之自动扩大。

### 6.3 从最终产物做四类检查

| 检查 | 本轮应有的证据 | 不能替代的检查 |
| --- | --- | --- |
| 变更范围 | 修改对象/属性差异；未修改页及依赖的保护。单一属性修补可核对“移除该属性后与输入一致” | 不证明架构语义正确 |
| 语义与一致性 | 沿相关数据/控制通路查看发起者、目标、返回归属和共享关系；比较相关同类端口/模块 | 不能只数箭头或只核对已列出的修补对象 |
| 视觉 | 从最终交付文件重新生成并实际查看整页和修改区局部，检查端点、跳线、文字、间距、图例与样式 | 中间文件预览和脚本无报错不等于最终显示正确 |
| 文件与编辑性 | 按交付格式检查原生文本/箭头/虚线、保存重读、关系引用；如实记录 Office 是否实测 | 本地 DrawingML/替代字体预览不是 Office 截图或硬件验证 |

检查规模随修改范围调整；一条线的小修无需重跑硬件构建或全部历史实验。最终报告写清“改了什么、上述哪些检查实际做了、还有什么未实测”，不以“检查通过”概括超出证据的范围。旧报告仍绑定旧输入；新发现的遗漏应补充其检查局限并链接修正证据，不改写成旧版原本正确。

这次返工来自 Agent 的授权理解、局部修改和检查覆盖问题。改进要求落在执行者，不要求用户用更长 Prompt 替代审图，也不作缺乏对照证据的模型优劣归因。
