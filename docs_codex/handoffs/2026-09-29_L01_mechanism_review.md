## 修改建议

### M1 · 中优先级 / 已有源码证据：SD/NOR 启动等待不是初始化后的固定延时

定位：`learning/content/boot.html:7、24、27`。总表和分模式正文分别写“初始化后等待约1 ms”和“初始化后等待约350 μs”。相关说法此前已有，本轮分模式扩写后再次保留；不能认为是新引入的底层代码问题。

实际调用：

- `hw/bootrom/cheshire_bootrom.c:43–45`：SD初始化后调用 `clint_spin_until((1000 * rtc_freq) / (1000 * 1000) + 1)`。
- 同文件 `:55–57`：NOR初始化后调用 `clint_spin_until((350 * rtc_freq) / (1000 * 1000) + 1)`。
- `sw/lib/dif/clint.c:19–21`：`clint_spin_until(tgt_mtime)` 只轮询 `mtime < tgt_mtime`。
- 同文件 `:24–25`：`clint_spin_ticks(ticks)` 才把当前mtime加到相对等待量上。

因此当前代码等待的是绝对mtime阈值。假设调用时mtime已超过该阈值，函数立即返回；尚未超过时也只等待剩余差值。这里不能保证从HAL初始化结束再额外等待固定时长。本轮没有测量真实启动耗时，也不据此宣称板上启动一定失败。

建议正文改成：

> 当前ROM在初始化后等待mtime达到按约1 ms／350 μs换算的绝对阈值；该调用不保证初始化完成后再延时相同时长。若设备要求从特定事件起等待，应按器件要求和计时基准另行核对。

同步修改模式比较表和SD/NOR小节。把“代码实际执行”“注释描述的意图”“器件规范要求”分开。若后续确认应使用相对等待，将修复建议交S01并另行授权；本轮不修改Boot ROM或原驱动。

验收：文档准确区分 `spin_until` 与 `spin_ticks`，不再将常量换算误写成相对延时；定向来源增加CLINT实现，而非只看调用点注释。

### M2 · 中优先级 / 教学条件补充：共享 PLL 的调频影响范围需要明确

定位：`learning/content/clocks.html:15–18` 和 `assets/mechanism-clocks.svg`。图中同一个PLL通过C0/C1给系统域和外设域供钟；正文随后描述“一次外设调频”停发、排空、配置PLL及恢复。

依据本页自己的简化关系 `f_out=f_ref×M/(N×C)`：修改共用M/N会同时影响C0和C1支路；只改C1则是在另一类假设下调整外设输出。实际IP是否允许独立修改、是否保持其他输出有效以及是否需要重新锁定，还需IP规范确认。

现有“切到允许的安全时钟/复位状态”没有指明适用域，读者可能把共用反馈环重配理解为仅需停止外设。

建议在现有小节内补一张小表或两段条件说明：

| 操作 | 需讨论的影响范围 |
| --- | --- |
| 只调整外设支路C1 | 确认IP支持及其他支路稳定条件，再说明外设排空、切换和时序约束 |
| 修改共享M/N或参考源 | 纳入系统域及所有相关输出，明确控制代码/常开控制的有效时钟、切换及恢复条件 |

区分“相关分频时钟之间的跨域”与“异步时钟”也可用一句话补充，避免把所有域间连接机械等同于同一种异步FIFO。保留现有候选方案标识，无须新建页面或冻结ASIC频率。

验收：能从图和正文判断哪个参数影响哪些域；不把仅停外设的步骤扩大成共享PLL重配的完整方案。

### M3 · 低优先级 / 证据追溯：浏览器输入快照尚未包含实际被加载的 HTML

定位：`learning/scripts/report_run.py:17`。`run.json` 的inputs只覆盖 `content/`、`scripts/`、`assets/`。浏览器实际加载的 `learning/*.html` 位于这些目录之外。

默认 `check_structure.py` 明确跳过生成比较，浏览器检查自身也不保证HTML与内容源完全一致。所以当前源文件快照与Git状态列表不能唯一确定浏览器看到的每个生成页面字节，尤其当前重构仍是未提交状态。

建议把根目录主页面及兼容HTML的SHA-256加入现有run.json，明确区分“内容源快照”和“被测页面快照”。可附带完成时间和最终成功/失败状态，便于汇总；不需要增加新的报告框架。

这不是历史覆盖问题复发：新目录保护已通过，当前报告也有可用检查结果。此项用于增强后续可重现性。

验收：一次浏览器报告可以对应到实际测试的HTML字节；仅改生成页面时，快照也会变化。
