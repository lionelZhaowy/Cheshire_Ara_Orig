| 标记 | 本文含义 | 关闭所需证据 |
| --- | --- | --- |
| 已确认方向 | 用户已选需求或架构关系；参数可能尚未冻结 | 可追溯决定及符合该方向的接口规格 |

## 01　GB 所有权、访问权限与仲裁

![GB 的接入、检查与区间交接](../diagrams/2026-10-18_implementation_challenges/png/01_gb_ownership.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/01_gb_ownership.svg) · [可编辑 PPTX，第 1 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制、困难与失败场景

“谁能寻址”“谁当前持有数据”“本周期服务谁”是三个问题。CPU 能访问 GB，不表示可以在 NPU 使用同一块时改写；轮询状态也不自动阻止 DDR→GB 搬运器尚未结束的旧写。软件分配表规定区间归属，权限检查决定是否接受来源/范围/操作，仲裁器决定合法请求的服务顺序，bank 和宏端口决定实际并发能力。

例如 DDR→GB 搬运器已开始向 GB 参数区写入，软件只看到命令被接收就把该 GB 区间交给 ISP；ISP 可能读到半新半旧参数。这里的 GB 写者是 DDR→GB 搬运器，并非 eMMC Host。另一例是 Ara 连续突发占用 M5 或某个 bank，平均带宽足够但帧处理一直得不到服务。还有范围尾端的窄写、越界 burst、两个逻辑地址别名、未初始化 SRAM、跨 bank 访问和同址读写碰撞，都会使“连上 AXI”与“可安全共享”之间出现缺口。

### 已有讨论与当前状态

[GB CPU 访问专题 §6～7](Global_Buffer_CPU_Access.md)及[总纲 §4.1、6.1](SoC_Architecture_v1_Master_Plan.md)已确定 CPU S0、Ara2 S2 为独立 Xbar 输入，经主 Xbar64 共享 M5；eMMC Host 内置 DMA 从 S7 在拓扑上也可到达 M5，但当前软件流程不向它提交 GB 目的地址。NPU、ISP 和 DDR↔GB 搬运器另有本地入口，最终共享适配、仲裁和 SRAM。**接入拓扑已确定；实际 GB 目标、权限和 bank 机制未实现/未验收。**

首版 GB 不缓存、不可执行、按普通幂等 SRAM 使用是已有建议，仍要在真实 PMA/地址映射中实现。[CVA6 官方 PMA 说明](https://docs.openhwgroup.org/projects/cva6-user-manual/01_cva6_user/PMA.html)给出属性机制；本工程实例由 `gen_cva6_cfg()` 配置，不能靠 C 指针或 `volatile` 设置。PMP、页表权限只覆盖相应 CPU 路径，不能据此推定独立 DMA 已隔离。GB 的 M5 支路也不继承 M2 主存路径的原子支持。

**2026-10-18 用户澄清的实际数据流：上电复位→平台与 DDR 初始化就绪→软件将 eMMC 数据搬入 DDR→ISP 工作时按需从 DDR 搬到 GB→装入完成后交给 ISP 计算。** 前文把 eMMC→GB 直达写成参数加载流程，是将硬件可达性误当成软件需求，现予纠正。软件搬运是否采用 CPU 拷贝或软件启动 Host 内置 DMA，尚未由本次澄清选定。

图 01 保留 eMMC/S7 到共享 M5 的连线，只表示**硬件可达性**；下方 GB 交接流程在当前软件规划中由 DDR→GB 搬运及实际 GB 使用者承担。eMMC→DDR 的完成/可见性与 DDR→GB 的装入/所有权交接是两个阶段；不能用前一阶段完成替代后一阶段完成。

### 尚需决定及推进步骤

1. **队长定义区间契约**：分配粒度、共享只读条件、单写者规则、有效长度、完成点、释放条件；TTY 将状态纳入公共 buffer 管理。建议从明确的软件交接开始，并单列需要硬件拒绝的违规行为。
2. **队长与 P01 确定物理服务**：容量、bank 数和映射、宏端口/时延/掩码、同址冲突语义、队列深度、最大突发与饥饿防止。宏多端口能力是外部输入，不能从逻辑入口数量推导。
3. **落实检查边界**：识别真实来源，检查地址加长度溢出、跨区请求和非法操作；若需要阻止 CPU 的全部违规访问，还要核对缓存/地址别名。GB 上 AMO/LRSC 是否支持必须明示，建议首版不把 GB 当 CPU/设备并发原子控制区。
4. **HYH/TTY 提交负载和交接规则**：ISP 参数版本、DDR→GB 装入完成、ROI/任务引用等由消费方共同定义；TTY 另提供 eMMC→DDR 源数据就绪条件；不能把仲裁器公平等同于每种业务的实时保证。

最晚：G0 给出所有权/权限契约及宏需求；G1 完成访问适配和冲突原型；G2 分别验证 eMMC→DDR 加载、DDR→GB 装入，以及 CPU/Ara/NPU/ISP 实际采用的 GB 访问路径。后续性能收敛在 G3 前完成。

### 验收用例与关闭证据

- 同范围双写、写读重叠、多个只读者、先完成后发布、迟到写与过早释放；通过条件是按契约拒绝或串行化，合法消费者只读完整版本。
- byte/halfword/word/doubleword、向量尾块、边界 burst、bank 冲突和越界；逐字节参考检查，未选通字节保持正确。
- 持续高负载与低频请求竞争；记录每源队列峰值和最长等待，达到约定服务预算。仅报告平均 GB 吞吐不能关闭本项。

证据应包含物理宏契约、地址/属性表、所有权状态机、仿真波形/检查器及 FPGA 适用路径结果；没有明确硬件强制隔离实现时，报告必须注明仍依赖软件纪律。

## 02　L1D、LLC、DDR 与 GB 的数据同步

![缓存数据路径和三类范围维护](../diagrams/2026-10-18_implementation_challenges/png/02_cache_sync.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/02_cache_sync.svg) · [可编辑 PPTX，第 2 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制、困难与失败场景

GB 是独立 SRAM；软件/搬运器显式移动 DDR 与 GB 数据。同一 DDR 地址却可能同时存在 L1D 副本、写缓冲在途写、LLC 脏行及 DDR 旧值。设备旁路 LLC 访问 DDR，既不自动清理这些副本，也不自动让 CPU 放弃旧数据。WT L1D 仍需排空写缓冲，不能由“写穿”推导 DDR 已更新。

输入未 clean 时，NPU 从 DDR 搬入旧数据。输出前若旧脏行未处理，设备结果写入后可被迟到的旧写回覆盖。只在设备写前 invalidate 也可能不足：旧读/回填或违规重新读取能再次留下旧副本。若输出仅覆盖一条 cache line 的部分字节，粗暴丢弃整行会破坏未覆盖的相邻数据。

### 已有讨论、已确认方向与历史适用范围

**本问题已有系统讨论及初步方案，不是本轮重新提出待选方向。** 主要依据为[DDR–GB 数据同步设计 §3～7](DDR_GB_Coherence_Design.md)、[维护评审答疑](../maintenance/L01/reviews/ddr_gb_coherence_review_qa.md)、[2026-10-16 用户收敛及后续修订记录](../handoffs/L01_cache_coherence_architecture.md)；[原规划](Cache_Coherence_Architecture.md)与[工业/学术综述](CPU_NPU_Cache_Coherence_Survey.md)保留比较依据。

用户已确认：软件确定 DDR 物理范围及交接时机，硬件实施 L1D/WT 写缓冲/LLC 范围维护，建立维护窗口、实际完成握手和错误闭环；通过 DDR 交换缓存与 GB 数据，不增加 LLC→GB 直接供数口。MMIO/HAL 是已有建议，具体命令编码、并发数、硬件划分和 C 组归属待定。不能把标准 CMO 或已有 Ara 失效请求接口当作本系统跨层维护已完成。

旧同步系统图和早期供应商讨论含三口 DDR、Ara 独立 GB 分支；**这些拓扑已由 v1 四口、CPU/Ara 共享 M5 取代**。原文的维护顺序和失败条件继续适用，端口覆盖扩到 F0～F3；旧图原件保留，不据旧图新增分支。本文图 2 仅突出 DDR 同步链，GB 的 M5 本地路径见图 1，四口完整连接见图 5。

### 三类维护不能混用

| 场景 | 必要动作及其目的 | 成功后允许做什么 |
| --- | --- | --- |
| 输入交设备 | 等生产者结束，先推进上游旧写/写缓冲，再 clean LLC；确认数据经前端/DDR 对设备口可见 | 启动 DDR→GB 或其他设备读取；按协议可保留干净输入副本 |
| 输出写前准备 | 排空旧写，clean＋invalidate 输出维护范围；保全未覆盖字节，收束旧回填/替换 | 设备开始写输出；CPU 不再改同一维护粒度内的数据 |
| 输出写后交 CPU | 设备数据和元数据跨口可见，相关旧读活动终止，再最终 invalidate L1D/LLC | CPU 读新结果；此时发现冲突脏数据应报错，不能把旧值 clean 覆盖新输出 |

### 实现缺口与推进步骤

1. **定义维护窗口及前进性**：命令接受→上游排空→缓存维护→系统完成期间阻止新增冲突，但允许已接收事务所需 W/R/B 前进。过早关 LLC 入口会卡住上游排空。设备持有期的软件所有权与硬件覆盖 L1 命中的强制保护需分别说明。
2. **扩展范围维护与真实确认**：当前向量 profile 的 L1D 行为 32 B，默认 LLC 行为 64 B；范围向外对齐并隔离活跃相邻对象。现有 LLC 按 way 维护需扩展；Ara `inval_ready` 是接受确认，不能直接当 done。行大小随固定配置变化时统一派生。
3. **保持启动与故障可前进**：LLC 阵列还承担 SPM 和启动栈；隔离不能依赖被阻塞 CPU 再执行回调。维护服务需自主完成或保留可用恢复路径。
4. **汇合错误与可见性**：对照第 05、07、13 节，保存命令前已发生但仍影响该数据的错误；不能接到新命令就清除历史失败。供应商 B 语义和前端元数据发布必须形成实证。

队长主责维护硬件/存储契约，TTY 主责 HAL、缓冲生命周期及驱动接入，HYH 提供帧/压缩交接条件。G1 验证维护原型和死锁边界，G2 完成普通区域缓存开启的交接，G3 覆盖压缩/并发/故障，G4 收敛回归。

### 验收用例与关闭证据

写缓冲尚有数据、LLC 脏命中/替换、维护时旧回填、部分行输出、CPU/Ara 并发、SPM 栈依赖、DDR 长背压、错误响应和超时都要进入矩阵。比较维护前后**实际 DDR 与 CPU/设备观察值**，同时证明完成未早报、无迟到覆盖、合法事务可前进，错误时保持隔离。

`fence`、`volatile`、IRQ、DMA 计算 done 或单个 B 响应均不是完整同步证据。需要命令与范围身份、各层完成/错误记录、跨口检查器、超时恢复波形；现阶段这些是待执行要求，不是通过结果。

## 03　NPU、ISP、DMA 地址体系与地址转换

### 机制、困难与失败场景

必须区分 CPU 虚拟地址 VA、CPU 物理地址 PA、设备看到的 DMA/总线地址、NPU/ISP 内部 GB 偏移。它们在某个裸机配置中可能数值相等，但类型和作用仍不同。将用户虚拟指针直接写入设备寄存器，或在 DMA 未结束时释放/换出页面，都可能访问错误位置；地址高位被裁掉或加长度溢出还会误写其他对象。

问题首先落在**实际发起内存请求的组件**：DDR↔GB 搬运器、帧写/读 DMA，以及软件加载若采用 Host DMA 时的 eMMC DMA；eMMC 的当前软件加载目标为 DDR。只使用本地 GB 偏移的计算核不一定需要独立 MMU。压缩前端把逻辑存储块映射到数据/元数据位置，属于存储格式转换，与进程 VA→PA 不同。

### 已有依据与初步方案

[软件基础地址说明](../software/LIBRARIES.md)、[运行布局说明](../software/RUNTIME_AND_DEBUG.md)、[CPU＋NPU 推理体系调研](CPU_NPU_Inference_Systems_Survey.md)已经讨论地址/运行时职责。当前 `cheshire_soc.sv` 连接 CVA6–Ara 专用 `acc_mmu` 交互，Ara 配置支持相关 OS 路径；这不等于新 DMA 自动接入同一 MMU，也不是通用设备 IOMMU。

[Linux DMA 官方指南](https://docs.kernel.org/core-api/dma-api-howto.html)明确区分 CPU 与设备地址，驱动应使用 DMA 映射结果并管理其有效期；Linux 本身不要求每个设备必须配 IOMMU。[RISC-V IOMMU 官方规范源](https://github.com/riscv-non-isa/riscv-iommu/blob/main/src/iommu_intro.adoc)提供设备/进程上下文及 I/O 地址翻译机制；它是选型依据，**不是当前工程已经选定或具备的 IP**。

### 待决问题与建议路径

| 待决定事项 | 建议评估方式 | 依赖与代价 |
| --- | --- | --- |
| 首片设备地址契约 | 优先评估驱动管理的缓冲，向设备提交显式设备地址/长度/方向，限定可达区间 | 裸机物理布局、OS DMA 后端、地址宽度和生命周期需统一 |
| 物理不连续内存 | 评估连续池、分段提交或 scatter-gather；设备支持什么就暴露什么 | 描述符读取也有缓存同步、错误和越界检查；不假定现有 DMA 支持 SG |
| 是否需要 IOMMU | 以强进程隔离、任意用户缓冲、连续 IOVA 或共享虚拟地址需求为触发条件 | 选成熟实现时评估页表遍历、上下文标识、失效完成、故障队列及驱动 |
| 是否允许用户直接提交任务 | 先明确可信边界，校验范围/长度/访问方向，固定页面至任务终止 | CPU PMP 不等于 DMA 防火墙，软件检查也不能防止全部硬件故障 |
| 本地 GB 地址形式 | 建议使用独立偏移/handle 类型，并由受控映射转换成可达范围 | 分配代际、边界、对齐及释放后失效需一致 |

IOMMU 能改变翻译与保护能力，**不能替代第 02 节的数据同步**。若采用 IOMMU，映射撤销必须等待相关事务及翻译失效完成；若不采用，也要证明设备地址可达、缓冲有效、必要的物理连续性及隔离边界。

队长确定系统地址/隔离策略，TTY 主责软件映射与 OS 接口，各设备负责人实现地址检查和提交语义。G0 冻结首版地址类型及 IOMMU 是否纳入首片；G1 明确设备寻址能力；G2 验收裸机基础路径。OS 如纳入首片必须在 G3/G4 门槛中单列，沿用团队排期的范围条件。

### 验收用例与证据

测试 CPU VA 与设备地址不相等、最高地址位、范围溢出、越界/未映射、物理分段、任务中途撤销和释放后迟到访问。启用 IOMMU 时增加页表更新、TLB/IOTLB 失效、权限故障与多上下文隔离；未启用时验证直接映射及拒绝行为。提交地址和最终落点必须可对照，错误不能静默绕回低地址。记录地址图、能力表、生命周期状态及实际映射日志。

## 04　新增 IP 的寄存器数量、复位值与配置生效

![配置从软件写入到边界生效](../diagrams/2026-10-18_implementation_challenges/png/04_register_commit.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/04_register_commit.svg) · [可编辑 PPTX，第 4 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制、困难与失败场景

寄存器数量由软件必须表达和观察的行为推导。先给每个 IP 分配任意“几十个寄存器”会遗漏任务身份、完成和错误信息，也可能留下无必要的可编程自由度。复位值、板级初始化值、推荐运行值和只读硬件状态不是同一概念。

64 位地址经 32 位控制口分拆写时，硬件若实时读取高低半部，可能在两次写之间启动到混合地址。ISP 校正表和尺寸分别更新，会把新参数用于旧帧；写 START 时 busy 尚未清除可能覆盖任务；W1C 状态与新事件同拍若优先级不明，会丢中断。读取计数器、任务 ID 或完成队列若有副作用，还必须规定访问宽度与原子快照。

### 已有讨论及尚未冻结的内容

[IP 契约 §5](IP_DDR_Interface_Contract.md)已有控制宽度、START/busy、状态副作用、IRQ 和任务身份要求；[总纲 §6.5](SoC_Architecture_v1_Master_Plan.md)定义 C1～C16。当前[Cheshire 寄存器描述](../../hw/regs/cheshire_regs.hjson)使用 `regwidth: 32`，区分软件/硬件访问及复位属性，可作为本版本生成流程参考。它不规定所有新增 IP 必须照搬同一寄存器集。

**已有控制职责，尚无冻结的寄存器总数、偏移、IRQ 号和默认值。** C 编号不是寄存器个数或独立 Regbus slave 数。供应商 IP 必须采用其实际版本的字段及初始化流程；不要为了图上的 C2/C3 重新设计厂商寄存器。

### 建议形成的寄存器规格包

| 内容组 | 需要记录的字段类别 | 关键疑问 |
| --- | --- | --- |
| 能力/身份 | 版本、可用功能、地址/数据宽度、队列与资源限制 | 固定参数是否只读暴露；软件如何拒绝不匹配版本 |
| 参数 | 地址、长度、stride、格式、模式、阈值、参数版本 | 合法范围、对齐、分拆写和快照；哪些适合描述符/表而非 MMIO 阵列 |
| 命令 | 提交、启动、停止、排空、软复位 | 自清还是 W1S；busy 时拒绝/排队；重入及接受不明如何处理 |
| 状态/错误 | ready/busy、阶段、任务身份、错误码和出错地址 | sticky 保存、覆盖优先级、读取副作用、清除与新事件竞争 |
| 中断/调试 | mask、pending、清源、计数与溢出 | 事件与电平关系，清源顺序，共享 IRQ 与轮询是否等价 |

每个字段至少写明：名称、偏移、位域、访问权限、宽度、复位值/掩码及来源、合法编码、写入副作用、生效时机、错误响应、时钟域和版本。数量应在字段打包、描述符方案和对齐规则明确后由机器描述统计；地址空间预留大小与已实现寄存器数分开。

自研 IP 的初步建议是复位后不自动提交传输、状态无有效任务，未配置的地址/长度不能触发访问；**这不是将所有字段硬填为零**。PLL/PHY、硬件状态及需要非零安全值的字段必须有真实依据。配置可采用 pending/active 两套状态或任务快照，图 4 表示该机制建议；是否需要双缓冲及在哪个帧/任务边界提交由各模块决定。ROI 最多 256 项也不自动意味着 256 套 MMIO 寄存器。

各 IP 主责维护单一寄存器描述源和基本控制测试；TTY 统一 HAL/API、生成头文件与访问约定，队长统一地址/IRQ 和跨 IP 原子生效。G1 前形成可生成的首版，G2 驱动联调，G3 冻结软件可见 ABI；后续变更记录版本与兼容性。

### 验收与证据

验证上电/局部复位读回、保留位、非法地址/编码、写掩码、64 位参数分拆、START/busy 竞争、帧中途改参数、W1C 与新 IRQ 同拍、状态读取副作用和超时恢复。通过条件是活动任务只见完整配置、事件不丢不伪造、错误可定位。交付字段清单、生成源/头文件同版本哈希、访问测试及真实 IP 初始化依据；示例默认值不得冒充供应商值。

## 05　四口 DDR 接入与跨端口可见性

![四口共享前端和 DDR 跨口读写](../diagrams/2026-10-18_implementation_challenges/png/05_ddr_ports.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/05_ddr_ports.svg) · [可编辑 PPTX，第 5 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制与失败场景

四个 AXI 入口最后使用同一个 DDR 物理服务资源。某口报告接收成功不说明其他口已经能看到该写；ID 的顺序规则也不是跨独立端口的全局屏障。前端压缩、元数据缓存、CDC 和 Controller 队列都可能处于可见性边界内。

典型失败是 F0 的 LLC clean 完成后 F1 仍读到旧输入；或者 F2 帧写结束后 F3 读到上一帧/旧元数据。若超时只复位某个入口而下游仍保留写事务，重新分配帧缓冲后旧写会破坏新帧。普通存储自测若总走 CPU cache，还可能掩盖 DDR 实际未就绪或跨口问题。

### 已有方案及供应商输入边界

[总纲 §4.1、6.3](SoC_Architecture_v1_Master_Plan.md)已确定 LLC→F0→DDR.S0，GB 搬运→F1→DDR.S1，帧写→F2→DDR.S2，二维帧读→F3→DDR.S3。四个入口共享 Controller 外部的压缩/旁路服务，并保留四路下游响应归属。

[DDR 供应商会议问题](DDR_Supplier_Coherence_Questions.md)已对用户提供的 Datasheet V2.1 做过能力摘要与 Q1～Q7 整理；“最多若干口”的产品能力不证明四口实例已交付。本文未新增供应商答复，也不转载受限手册内容。旧三口问法应扩成四口矩阵，保留其版本背景。

### 最小澄清清单与实施顺序

| 输入/疑点 | 必须获得的答复或交付 |
| --- | --- |
| 实际实例 | 四口 AXI4 配置、每口宽度/ID/在途/时钟、配套 PHY/模型/视图及授权范围 |
| 完成点 | B 在什么队列/可见点返回；端口 A 写后如何允许 B 读；是否与属性、ID、地址重叠相关 |
| 顺序和并发 | 所有实际可写口对所有可读口的可见关系；同址并发如何串行化或禁止 |
| 错误 | 部分写成功、ECC/PHY/训练失败、R/B 错误、错误定位和 sticky 保存 |
| 停止与复位 | 每个隔离/排空/复位动作覆盖哪些队列、CDC 和已发 DRAM 请求，何时保证不再访问旧地址 |
| 服务与初始化 | ready 前访问处理、训练/重训、刷新/低功耗、仲裁与最大无服务间隔保证 |

先完成普通旁路模型和实际四口接口，再接完整压缩。若厂商 B 已保证所需跨口可见性，应直接引用该条件；否则依据其官方能力设计补充同步，不能仅发明 `visible_done` 信号而不说明下游如何证明。所有属性（包括 AxCACHE 等）按厂商接口与系统语义填写，不能把属性位当作自动一致性开关。

队长主责厂商对接、四口集成和完成条件；HYH 配合前端元数据，TTY 配合初始化与恢复。G0 关闭交付条件或登记关键路径阻塞；G1 接入可用模型；G2 普通区域四口可见；G3 压缩/异常完整矩阵。供应商无法提供目标实例时需由队长评估影响，本文不自动修改已确认拓扑。

### 验收与证据

对所有实际可写→可读端口对执行地址 X 写新版本、按契约完成、另一口读回；覆盖不同 ID、背压、同址/异址、部分行、前端缓存元数据、错误及复位。F2 以写为主、F3 以读为主，不虚构未实现能力。通过条件是许可交接后的每个读都看到正确逻辑数据；错误不早报成功；排空证明可追溯。保存供应商答复版本、模型配置、端口矩阵、波形和版本化数据检查记录。

## 06　共享无损压缩前端

![共享压缩的映射、元数据与响应汇合](../diagrams/2026-10-18_implementation_challenges/png/06_compression.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/06_compression.svg) · [可编辑 PPTX，第 6 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制、困难与失败场景

压缩核的无损往返只是必要条件。前端还要在不改变上游逻辑地址、字节结果和响应语义的条件下管理可变长度存储、元数据、部分写、竞争访问和失败恢复。一个 AXI 写可能拆成旧块读取、解码、合并、压缩、新数据写和元数据发布多个子事务。

例如写一个字节必须保护块内其他字节；两个端口同时更新同一块若没有合并/串行化会互相覆盖。先发布新元数据但新数据尚未可见会让读者解码错误；只压缩成功却漏报某个元数据写错误，会产生“成功响应、不可读数据”。不可压缩输入、ROI 小块多读、元数据争用也可能使平均压缩收益转为最坏延迟。

### 已有讨论及方向

[总纲 §6.3](SoC_Architecture_v1_Master_Plan.md)和[团队分工 §2.1](Team_Responsibilities_and_Tapeout_Schedule.md)已明确：HYH 负责整个共享前端，包括区域/块映射、普通旁路、元数据、部分写/跨块、事务跟踪、响应和恢复。四口共同解释同一逻辑区域；压缩器处理 W 数据，解压器处理 R 数据，AR/AW 走地址控制，B 走结果汇合，不能画成经过编解码核。

当前已有功能职责，**算法、块大小、元数据布局、分配机制和并发数尚未冻结**。图 6 的部分写合并是待具体化机制，不表示生产源码已有该服务。元数据通过现有下游路由访问，图和本文均不增加第五个 DDR 端口。

### 待决事项与推进步骤

1. 定义逻辑块、独立解码粒度、实际存储布局、原样块标识和最坏容量。原样回退必须由元数据明确标识，不能让不同口各自猜测格式。
2. 定义部分写/跨块拆分、WSTRB 合并、冲突块串行化和读者看到哪个版本。评估保守读改写的代价，再讨论可证明正确的优化。
3. 定义发布与失败协议：何时新块可读，旧块何时回收，哪些子事务成功才能返回上游成功；分配失败、元数据损坏、复位中断发布时怎样隔离并重建。
4. 统一所有口的区域属性，先普通旁路再启用压缩；改格式/区域前停止请求、维护缓存、排空并迁移或废弃旧数据。禁止从所谓普通旁路读取压缩字节当逻辑数据。
5. 建立成本模型：压缩率分布、不可压缩最坏情况、编解码吞吐/时延、元数据流量、部分写放大、ROI 额外读和资源共享公平性。

HYH 主责；队长审核跨口可见、分配/完成和存储同步；TTY 接入配置/恢复与统计接口。G1 必须完成格式、软件参考和部分写原型，否则无法可靠估算 G3 集成。G3 关闭功能与错误协议，G4 交付覆盖证据。

### 验收与证据

逐字节压缩/解压往返、不可压缩/极短/最大块、首尾部分写、跨块和 4 KiB 边界、多口同块冲突、ROI 非对齐读、数据/元数据任一子事务错误、发布中复位和资源耗尽。通过条件是逻辑数据完全一致、原请求拍数/ID/响应正确、失败不发布可用版本、旧版本不被过早回收。证据包括格式规格、独立参考模型、事务与元数据一致性检查器、压力和故障结果；平均压缩率不能替代正确性验收。

<a id="challenge-07"></a>
## 07　任务完成、错误处理与缓冲回收

![任务阶段及故障隔离恢复](../diagrams/2026-10-18_implementation_challenges/png/07_completion_recovery.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/07_completion_recovery.svg) · [可编辑 PPTX，第 7 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制与具体失败

接收命令、运算结束、总线传输结束、数据可见、消费者退出、资源可回收可能发生在不同时间。LVDS 帧末只表明像素生产结束；读 DMA 完成不等于 TX FIFO 已发送完；NPU done 不代表 GB 结果已经搬到 DDR。IRQ 是通知手段，必须知道它通知哪个完成点。

软件等待超时后直接把 GB/DDR 交给下一帧，旧事务仍可能写回来。更换 token 能识别旧 IRQ，却不能阻止旧 AXI 地址写。单侧复位也可能让请求/返回失配；缓存写回错误若在维护命令前发生，又在新命令开始时清掉，后续“同步成功”会建立在丢失数据之上。

### 已有讨论与初步方案

[IP 契约 §5、8](IP_DDR_Interface_Contract.md)、[同步设计 §6～7](DDR_GB_Coherence_Design.md)及[总纲 §8.3](SoC_Architecture_v1_Master_Plan.md)已有共同方向：建立任务/范围上下文，失败后停止新提交、保留缓冲、隔离并排空或受控恢复，确认旧活动终止后再复用。部分结果作废，从可靠输入重建；复位不修复数据。该恢复方向已记录，具体状态机和真实 IP 能力未落实。

### 需要逐 IP 填写的契约

| 阶段 | 必须回答的问题 |
| --- | --- |
| 提交前 | 范围、格式、参数版本、读写方向和引用者是否齐全；同步/权限是否已准备 |
| 已接收 | 接收确认是否可靠；重试会不会重复提交；接受不明怎样查询/隔离 |
| 执行中 | 数据写到哪里；可取消到什么程度；错误首次发生在哪个子事务 |
| 完成 | done/IRQ 精确指向哪一阶段；下游队列、元数据和所有读写是否仍在途 |
| 交接与释放 | 谁持有数据、谁仍有读引用；何种证据保证以后不会再访问旧地址 |
| 错误与恢复 | 哪些错误可局部恢复；需要扩大隔离时谁负责；状态保留至何时 |

建议用任务身份、阶段、有效范围和引用计数/等价所有权记录统一跨模块管理；具体编码和位宽待定。故障仍超时则保持隔离并上报平台级错误，不能为了回收内存强行成功。若产品要求硬故障时限，要另定不依赖被阻塞 CPU 的监控主体及预算。

队长统一系统完成/错误规则，各模块负责人实现自己的状态机和基本程序，TTY 实现公共等待/恢复服务。G1 每 IP 明确完成点，G2 普通链路验证，G3 压缩/全链异常闭环；G4 前不得只剩正常路径证据。

### 验收与证据

注入提交未接受、接受不明、执行中错误、最后响应迟到、数据已写但通知丢失、重复 IRQ、计数回绕、取消/复位中响应返回。要求成功只在全部条件成立时发布；失败保留可定位状态；隔离期间缓冲不被新任务使用；恢复后旧任务不能再访问。保存状态转换表、事务计数和软件生命周期日志，明确已验证的恢复等级，不能泛称“支持重试”。

## 08　AXI 协议、位宽与事务适配

![AXI 五通道的方向和适配责任](../diagrams/2026-10-18_implementation_challenges/png/08_axi_adaptation.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/08_axi_adaptation.svg) · [可编辑 PPTX，第 8 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制与失败场景

AXI 接口名称相同不保证配置匹配。地址宽度、数据宽度、ID、USER、在途数、突发限制、支持的窄访问、选通和原子扩展都需要两端一致。AW/W 是独立通道，不能假定地址先到或同时到；阻塞期间 payload 必须保持稳定，响应必须匹配原来源和 ID。

常见失败包括 256→64 位拆分丢 WSTRB、32 位寄存器读写落在 64 位总线错误 lane、R/B 被错误发起端接收、跨 4 KiB burst 未拆分、队列满造成资源循环等待。新增 master 会影响派生 ID 位数，简单截短会使两个事务发生身份碰撞。

### 已有方案与适用条件

[IP 契约 §4～5](IP_DDR_Interface_Contract.md)已有双端逐字段表；官方随附 [AXI 库说明](../../.bender/git/checkouts/axi-ecdc900686449c15/README.md)与 [Xbar 文档](../../.bender/git/checkouts/axi-ecdc900686449c15/doc/axi_xbar.md)提供当前依赖组件和顺序约束。应优先复用本版本适用的 converter、ID 适配、CDC 等组件，并核查实际参数、断言和支持范围。

v1 保持 Ara2/主 Xbar64；Ara 的 filter→等宽 converter→Xbar 路径保留。NPU 侧已有 256-bit 发起需求，但供应商端宽度和转换位置未冻结。供应商可提供 AXI4，因此 AXI3 桥不是必选。ATOP 是扩展，现有主存原子执行在 LLC 前；新增旁路普通写仍可能破坏 LR/SC 观察假设，不能用“不发 AMO”证明原子域安全。

### 推进步骤与边界

逐链路完成发起/接收双方签字的字段表，明确不支持访问的拒绝行为；再验证宽度/ID/选通转换；最后在四口、GB 与寄存器实际拓扑中做并发和复位回归。原子共享控制数据与设备数据按既有建议隔离；如确需跨 CPU/设备原子对象，必须另评统一观察域和缓存协议。

队长负责主 Xbar、GB 搬运和 DDR 适配，HYH 负责图像 DMA/前端，TTY 负责 eMMC/LVDS 周边控制及 Regbus 访问；TTY 不替其他 IP 承担全部协议验证。G1 关闭单元适配，G2 普通路径集成，G3 压缩拆分/重组和异常组合。

### 验收与证据

随机且定向的 AW/W 不同到达顺序、五通道独立背压、窄读写/非全 WSTRB、最短/最长合法 burst、窗口/4 KiB 边界、ID 复用/乱序、不同目标、reset 在途、SLVERR/DECERR 等按真实支持范围执行。要求无丢失/重复拍、选通字节正确、响应身份和顺序合法、非法请求不静默转换为成功。交付双端参数表、协议断言、端到端字节 scoreboard、死锁条件分析与可复现实例。

## 09　实时带宽、容量和有界服务

![输入输出缓冲与共享资源预算](../diagrams/2026-10-18_implementation_challenges/png/09_bandwidth.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/09_bandwidth.svg) · [可编辑 PPTX，第 9 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制、困难与失败场景

平均吞吐低于 DDR 标称带宽，不能保证采集不溢出或 TX 不欠载。传感器可能不能背压；DDR 刷新、长突发、压缩元数据、LLC 维护与 NPU 搬运会造成服务空窗。四口不产生四倍物理带宽，多个 GB 入口也不产生无限 SRAM 端口。

256 个小 ROI 可能反复读取/解码相同块，ROI 有效像素很少但 DDR 与解码流量很大。压缩在正常图像上收益好，噪声帧或已压缩数据却可能接近原样甚至增加管理开销。参数、激活、临时结果和双缓冲同时驻留时，GB 容量可先于算力成为瓶颈。

### 已有讨论与预算方法

[IP 契约 §8.2、12.3](IP_DDR_Interface_Contract.md)、[GB 服务约束](Global_Buffer_CPU_Access.md)和[总纲 §4、8.1](SoC_Architecture_v1_Master_Plan.md)已有平均流量、驻留容量和最长等待的区分。1080p/60、历史 DDR 档位和容量只是旧示例/候选，不是本项目指标；本轮不补造产品数值。

建议预算分别填写：

- 帧有效负载 `H × W × 每像素有效字节 × 帧率`；再加入实际 packing、stride、读写方向和总线开销。
- ROI 统计有效输出字节、实际 DDR 字节、解码字节三套数；重叠 ROI 的重复工作按真实调度计算。
- FIFO 按最坏区间的累计到达减累计服务求峰值，加约定余量；只有到达率恒定且其他条件成立时才可简化成“输入率×最大无服务间隔”。
- GB 容量计入所有同时存活的权重、激活、临时区、输入输出和搬运缓冲；DDR 再计帧引用、压缩元数据与最坏存储分配。
- M5 的理想每方向数据上限为 `8 × f B/s`，这是 AXI64 的接口算术上限，尚未扣除冲突、等待和实际宏服务，不是实测吞吐。

### 待输入与推进责任

G0 需要传感器/TX 对端格式、峰值、背压能力、帧率/期限；代表模型、并发负载、ROI 分布和质量要求；实际 DDR/宏配置。HYH 提供图像/ROI/压缩模型，TTY 提供 LVDS/eMMC 和软件调度开销，队长汇总 NPU/GB/DDR 资源预算并确定仲裁目标。

G1 建立可复现流量模型和硬件计数点，G2 测普通区域基线，G3 在完整并发和最坏压缩条件下关闭服务预算。若过载不可避免，丢帧、降速、中止或降级行为需产品决定；本轮不擅自选择。对不能背压的输入，应证明不溢出或明确按约定报告丢帧，不能静默损坏图像。

### 验收与证据

覆盖最大帧/ROI 工作集、持续并发、DDR 长停顿、LLC 维护、不可压缩块、最不利 bank 冲突。记录每帧时延、各源最长等待、FIFO 高水位、实际 DDR/解码字节、GB 利用与功耗/面积相关约束。用计数或波形解释瓶颈，按明确期限和容量阈值判通过；平均值或单算子峰值不能关闭实时项。

## 10　算法、精度、布局与数据驻留

![从参考模型到异构执行与结果检查](../diagrams/2026-10-18_implementation_challenges/png/10_algorithm_layout.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/10_algorithm_layout.svg) · [可编辑 PPTX，第 10 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制与失败场景

阵列能完成矩阵乘不等于代表应用可运行。首片需要的算子、数据类型、累加精度、舍入/饱和、布局、padding、stride 和尾块规则决定硬件、运行时与 GB 组织。缺算子回退到 CPU/Ara 会增加搬运/重排及同步成本；如果各后端对格式理解不同，传输字节正确也会算出错误结果。

ISP 校正参数版本、RAW packing 与像素位宽同样影响数值结果。极值输入可能触发溢出，非整块尺寸暴露尾块缺陷；量化模型平均误差小也不代表任务质量达标。只测规则尺寸和一个算子会掩盖图级内存峰值及格式切换成本。

### 已有讨论与初步方案

[CPU＋NPU 推理体系调研](CPU_NPU_Inference_Systems_Survey.md)、[OS 选择讨论](Edge_LLM_OS_Selection.md)和[总纲 §6.5](SoC_Architecture_v1_Master_Plan.md)已有编译/运行时/驱动/计算的责任划分，以及固定输入→小算子→子图→应用的验证顺序。它们是参考路径，不代表选定模型、框架或产品 OS。已有 CPU/Ara 示例也不能替代新增 NPU 的数值验收。

队长负责 NPU 算法/HW/SW 一致性，HYH 负责 ISP/压缩参考与图像质量，TTY 提供公共平台和运行入口。各主责交付自己的黄金参考与基本程序，不把全部算法驱动交给 TTY。

### 设计决策与最小推进步骤

1. G0 冻结首片代表应用、算子集合、精度/质量底线和测试数据；明确必须硬件加速与可回退部分，后续新增算子计入变更。
2. 定义统一数据格式包：张量轴顺序、像素 packing、字节序、通道 padding、量化 scale/zero point（如采用）、累加/舍入/饱和、参数版本与布局转换。
3. 用独立参考生成极值、随机、真实样本和非整块输入；决定定点 bit-exact 或浮点/量化误差判据，禁止测试后再随意放宽阈值。
4. 结合第 09 节给出 tiling 和驻留计划，明确谁装入、谁计算、何时可覆盖、何时搬出；把重排、同步、回退和参数加载计入端到端周期。
5. G1 小算子/ISP 核心处理对照；G2 子图与真实数据流；G3 完整应用及质量/性能收敛。OS 需求若进入首片，再验证其调度和向量上下文，不以裸机通过替代。

### 验收与证据

逐算子比较中间值和输出；覆盖最小/最大值、溢出、非整维度、不同 stride/packing、跨 tile 边界、参数帧边界更新和 CPU/Ara 回退。端到端使用固定模型/数据哈希及预先确定指标，记录数值、质量、周期和流量。通过条件既包括算法正确，也包括工作集未越界、参数版本一致与代表应用期限满足。

## 11　启动、时钟、复位与跨时钟域

![启动依赖与运行时受控重配置](../diagrams/2026-10-18_implementation_challenges/png/11_boot_clock_reset.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/11_boot_clock_reset.svg) · [可编辑 PPTX，第 11 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制与失败场景

执行 PLL 初始化代码的 CPU 首先必须有安全时钟、可取指 ROM 和可用早期栈；不能让该代码创造自身第一个执行条件。DDR 未训练就加载程序/栈会访问无效存储。多个时钟域之间仅同步单个 ready 位，不能保证多位数据、事务队列和复位状态一致。

运行时切钟若没有排空，会截断 AXI/像素传输；只复位 FIFO 一侧可丢失计数或旧数据。PLL locked、PHY trained、Controller ready 和系统允许访问应区分。MMCM/MIG 的旧 FPGA 接线与 HelloWorld 结果不能证明 ASIC ready 放行已经正确。

### 已有讨论及缺陷

[平台 ROM 与时钟/IP 配置约定](../03_Platform_ROM_Clock_IP_Configuration.md)记录了用户确认方向：沿官方 Platform ROM 钩子，在安全启动条件下配置 PLL 和必要 IP，并保留运行软件重复配置接口。当前官方集成入口可见[仓库集成说明](../../docs/tg/integr.md)。[返回路径核查](../handoffs/L01_platform_rom_boot_review.md)和[决策登记](../handoffs/L01_platform_rom_decision_tracking.md)已登记 S01-B01，不能忽略它直接启用非零 Platform ROM。

当前缺陷表指出 `jalr t0` 普通返回会落入 `boot_next_stage`；默认 PlatformRom=0 绕过，已有官方修复 `9b4c222df72f74f90ab9f36d80ba7b527f92e62b` 可在本地历史核对，尚未应用。ROM C 入口栈对齐也需定向复核。两者是待实现/验证的具体问题，不是重新设计启动机制的理由。

### 推进顺序与责任

TTY 主责启动/BSP/链接与运行时控制，队长负责时钟复位架构、真实 PLL/DDR 输入及配置审核，各 IP 主责提供 reset/ready/CDC 契约。

- G1：按官方修复评估最小改动和 ROM 重新生成；明确上电安全时钟、SPM 栈与 Platform ROM 返回路径，完成真实库/时钟资源初步确认。
- 在第一次 DDR 访问前完成 Controller/PHY 初始化、训练、错误检查和不被缓存掩盖的访问验证。ZSL 向 DDR 加载前同样需要此条件；最终启动介质待定，eMMC 数据加载安排在上电复位后、DDR 就绪的初始化阶段；它不因此成为 Boot ROM 的启动介质要求。
- G2：逐域建立时钟/复位图、异步 FIFO/握手、复位释放、单侧 reset 和在途事务处理。控制 CDC、数据 CDC、复位域检查分别开展。
- G3/G4：验证允许的运行时切钟/重配置状态和失败回退，所有合法工作点/约束有真实 IP 依据。若产品未要求某种调频，不自行增加功能。

### 验收与证据

默认与非零平台入口、返回成功/失败、PLL 不锁/失锁、DDR ready 超时、复位在途、异步时钟比和相位变化、动态重配中断、SPM/DDR 栈切换。通过条件是访问依赖满足后才放行，失败可定位且保持受控状态，合法 CDC 不丢数据，源码与生成 ROM 指令一致。保存启动轨迹、时钟复位契约、CDC/RDC 报告及有效约束；静态 CDC 无违例也不单独证明协议/恢复正确。

## 12　工艺宏适配、DFT 与物理实现

![逻辑消费者、宏适配和签核关系](../diagrams/2026-10-18_implementation_challenges/png/12_asic_dft.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/12_asic_dft.svg) · [可编辑 PPTX，第 12 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制、困难与失败场景

FPGA 的 XPM/MIG/MMCM/PAD 适配不是简单改实例名。真实 SRAM 的读时延、写掩码、端口数量、同址碰撞、初始化和低功耗/测试语义可能与逻辑假设不同；CVA6 cache、Ara VRF、LLC 和 GB 都要逐消费者核对。增加一级宏读延迟可能破坏流水线，掩码粒度不同可能使窄写破坏邻字节。

DFT 需要测试时钟/复位可控、状态可观察、宏测试接管及功能隔离。现有 LLC tag BIST 不等于全芯片 SRAM MBIST，Ara 中绑死的 test/scan 信号也不是可制造测试证明。物理上宏位置、总线宽度、时钟树、供电和布线拥塞会反向限制频率/容量；RTL 仿真通过不覆盖这些条件。

### 已有盘点与实际缺口

[ASIC 适配与证据手册](ASIC_Adaptation_and_Evidence.md)已经按 SRAM/ROM、PLL/PAD、PHY、复位和 DFT 列出语义与资料责任；[02 提取规格](../02_Cheshire_Ara_ASIC_Extraction_Handoff.md)保留独立固定工程目标。**尚未实施提取或真实工艺适配**，供应商视图和工具许可仍是外部输入。本轮不创建 ASIC 工程、不裁切依赖，也不把 Vivado 文件列表当 ASIC 可用清单。

### 推进步骤与既有责任

| 承担者 | 应关闭的工作 | 最晚门槛 |
| --- | --- | --- |
| 队长 | 工艺/IP 协调、固定配置、宏需求、SDC/综合/STA/等价/ECO和最终技术放行 | G0 资源表；G1 真实库试跑；G4/G5 收敛 |
| HYH | DFT 架构、Scan/MBIST/ATPG、测试时钟/复位、覆盖缺口 | G1 初步接管方案；功能冻结前落实可测试性；G5 签核 |
| TTY | 物理流程、宏/IO 布局、CTS/P&R/提取、物理/电源完整性、封装板接口 | G1 小设计流程；G3 持续评估；G5 签核 |
| 各 IP 主责及指导方 | 局部适配、真实约束与测试接口；实验室指导评审 | 指导人和时间需实际落实，不能记为已有人力 |

逐宏建立账本：消费者、逻辑需求、供应商版本/受控资料位置、功能/时序/物理视图、模型差异、唯一绑定方式和验证。明确 ROM 生成源与掩膜/初始化工艺；硬复位清零整个大 SRAM 是否可行不得凭仿真行为假定。正式签核的 corner/mode、例外、IO 约束、测试模式和工具版本需可追溯。

### 验收与证据

宏适配验证正常/冲突读写、掩码、时延、未初始化/有效位、测试进入退出和 reset；综合/等价验证实现选择正确；CDC/RDC、STA、DRC/LVS、IR/EM、DFT/ATPG 等按真实工艺与交付要求分别出报告。应记录约束覆盖、未分析路径、waiver 理由及签字责任，不能把“工具退出 0”当全部签核通过。文件只记录授权摘要与受控位置，不保存限制传播内容或许可密钥。

## 13　验证、调试能力与既有实现缺陷

![验证闭环及已登记缺陷](../diagrams/2026-10-18_implementation_challenges/png/13_verification.png)

[SVG](../diagrams/2026-10-18_implementation_challenges/masters/13_verification.svg) · [可编辑 PPTX，第 13 页](../diagrams/2026-10-18_implementation_challenges/export/diagrams.pptx)

### 机制与主要困难

三人团队同时承担设计、软件、系统与后端，容易把单模块正常路径通过当作集成完成。真正难复现的问题往往只在队列拥塞、跨端口交接、元数据错误、旧回填或复位中出现。若没有任务身份、阶段和队列/错误观测点，板上只剩“卡死或结果不对”，定位成本会超过预留时间。

验证应由独立期望行为检查 DUT，而不是读取 DUT 算出的校验值自证正确。正常运行、故障诊断、恢复后再运行和长时间压力分别建立证据。已有 RTL/示例存在，不表示本配置支持全部外设、接口或 OS。

### 已有缺陷登记：与架构选型分开

### 建议验证层次与执行责任

1. 单元：每个 IP 主责交付协议、数值、错误和复位测试及基本控制程序。
2. 子系统：GB 竞争、缓存维护、四口普通路径、压缩事务、采集/ROI 分别建立参考检查与故障注入。
3. 系统：TTY 组织固定配置/命令/日志；队长维护 NPU/内存并发，HYH 维护图像/压缩检查。运行真实场景及异常恢复，不把全部验证压给 TTY。
4. FPGA：保留现有可运行工程用于对照；证明与被测源码/配置对应，再做数据和性能检查。用户报告的 HelloWorld 只保留其历史范围。
5. ASIC：第 12 节制造与物理证据独立验收；不从功能回归推导可流片。

G1 即纳入必要的状态/计数/错误观测，G2 建立普通路径回归，G3 覆盖完整并发和故障，G4/G5 按各自门槛关闭。日志至少含版本、配置、随机种子、请求/任务身份、输入数据哈希、期望结果、失败阶段、工具与命令。硬件调试资源和计数器数量按定位需要及成本评审，尚不冻结具体寄存器。

### 关闭判据

每个缺陷有触发条件、最小复现、原因、修复版本、修复前后对照、关联回归和未测边界；每个需求有测试/断言/分析覆盖和结果。覆盖率目标、允许 waiver 和签核主体应预先定义。代码阅读、编译通过、已有 ELF/bitstream 或文档图稿检查不能填入 RTL/板测通过栏。
