## 2. 写回失败、等待与重试

**Q：评审第一项真正增加了什么？**

评审指出：普通替换也可能发生写回错误，且时间可能早于同步命令。例子是 CPU 写 x=2，LLC 替换该行时下游报错，旧行随后被替换；以后同步 x，已没有该脏行可供 clean，检查本次维护可能看不出此前的数据问题。作者同意，需要使相关错误影响跨命令保留。旁路事务须单独分类；上游存在错误监控，不能据内生写回缺口说成“系统没有任何错误报告”。

**用户追问：在什么情况下替换写回失败？不能等待或重试吗？为什么新同步会清掉历史错误？**

DDR 忙、刷新和正常端口竞争通常表现为暂不接受请求或响应延迟，LLC 应等待。返回错误是另一种情况：地址未映射可产生 DECERR，不支持的访问或下游检测到异常可产生 SLVERR。一直不返回响应则是尚未完成或故障阻塞。具体 IP 支持哪些错误原因仍需查资料；本工程未故障注入复现。

当前 w_master 实现了等待 B，收到 B 握手后却不检查响应内容，没有错误后重新发出的分支。可以增加重试，但必须保留旧地址和数据、阻止后续覆盖，并规定持续失败的退出方式。地址映射错误等原因不会仅因多等一会儿自动消失。

**作者更正：“新同步清掉历史错误”不是当前源码事实。** 当前写回路径未记录这个错误；讨论的是未来若新增错误标志，就不能在每次新同步开始时无条件清零。这是需要避免的实现风险。原回答未交代这个前提，已经在主文第 7 章明确更正。

依据：[w_master](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/eviction_refill/axi_llc_w_master.sv)、[config 完成计数](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/axi_llc_config.sv)、[AXI 规范 A3.4](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)。回填模块也未把 RRESP 纳入成功判断，列入同类可靠性核查；修复位置和实际故障影响未验收。

## 3. 旧事务、资源复用与数据恢复

**Q：评审为什么强调“检测到错误不等于能保留脏行重试”？**

tag store 在普通 miss 时安装新 tag，flush 时清除旧 tag，不等待对应写回 B 成功；写回 FIFO 随 W 握手弹出数据。旧数据在错误刚到时可能仍留在阵列，但当前没有保证旧地址、数据和状态被持续保留以便重发的流程。评审提出两种可选恢复目标：失败后重建／平台恢复，或增加保存机制以支持透明重试。作者认为需要明确区分，但用户尚未选择透明重试或具体硬件方案。

**用户追问：旧事务是什么？谁发起？为什么旧事务不会写？不要只讲抽象结论。**

“旧事务”指前一任务尚未完成的访问。例如 CPU／Ara 之前的读写、LLC 发出的写回／回填、搬运器或帧 DMA 的搬运。它们可能仍在本地队列、互连或 DDR 控制器中。

具体例子：任务 A 要把 GB 中 4 KiB 结果写到 DDR 地址 P，只完成部分时软件等待超时。软件若立即把 P 分给 B，A 后续继续发送的写，或已经进入下游队列的写，可能覆盖 B 的数据。软件超时不会自动撤销搬运器任务。

**作者澄清：不是“旧事务天然不会写”，而是复用 P 之前必须确认 A 不再访问 P。** 可以等 A 和其访问完成，也可以采用经过验证的停止／排空／隔离／复位流程。只停止新增请求，仍需处理下游已接受的部分；换 task ID 只能区分通知。

即使 A 已停止，P 可能仍只有半份输出。此时可重新初始化 P 再运行 B，但不能把它当作完整的 A 结果。检测错误、停止活动、恢复数据分别解决“知道失败”“防止继续破坏”“取得有效内容”。原总结未给出上下文，本轮以该例子替换主文中的抽象说明。

依据：[tag store](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/hit_miss_detect/axi_llc_tag_store.sv)。A/B 示例解释拟议设备集成的恢复要求，不是已经在当前未集成设备路径上复现的故障。

## 4. 维护窗口与各层确认

**Q：评审是否推翻了当前的排空顺序？**

没有。评审认可先排空依赖 LLC 的上游写，再隔离 LLC 进行维护。补充要求是：窗口阻止新的冲突请求，但允许旧请求的数据和响应继续推进；命令接受、上游排空、L1 状态更新、LLC 维护和整体同步完成各有不同含义。

WT 的 DRAIN 排空后先返回 IDLE，再检查 flush 请求；新增控制器需保持或锁存请求，不能随意打一拍脉冲后把局部 ack 当成整体完成。读控制器的等待、取消状态也须纳入排空分析。Ara inval_ready 是接收握手，不能代替跨层完成。

## 5. SPM 栈访问的短暂等待与故障挂起

**用户追问：CPU 为什么会卡在 SPM 栈访问？正常情况不会卡住，是不是过于谨慎？哪些条件才会发生？**

SPM 是使用 LLC 阵列的片上存储。当前 LLC 入口隔离模块放在缓存／SPM／旁路分流之前。栈若位于 SPM，CPU 在维护期间发出必须走出 L1 的栈访问，例如读取栈数据发生 L1 miss，就会经过被隔离的入口而等待。L1 维护还可能清掉原先驻留的栈行。

**正常情况：维护引擎自主结束并解除隔离，CPU 继续。这是有限等待，不是死锁。** 永久等待需额外条件，如下游一直不返回 B、接口被错误关钟／复位、互连缺陷，或新维护引擎要求被阻塞的 CPU 回调才能继续。作者原先混用了“卡住”，本轮明确区分这两种情况。

程序是否使用 SPM 栈由启动与链接决定，dram.ld 会把栈放在 DDR，不能说所有程序都在 SPM。即使状态寄存器在另一条路径，CPU 也可能先阻塞于栈访问，执行不到轮询。只有产品要求故障也在限定时间内处理，才需明确不依赖受阻 CPU 的监控主体；用户尚未冻结硬故障时限及监控实现。

依据：[LLC 入口隔离位置](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/axi_llc_top.sv)、[dram.ld](../../../../sw/link/dram.ld)、[crt0](../../../../sw/lib/crt0.S)。本轮没有仿真证明该停顿或故障序列已经发生。

### 2. 按影响排序的发现

#### 2.1 高影响：LLC 内生写回错误确实会被遗漏，旁路事务应另行分类

**位置：**主文第 7 节，尤其第 161、168、170 行。

**源码事实：**

| 事务类型 | 实际路径和错误处理 |
|---|---|
| 普通脏行替换 | 经过 `axi_llc_w_master`；B 握手后继续推进，没有使用 BRESP 更新结果 |
| 主动 flush | 使用相同写回路径；flush 描述符退出形成计数，config 据计数结束维护 |
| LLC 旁路事务 | 通过 bypass demux/mux 返回下游 B/R 响应，不经过上述写回完成逻辑 |
| 上游错误监控 | CVA6、DMA 等已有 bus-error 观察点，但只能检查其连接位置实际返回的响应 |

证据见 [w_master 的完成状态机](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/eviction_refill/axi_llc_w_master.sv)、[flush 完成计数](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/axi_llc_config.sv)、[旁路响应连接](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/axi_llc_top.sv)。

现有 [CVA6 bus-error 实例](../../../../hw/cheshire_soc.sv)观察 `core_out_req/rsp`；[错误检测模块](../../../../.bender/git/checkouts/unbent-a93c32aef5b319fd/src/axi_err_unit_wrap.sv)确实检查 BRESP/RRESP。**它不能还原已经被 LLC 内部吞掉的错误。**在此次检查的 SoC—FPGA DDR 连接中，也未找到覆盖 LLC 全部内生写回的独立错误上报闭环。

**最短反例：**

1. CPU 写 `x=2`，LLC 持脏数据，DDR 仍为 1。
2. 无关地址的访问触发 `x` 被替换。
3. DDR 返回写错误，LLC 按完成继续运行。
4. 后来同步 `x`，缓存已经没有该脏行；只检查“本次 clean 是否出错”得到成功。
5. S1 读取到 1。

因此，错误覆盖范围不能只从维护命令接受时开始。

**最小建议：**

- LLC 写回层或其下游观察点必须捕获错误，并与维护成功判定连接。
- 对普通替换错误，保留跨命令的错误状态或受影响地址信息；无法精确判断影响范围时，应保守地拒绝后续相关同步成功。
- 同步服务负责汇合错误并阻止设备准入；DDR 平台负责提供真实的响应、错误归属及复位契约。
- 同类检查还发现 LLC 回填路径没有将下游 RRESP 纳入成功判定，宜一并进入可靠性验收范围。

**验证：**分别对普通替换、主动 flush、旁路读写注入错误；增加“错误发生在创建任务上下文之前”的用例。不能只测主动维护。

**分类更正：**这是引入 GB 前已经存在的可靠性问题；“系统没有任何错误报告机制”则过于宽泛，应撤回。

#### 2.2 高影响：检测到写回错误，不代表能够保留脏数据重试

**位置：**主文第 148、168、170 行。

[tag store](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/hit_miss_detect/axi_llc_tag_store.sv)在普通 miss 时安装新 tag；flush 则在 tag 查询结果被接受时清除旧 tag。这些动作发生在相应写回 B 成功之前。

**影响：**即使新增 BRESP 检测，错误发生时也不能直接假定旧行仍以完整的“地址＋脏状态＋数据”形式保留。普通替换后还可能继续回填，覆盖原数据。flush 时数据阵列暂时仍有旧值，也不等于已经具备可恢复副本。

修订稿“能否保留数据重试取决于恢复设计”的分类正确，尚需在接口评审中选择恢复目标：

- **近期较小实现：**错误后任务失败、禁止消费结果、停止相关资源复用；在可靠停止旧事务后，由可验证的数据源重建，或升级为平台恢复。
- **要求透明重试：**必须增加保留 victim 数据和地址、延迟释放或替换、错误关联及重试控制。成本明显高于增加错误状态位。

这两种都是建议，尚不是已批准决策。尤其不能承诺“复位后继续使用原缓冲区内容”：复位可以停止活动，却不会自动恢复丢失或部分更新的数据。

**验证：**在最后一个 W beat 后返回错误，随后制造同组替换；检查旧行是否仍可重建、失败状态是否阻止消费和复用。

#### 2.3 重要接口要求：WT 的 DRAIN／FLUSH 可复用，但不是完整维护窗口

**位置：**主文第 65、156、164 行。

[WT missunit](../../../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/cache_subsystem/wt_dcache_missunit.sv)支持等待写缓冲为空和 MSHR 清空，再扫描失效。需要明确其边界：

- `DRAIN` 屏蔽新读 miss，继续推进写。
- 排空后先回 `IDLE`，因此外部 flush 请求必须保持有效或被可靠锁存，直到后续进入 `FLUSH`。
- `flush_ack` 表示该次 L1 扫描结束，不包括 LLC 和 DDR。
- 写缓冲入口及各读控制器还有独立状态；“MSHR 为空”不能替代所有已接受请求的完成判定。
- L1 完成后，跨层维护期间仍须维持冲突访问限制。

[WT 顶层 busy 汇合](../../../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/cache_subsystem/wt_dcache.sv)本身就包含读控制器、missunit 和写缓冲，说明这些状态不能只看一个。

**迟到回填应作如下精确判断。**

当前源码确实允许已取消的 load 仍留下在途缓存事务：[读控制器进入 KILL_MISS 后继续等待响应](../../../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/cache_subsystem/wt_dcache_ctrl.sv)，MSHR 则由 `load_ack` 清除，返回数据仍可安装缓存行。

因此，若未来实现错误地采用：

> 已接受 miss → CPU 取消该 load → 仅发失效并认为完成 → 旧响应返回并重新安装

就可能恢复旧副本。这个风险不需要假定存在无根据的硬件预取。

**但修订稿要求完整写前排空，已经排除了相应交接前事务。不能再把上述序列当作修订后基线必然存在的漏洞。**

Ara 专用入口也不能直接替代维护服务：[adapter](../../../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/cache_subsystem/wt_axi_adapter.sv)明确依赖无其他并发事务的前提；`inval_ready` 是接收确认。其仲裁还要求专门检查与读响应同时出现的情况。

**最小建议：**将窗口定义为“禁止新的冲突请求进入，但允许旧事务及其响应继续前进”，并明确上游排空、L1 更新完成、LLC 完成三个不同确认。不要用一个 flush 脉冲串接所有层。

**验证：**覆盖读 miss 已发出、等待接受、取消、响应背压、写缓冲同字节再次写入，以及维护期间无关 CPU 流量。检查完成以后是否仍可能出现目标范围旧回填或旧写。

#### 2.4 重要平台要求：正常自主完成与故障时可恢复，需要分别证明

**位置：**主文第 73、148、150 行。

修订稿已正确禁止“先隔离 LLC，再等待依赖 LLC 的上游写”。此项不应继续列为未修正的方案错误。

但现有 [LLC 隔离位置](../../../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/axi_llc_top.sv)在缓存／SPM／旁路分流之前。因此：

- 保留 SPM way 内容，不代表维护期间仍能访问 SPM。
- 状态寄存器位于独立路径，也不代表 CPU 能执行到那次读取；CPU 可能先阻塞在栈访问或取指上。
- 当前写回状态机等待 B，没有自带有限时间完成保证。

**条件性反例：**

> flush 隔离入口 → CPU 阻塞在 SPM 栈访问 → 下游永久不返回 B → 维护无法结束 → 软件超时处理无法执行。

这是故障条件下的进展问题，不能用普通轮询预算解决。

**最小建议：**

- 对正常维护，证明引擎不需要暂停中的 CPU、ISR 或软件回调。
- 对故障，明确独立计时／监控的执行主体、可访问的恢复控制路径以及复位覆盖范围。
- 停止发新请求与清除已接受请求必须分开。只复位搬运器、只换 task ID，都不足以证明 DDR 队列中的旧写已经消失。
- 若无法证明安全停止，允许保留隔离并上报平台故障；不要为了让函数返回而解除资源保护。

**验证：**分别阻塞 AW、W、B、R；让 CPU 的代码／栈访问落入受隔离路径；验证无需 CPU 配合仍能完成正常维护，且故障路径不会提前复用缓冲区。

#### 2.5 待供应商确认：成功 B 响应是否足够，应依据完整跨口契约判断

**位置：**主文第 77、91、170 行。

当前修订措辞合理，不应预设新增 DDR 完成接口。

[AXI IHI0022H 的 A6.5.2、A6.6及 A7.1.1](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)规定完成响应的可观察性，并要求 Issue G 及以后符合相应多副本原子性要求。提前响应可以通过内部排序和转发实现，并不要求等待实际 DRAM 单元写入。

因此，也不宜笼统声称“AXI B 对其他 master 没有保证”。实际未决项是：**供应商宣称的规范版本、三个端口是否属于同一保证范围，以及集成的桥、CDC 和通知路径是否维持该保证。**

最小确认问题是：

1. S0 成功 B 之后才发起的 S1／S2 同地址读取，是否保证看到该写或更新版本？反方向是否相同？
2. 该保证适用于哪些 AxCACHE 属性、端口及 ID；提前 B 后如何处理跨口读？
3. 错误响应是否可能伴随部分写入；是否存在 B 之后才报告的存储错误？
4. 停止、排空和局部复位分别覆盖哪些内部队列？何时能证明旧请求不会再修改 DDR？

若现有响应语义满足这些条件，完成计数及发布排序即可使用；否则再针对缺失语义讨论补充机制。当前不能冻结额外控制器接口。

### 3. 建议后的完整交接流程

下列流程基本维持修订稿，只细化成功与释放条件：

1. **保留上下文和全部资源。**记录实际传输范围、向外覆盖的维护范围、DDR／GB 资源、任务身份及阶段；基线拒绝输入输出维护范围重叠。
2. **完成生产并交出使用权。**CPU、Ara、中断及其他主设备停止冲突访问；LR/SC 不跨越交接。HAL 建立编译器和访存顺序。
3. **输入同步。**建立维护窗口，允许旧事务前进，保持 LLC 接收直到上游写排空；再协调 LLC 在途事务并 clean。汇合既有错误状态、维护结果及跨口可见性，成功后才准许搬入。
4. **输出准备。**在相同保护条件下排空旧写，clean＋invalidate；保留未覆盖字节，等待全部状态更新完成。
5. **发布任务。**描述符本身已可见；登记待提交状态后启动。接受结果不明确时按可能已经启动处理。
6. **搬入、计算、搬出。**分别等待其真实完成；最终完成必须覆盖所需读写响应、错误检查和 CPU 端口可见性。
7. **输出同步。**限制新冲突请求，收束已有回填，最终失效 L1D／LLC。若发现目标范围意外脏数据或写事务，任务失败；不能把它当普通 clean 写到设备结果上。
8. **消费和释放。**CPU 才读取结果。只有任务、维护和搬运均不再可能访问所保留资源，才能释放 DDR／GB 和上下文。
9. **任一步失败。**保留上下文及资源；先证明旧活动结束或被可靠隔离，再决定重建、释放或平台恢复。

FENCE 负责访问顺序，缓存维护负责副本状态；[RISC-V FENCE 规范](https://docs.riscv.org/reference/isa/v20240411/unpriv/rv32.html)没有赋予它通用 LLC clean 功能。本地 FENCE 提交条件包含 WT 写缓冲为空，但向量 profile 的 `DcacheFlushOnFence=0`，两者不能混淆。

### 4. 正确性边界、实现成本和图文结论

**部分行基线成立。**以当前 32 B L1D／64 B LLC 为例，应保留整个 64 B 公共维护范围的使用权；仅把维护地址向外取整、却允许邻接对象继续写入，仍会破坏结果。正文 `[10,9,30,4]` 示例正确。完整覆盖省略旧数据写回，只适合作为后续优化，并须同时证明旧写被消除、全部字节覆盖及失败时不会消费部分结果。

**输入干净副本可以保留。**前提是交出的是设备只读输入、不存在其他 writer，且本次排空和 clean 成功。其他地址引发的干净替换不会破坏输入；正常流程下，输出范围也不应再有可覆盖设备结果的旧脏 victim。

**原子访问边界正确。**当前原子适配器位于 LLC 上游，不能自然观察 S1／S2 写。禁止 LR/SC 跨交接、控制对象与设备数据分行，是可行基线；若以后允许设备修改同一 LR 字节，必须满足 [RISC-V A 扩展](https://docs.riscv.org/reference/isa/v20240411/unpriv/a-st-ext.html)的 reservation 语义，不能只依赖 L1 失效。

**重叠和并发应单独扩展。**原地计算需要先保证原输入已被完整消费，再允许覆盖相交输出；双缓冲也必须按维护范围而非仅按数组字节范围判定独立。当前单任务教学基线不应被解释为已经支持这些模式。

近期可以复用 WT 排空、全索引失效和 LLC way 维护的组成部分，但仍需新增跨层控制、错误汇合、准入及完成状态。按 way 维护还会处理无关数据，并阻塞共享入口；它不能直接等价为任意范围 clean 或 invalidate。

当前向量 profile 为 8 KiB、4 路、32 B 行，即 256 个驻留位置。探测成本可估为：

- 逐地址：约 `ceil(范围长度 / 32)` 次行查询，再乘端口调度成本。
- 驻留扫描：检查 256 个 tag；若四路并行读取，可按 64 个 set 组织，但不意味着总耗时必然是 64 周期。
- 总等待还包含写缓冲排空、LLC 扫描、脏写回、DDR 仲裁及失效后的重填。

大范围时 LLC 和 DDR 很可能比 L1 tag 查询更主要，须测量，不能据此给出面积或性能百分比。

现有 [DMA HAL](../../../../sw/include/dif/dma.h)主要提供提交和 done-ID 轮询，没有完整维护、错误恢复及超时闭环。后续 Linux 可复用底层能力，但应由平台 DMA 后端实现，其所有权切换遵循 [Linux 6.5 DMA API](https://docs.kernel.org/6.5/core-api/dma-api-howto.html)，不能把裸机接口名称直接映射成已有驱动支持。

三张图及生成源的主要连接、数值和顺序与正文一致，工业版系统布局可保留。建议仅作局部标注：

- “跨口可见／完成”表示逻辑条件，不预先规定新增 DDR 信号。
- 时序图“排空及失效确认”不等同于 Ara `inval_ready`。
- 图中成功路径隐含整个窗口持续保护，直到最后一次确认。

### 5. 最小验收矩阵与未决输入

| 场景 | 预期结果 | 关键观测点 |
|---|---|---|
| CPU 写后立即同步 | S1 得到交出的输入版本 | WT 有效／在途状态、LLC 脏状态、S0 B、S1 R |
| 普通替换先发生写错误 | 后续同步不得伪报成功 | 错误持久状态、victim 地址、维护完成 |
| flush 返回错误 | 任务不得准入；恢复能力与承诺一致 | BRESP、flush 计数、tag／数据保留 |
| 取消 load、迟到回填 | 最终确认后不恢复旧副本 | 控制器状态、MSHR、回填写使能 |
| 部分行、跨 32／64 B 边界 | 设备未覆盖字节保持正确 | WSTRB、两条 L1 行、完整 LLC 行 |
| 输出期间出现冲突脏行 | 不执行覆盖结果的常规 clean，不报成功 | 目标写事务、dirty、错误状态 |
| 三端口双向交接 | 完成后发起的读取看到新值 | 各端口响应与新请求先后 |
| CPU 栈受隔离、下游无响应 | 正常动作自主完成；故障不提前释放 | 隔离、状态机、独立超时路径 |
| 超时、部分传输、局部复位 | 旧事务不能污染复用后的 DDR／GB | 所有在途队列、迟到 W/B/R、资源状态 |
| 双缓冲及邻接数据 | 不相交维护范围互不破坏 | 范围保留、替换、完成身份 |

尚需补充的输入集中在：**DDR 多端口及复位契约、维护握手规格、错误后恢复目标、运行时 cache/SPM 分配与执行路径、搬运器最终完成和退出语义。**
