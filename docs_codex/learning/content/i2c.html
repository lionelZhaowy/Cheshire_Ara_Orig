学习目标

从 EEPROM 读操作写出总线事务序列，解释 I2C 格式队列，定位 ACK、FIFO 与时序错误。前置：第 10/11 章。场景：驱动函数不返回，SCL 或 SDA 一直为低。

I2C 总线协议与 EEPROM 读事务

I2C（Inter-Integrated Circuit，双线串行总线）使用 SCL 时钟与 SDA 数据，开漏（Open Drain）输出只主动拉低，逻辑高依赖上拉和释放。源码中的 scl_o/scl_en_o、sda_o/sda_en_o 要与 wrapper 的三态/上拉一起看；把输出 1 当作推挽高电平会误解仲裁和时钟拉伸（Clock Stretching）。

当前 HAL 的读序列是：START → 控制字写方向 → 地址高8位 → 地址低8位并 STOP → 新 START → 控制字读方向 → 请求 len 字节 → 接收 FIFO → 软件取数。它在地址设置后用了 STOP，再发 START；不要画成“此实现一定使用 repeated START”。7-bit 设备地址与含 R/W 位的线上控制字不同，HAL 的 0xA0 是后者，再按 block/chip 选择组合。多器件高地址编码需要单独测试。

控制寄存器与 FIFO 结构

i2c_24fc1025_init 先禁用 host、复位四个 FIFO，通过 dif_i2c_compute_timing 把 ns 转周期，配置后启用 host。它使用 Fast mode、SCL 周期2500ns、rise100ns/fall300ns 作为当前 HAL 的假设；实际板上上拉、负载、电压、器件时序必须匹配，不能把仿真参数当测量值。I2C 核心通过 FIFO 与 i2c_fsm 的 ready/valid 解耦软件速度和总线速度。

地址/FIFO命令阶段 HAL 多次允许 NAK（NAKOK），故“函数没有报错”不是器件确实应答的证据。正确检查包括线上 ACK、接收长度、数据内容和控制器错误状态。寄存器/FIFO层超时本身不能区分是缺上拉、器件地址错还是时序不匹配，要向最早未成立的协议事件追。

本地 HAL 静态审读发现，尚未运行复现：

未对齐起始地址时，首块长度直接取 FIFO_DEPTH−addr_offs，没有与请求 len 取 min；短读可能越过调用者缓冲区。写分支注释要求末字节 STOP，实际传入 kDifI2cFmtTx；大于 half_fill 时递归偏移用 buf+len/addr+len，又与分块长度不一致。高地址 chip 选择表达式也应结合多器件模型验证。独立建议：先写边界用例与总线事务期望，再修剪长度、STOP 和偏移。本轮不改生产 HAL，也不提供 EEPROM 写入运行命令。

I2C target 模式与异常恢复

target 模式需第二个 host VIP 或板端主机，先配置 TARGET_ID、复位 ACQ/TX、启用 target，再根据 ACQDATA 中的地址/读写请求提供 TXDATA 或消费写数据，并服务阈值/溢出事件。当前 fixture 主要提供 EEPROM target，不能用它证明 SoC 自己的 target 模式。总线锁死恢复应在独立 TB 中验证：关闭新任务、快照 FIFO/线路、复位控制器、确认 SDA释放；手工 SCL 脉冲/STOP 方案必须遵守器件协议，不作为本轮默认板级动作。

1. 为什么 SCL 为低不一定是控制器坏了？

设备可能拉伸时钟，也可能线路未释放/缺上拉或 reset 配置不正确；观察驱动使能和外部模型，区分谁在拉低。

2. 读16字节通过能覆盖整个 EEPROM HAL 吗？

不能。还缺未对齐短读、跨FIFO/页/块、多器件、NAK、超时、写STOP和写周期等边界。

3. FDATA 的 READ 位为什么不是读一个CPU寄存器？

它是向 I2C 主状态机排入收字节命令；随后线路完成事务，把字节写入 RX FIFO，CPU 再读 RDATA。
