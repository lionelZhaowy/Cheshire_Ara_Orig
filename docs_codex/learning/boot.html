15.1 ROM 先建立可用的片上环境

15.1.1 固化启动代码、外部镜像与执行存储

Boot ROM 保存上电后的第一阶段代码。四种启动模式是这段代码中的分支，选择从哪里取得后续程序；它们没有改变 Boot ROM 的存储位置。以 NOR 启动为例，CPU 先在片上 ROM 中执行 SPI 驱动，将 NOR 里的程序复制到片上 SPM，再跳到 SPM 执行。此时 ROM、NOR、SPM 分别承担“执行加载器”“保存镜像”“承载后续运行”的职责。

ASIC 中固定 ROM 内容需要在实现/制造前确定，具体可以映射为常量逻辑或 ROM 宏；FPGA 可通过重新生成硬件映像更新相应内容。外部 NOR/EEPROM 则可用规定流程更新程序镜像。更新外部镜像之所以有用，正是因为固定加载器能够读取不同的后续程序。

15.1.2 Boot ROM 的早期存储与栈

cheshire_bootrom.S 等待 LLC 内建自测（BIST）完成，设置 CFG_SPM 的 way 位图并提交配置。默认 8 个 way 全部作为 SPM。随后用 LLC_SIZE 把早期栈放到阵列高端，128 KiB 时相应早期 sp 为 0x1001fff8；后续启动汇编还会调整它以建立调用上下文。平台 ROM 若被配置，则按源码约定调用。

Boot ROM 的 C 代码负责启动策略。模式 0 提供被动加载服务，模式 1/2/3 分别访问 SPI SD、SPI NOR 和 I2C EEPROM。JTAG VIP 等待 LLC 的 SPM 配置标志后就请求 halt，因而主线无需假设 ROM 的 C main 已执行完。删除 LLC 或改变其阵列容量会同时改变这里的启动存储和栈条件。

15.2 每条启动路径的入口、搬运者与失败点

15.2.1 Platform ROM 与 Boot ROM 的调用关系

Platform ROM 是集成平台提供的早期代码入口，用于处理通用 Boot ROM 无法预先知道的 PLL、PAD、存储或其他 IP 初始化。Cheshire 不因为配置这个地址就生成这份 ROM；wrapper 还需提供内容、可取指的地址映射，以及所需控制寄存器。两段代码由同一个 CVA6 执行，Platform ROM 不是独立运行的管理核。

15.2.2 装载路径比较

复位 PC 进入 ROM 后有两种推进方式：ROM 继续建立栈、进入 C main 并读取模式/测频，服务 UART/Link 或自主介质；JTAG 则由外部 VIP 在自身条件满足后暂停并接管。当前 VIP 只在 LlcNotBypass 时轮询 CFG_SPM_LOW.bit0，没有等待 ROM C 或测频完成，也不能由这个配置位推出后续栈初始化已经结束。不同介质最终都要让程序字节落到可执行存储、确定入口并转交控制。文件格式、介质读取和入口选择分别完成，不能把主机读 ELF 的逻辑想成 CPU 自动解析 ELF。

15.3 被动加载服务

BOOT_MODE=0 使 ROM C 进入 boot_passive。ROM 完成测频并初始化 UART 后，轮询 scratch2 的掩码 2 和 UART 握手字节。PRELMODE 是 testbench 选择外部装载方式的参数；它与硬件 BOOT_MODE 是不同输入。JTAG 接管前提见调试章。

15.3.1 Serial Link：远端写入与 scratch 交接

选择与搬运：仿真 PRELMODE=1 由 VIP 通过 Link 对端发送 AXI 写；ROM 处于被动模式。主机侧解析 ELF，按目标段地址写入可用存储；ROM 本身不解析 ELF。地址译码、目标可写性及完成应答须由装载者核对。

入口交接：写数据完成并满足可见性约定后，装载者把入口低/高 32 位放入 scratch0/1，再向 scratch2 写掩码 2。ROM 测试的是 bit1，清 scratch2 后把 scratch1:0 拼为 64 位地址，调用 boot_next_stage。代码某些注释写 bit2，本书按表达式解释。入口必须指向已装载的可执行代码。

验证条件：当前 VIP 有 Link 对端；VCU118 的 Link 没有可用板端闭环。仿真需要同时看写响应、scratch 发布顺序、CPU 入口及数值结果；[SLINK] 结束不是当前仅识别 JTAG 的日志检查器可直接替代的判据。链路机制见Serial Link 设备章。

15.3.2 UART：二进制读写与调用协议

选择与格式：ROM 被动服务收到 0x06 后回 ACK=0x06；PRELMODE=2 的 VIP 使用该服务。READ=0x11 带 addr64/len64，WRITE=0x12 带 addr64/len64 和数据，EXEC=0x13 带 addr64。本地服务直接收进 uint64_t，主机应按该目标的小端字节顺序发送字段；终端发送 ELF 文件的原始字节不能构成这些命令。

装载与交接：WRITE 解析地址和长度后先 ACK，再把指定字节接收到该地址，结束回 EOT=0x04。装载者负责合法目标范围与各段/BSS 策略；服务没有 ELF 格式验证或完整地址白名单。EXEC 经 ACK、fence 后 invoke 指定地址；被调用代码返回时发送 EOC=0x14 和 32 位返回值。它与 scratch2 退出协议应分别观察。

验证条件：115200 波特率依赖 ROM 测频及 UART 初始化；先核对 ACK、长度、逐字节读回和入口，再检查运行结果。服务含轮询等待，需要主机超时；主线实验没有新验收 UART 装载。协议依据为uart_debug_serve，控制器配置见UART 初始化。

15.4 自主介质启动

15.4.1 共同镜像格式与 SPM 装载

ROM 用 HAL 回调读取介质字节。gpt_boot_part_else_raw 先查 LBA1 的 GPT 签名（每 LBA 512 字节）；有签名时找符合类型/分区 GUID 和大小条件的分区，未找到符合条件的项时沿本地实现回退首分区截取范围；无签名则从介质偏移 0 读 raw 区。该简化实现不应当作完整 GPT 完整性或镜像认证机制。

默认 max_lbas=96，原始路径读取 48 KiB；分区路径按含末尾 LBA 的区间读取，载荷上限同样受此值约束。目的地址为 &__base_spm，随后 boot_next_stage(code_buf) 从缓冲起点执行，不从 ELF header 取 entry。连续镜像须把入口放在所约定起点并满足运行布局；rom.ld 用于 SPM 运行、外部镜像装载。教材 spm.ld 的 64 KiB 链接区是另一层约束。

跳转前函数把读取回调、设备私有指针和 gp 约定写进 scratch0/1/3，供后续阶段使用；这些槽在不同启动阶段的含义不同。根软件通用 GPT 打包规则当前已注释，ROM 解析代码仍保留。以下三路只更换设备初始化与 read 回调，镜像解释和入口规则共用本节。

等待的计时基准：clint_spin_until(tgt_mtime) 只在 mtime < tgt_mtime 时轮询；阈值已过去就立即返回，尚未到达则只等待剩余差值。clint_spin_ticks(ticks) 才将当前 mtime 加到相对等待量上。ROM 注释表达设备初始化等待意图，实际调用采用绝对阈值；器件从上电、复位或命令完成等事件起要求的等待时间，还需按器件规范和计时基准验证。本轮仅修正文档，不修改驱动，也未据此判断板上启动成败。

15.4.2 SPI SD：块读取与 CRC

选择：BOOT_MODE=1 调用 boot_spi_sdcard；CS0，目标 SPI 24 MHz，另有 dummy CS。ROM 先用 HAL 完成卡初始化，再调用 clint_spin_until((1000 * rtc_freq) / 1000000 + 1)，等待 mtime 达到该绝对阈值，并非从初始化结束起再等 1 ms；输入和装载：spi_sdcard_read_checkcrc 提供按字节范围读取的回调，底层以卡块传输并检查 CRC，共同加载器把 GPT/raw 载荷放到 SPM 起点；入口：成功读取后进入 boot_next_stage。

验证条件：当前 TB 拒绝 BOOTMODE=1，尚无 SD 模型闭环。卡初始化、容量/寻址、块响应与 CRC、载荷布局需逐层验证。具体卡命令见SPI SD 协议；本节不授权写卡或修改生产启动脚本。

15.4.3 SPI NOR：地址读取与器件配置

选择：BOOT_MODE=2 调用 boot_spi_s25fs512s；CS1，SPI 频率 min(40 MHz, core_freq/4)，初始化后调用 clint_spin_until((350 * rtc_freq) / 1000000 + 1)，等待 mtime 达到该绝对阈值，并非从初始化结束起再等 350 μs；输入和装载：spi_s25fs512s_single_read 读取镜像，按共同 GPT/raw 规则写 SPM；入口：返回成功后调用 SPM 起点。

验证条件：先确认器件模式、地址长度和只读数据，再验证完整镜像启动。现有 HAL 的 CR3V 写配置方向仍有静态疑点；VIP 有 NOR 模型不表示已通过自主启动。只读步骤及缺口见NOR 驱动，不以介质写入替代诊断。

15.4.4 I2C EEPROM：器件地址与内部地址

选择：BOOT_MODE=3 初始化 I2C/24fc1025；输入和装载：i2c_24fc1025_read 把介质偏移转换为器件选择及内部地址，读到的 GPT/raw 字节按共同规则写入 SPM；入口：加载成功后调用 SPM 起点，不由 EEPROM 提供独立 ELF 入口。

验证条件：ACK、STOP、器件容量与跨界拆分决定读回是否正确；HAL 边界和递归缺口仍待处理。VIP 的预填模式适合验证少量读取，启动需要合法连续镜像和完整结果判据。见EEPROM 事务与读取边界。OpenOCD/GDB 的板级接管另取决于探针和连接配置。

15.5 应用入口与运行交接

15.5.1 ZSL、OpenSBI 与操作系统启动的分层

当后续软件超出 ROM 的小型装载空间时，可以先把一个较小的加载器放入 SPM，由它继续读取大映像。本地 sw/boot/zsl.c 的 ZSL 使用前一阶段保留的读取回调访问启动介质；scratch0/1/3 在该阶段分别携带函数指针及标志、设备私有参数和原 gp 上下文。grread 负责按约定切换 gp 后调用读取函数。

ZSL 将 DTB 放到 0x80800000、固件载荷放到 0x80000000，再按入口约定交接。DTB 是设备树二进制，用数据结构描述硬件地址、设备和中断；OpenSBI 提供监管态软件所需的固件服务，U-Boot 再负责后续启动组织。fw_payload 可把 OpenSBI 与后续载荷组合起来。这条链与直接运行裸机 ELF 是不同用途。

这些 DRAM 写入要求外存已可用；当前 ZSL 不能代替尚未提供的 ASIC DDR 初始化驱动。把初始化职责放在 Platform ROM 或明确的早期平台阶段时，应按实际依赖安排，再进入 ZSL 的加载动作。本地通用 GPT 打包规则已注释，Linux 专用规则仍存在，操作前按当前 SDK/镜像规则逐项核对。

15.5.2 应用启动代码建立 C 环境

应用 crt0 首先关闭 M/S 全局中断并停住非零 hart。机器态（M）、监管态（S）和用户态（U）是 RISC-V 的权限层级，本书沿机器态裸机路径。crt0 根据非零栈符号决定是否换栈，建立 gp（访问全局数据的辅助指针），保存进入时上下文，再把 mtvec 设为异常入口。

接着清除 __bss_start 到 __bss_end，把 result 等零初始化对象置零；设置 FS 并初始化浮点寄存器，然后 fence 并 call main。即使 C 只做整数运算，当前原始 crt0 仍执行双精度浮点指令，所以本例要求 F/D 硬件。VS 未在原 crt0 统一设置，向量变体由标量 main 在调用向量函数前开启。

异常是当前指令引起的事件，如非法指令或访存失败；中断是计时或设备等异步事件。两者统称 trap。CPU 把原因和位置记入 mcause、mepc、mtval 等 CSR，并跳到 mtvec。当前弱 trap_vector 是自循环，故“无输出”也可能是 main 之前已陷入异常。中断章会加入保存现场和返回流程。

15.5.3 系统寄存器参与初始化与结束

SoC 寄存器位于 0x03000000。它们向软件提供硬件信息，避免把某个平台频率硬编码进每个应用。RTC_FREQ（+0x44）供 CLINT 测频使用；NUM_INT_HARTS（+0x4c）报告核数；HW_FEATURES（+0x50）报告配置能力；LLC_SIZE（+0x54）报告阵列容量。容量和当前 way 用途需分别查询，硬件能力位还需结合引脚、时钟和设备模型理解。

scratch0..15 每项 4 字节，低几个槽承担启动交接。主线程序读取 RTC_FREQ，用 RTC 与 mcycle 测系统频率，再配置 UART。printf 把结果变成字符，经 _putchar、uart_write、MMIO 写到 UART，VIP 采样串行数据并在换行后输出日志。返回前调用 uart_write_flush，确保末尾字符发完。

main 返回值在 a0，crt0 的 _exit 把 (返回值 << 1) | 1 写到 scratch2（+0x08）。VIP 观察 bit0，右移得到返回码；0 输出 [JTAG] SUCCESS，非零输出 FAILED。源码注释写 wait forever，而实际末尾是 ret；验收应以完成寄存器和日志为准。这个协议相当于测试环境的程序结束通知，不是操作系统的 exit 服务。

UART 的 EXEC 地址和 NOR 自主启动入口为何可能不同？

UART 调用装载者显式发送的 addr64；NOR 共同加载器从 SPM code_buf 起点调用，要求镜像在该处布置入口。两者都要满足地址、代码和栈条件。

NOR 镜像更新后，片上 Boot ROM 的程序是否也随之改变？

不会。固定 ROM 仍执行原有读取流程，新镜像被搬到 SPM 后由 CPU 执行。变化的是载荷字节，而不是第一阶段加载器。

Platform ROM 初始化 PLL 后，应用怎样改变频率？

通过真实 PLL IP 的运行时控制接口，遵守停止任务、排空、安全时钟切换、锁定和恢复契约。ROM 固定初始代码不等于 PLL 状态锁死；还要先解决本地平台钩子的正常返回缺口。
