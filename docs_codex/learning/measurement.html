本章任务

为同一个数组计算设计可重复的正确性与性能实验，解释内核时间为什么不同于应用等待时间。前置：向量数组、数据交接、OS设备使用。本章是实验设计，未新增目标运行或性能数字。

42.1 计算任务定义与结果正确性

假设要比较标量与 Ara 对137项整数的计算。现有 journey.c 的普通分支逐项产生 3*i+1，向量分支准备 a[i]=i、b[i]=2*i+1 后相加，二者都逐项检查结果及总和28085。这是相同输出规格，却还不是公平的内核基准：输入准备、函数调用、临时存储和检查工作并不相同。先决定比较的是“从原始输入到已校验结果”的应用，还是“已准备好两个数组后的加法”，再统一两种实现的工作边界。

正确性先于计时。长度0、1、63、64、65、137覆盖空任务、整块和尾部；现有深度例还检查输入不被破坏、结果逐项匹配和边界守卫。独立参考不应重用被测向量算法，否则同一个错误可能同时出现在实现与参考中。输出被消费和校验，才能避免只测到编译器删除后的空计算。现有程序的历史编译与当前目标执行证据仍按验证缺口区分。

42.2 算法内核、设备服务与端到端计时边界

一次应用操作先获得缓冲、准备输入，再发布数据，提交计算；计算结果可见后，消费者读取和检查，最后归还资源。不要在提交刚被接受时就结束计时，之后的排队、Ara执行、存储响应和缓存交接仍可能占据主要时间。

  1. 算法内核：输入和所需运行状态已经准备好，从进入计算到约定的结果完成点。向量版本必须核对本地协作、访存排序和结果读取的实际边界；单独读一次CSR不是通用的“Ara已经空闲”证明。
  2. 设备服务：从驱动提交到结果已可由调用者使用，包含排队、数据移动、完成通知及必要同步。阻塞API、异步提交API和任务完成事件分别标时。
  3. 端到端：从应用取得一份输入到产生可消费输出，包含分配、格式转换、驱动、OS调度及多设备交接。是否包含校验/输出日志应明确，并另存正确性证据。

以下为计时位置示意，名称不是本地新增API，也不是可直接执行程序：

t0 = elapsed_clock();          // 输入已到达应用
prepare_and_publish_input();
t1 = elapsed_clock();          // 数据已满足计算入口契约
submit_compute();
wait_for_result_and_visibility();
t2 = elapsed_clock();          // 调用者此时才能读取结果
consume_output();
t3 = elapsed_clock();          // 应用可交付结果
verify_against_independent_reference();  // 保留独立正确性记录

t2-t1与t3-t0回答不同问题。比如教学假设方案A计算10个时间单位、准备与交接90，方案B计算5、准备与交接120，则内核快2倍，端到端却从100变成125。这里的数字仅说明边界，不能作为本工程测量结果。

42.3 本地计数器、日志与事务观测接口

入口与本地依据可以观察什么使用时必须明确的条件
get_mcycle()；cycle_q / CSR_MCYCLECPU周期计数差权限、计数禁止位、时钟及Debug状态；不是Ara周期或设备独占时间。需检查读计数指令与被测工作的编译和硬件顺序
clint_get_mtime / clint_get_core_freq；接口单位参考时钟tick与CPU计数的比值；原例据此初始化UART测频假定时钟稳定，RTC参数有效且计数推进。当前分高低读取限制见事件/定时器诊断，不能据函数存在宣布连续时间读可靠
目标仿真观测点请求、应答、CPU提交、内部在途、AXI握手与响应需真实层次、时钟尺度、数据库和输入版本；教材WaveDrom是示意
UART、scratch结束协议、数组比对进度、正常退出、数值正确串口发送会增加时间，放在窗口外；退出码不自动证明所有数值正确

计数器规范区分周期、时间和退休指令；执行环境可以限制访问，计数速率也与实现和运行条件有关。这里参考RISC-V Zicntr/Zihpm 2.0（20260120汇编版），不把新版扩展自动视为本地已启用。本地CSR消费者显示 cycle/instret 在Debug模式下暂停更新，cycle可受计数禁止控制；因此带断点的计数不能直接用于连续运行比较。

没有核实的PMU事件、AXI字节计数器、能耗采样和片上trace不填成现成功能。需要新增观测时先提出信号、采样边界和开销，由后续工程任务实现。CPU被调试暂停时，其他模块是否停止需分别核对；主机仿真耗时也不是目标执行时间。

42.4 周期数、执行时间、吞吐率与延迟的换算

固定且已知频率时，时间约为周期差除以频率；运行中调频则不能用一个频率乘整个区间。参考tick差乘tick周期得到经过时间，分辨率应足以覆盖所测任务。137项小数组若远短于一次tick，就需要更细计数或在明确缓存与批处理条件下重复工作；不能把零tick解释成零耗时。

延迟是一个任务从指定开始到指定完成的时间。吞吐是稳定区间内已正确完成任务数除以区间时间。双缓冲可以让采集和计算重叠，提高吞吐，却不保证某一帧延迟减半。AXI写有效字节按已握手W拍的WSTRB有效位累加；读有效载荷结合ARSIZE、长度和有效地址范围判断，不能把总线位宽乘每个空闲周期当有效带宽。DDR理论峰值、端口传输率和应用有用字节分别报告。

42.5 性能实验的可重复性条件

先保存当前HEAD及未提交差异、硬件profile/Cfg、ELF哈希、工具链与选项、输入数据和结果参考，再决定数据在SPM还是DDR、缓存冷暖、是否允许中断和后台任务。不要为得到小数字偷偷换输入规模或省掉必要的同步。OS实验还记录内核/固件/根文件系统版本、任务优先级、调度策略和实际CPU亲和条件；未实现的配置明确留空。

每次先按相同规则准备状态，完成完整工作并校验，再保存原始时间样本。预热次数、测量次数和剔除规则先规定；同时报告中位数、分位数或范围，以及样本数。慢样本若来自真实调度或刷新，应保留为系统行为，不因它“不好看”删掉。空窗口测量可以帮助估计计时开销，但扣除方法、可重复性和最终是否出现负值都需检查。

要比较裸机、RTOS、Linux，至少分成“相同工作/数据位置/正确性要求”的控制组与“各自正常部署”的系统组，说明驱动和缓冲策略是否不同。只禁中断测到的是受控内核条件，不能据此宣称满足实时应用。性能不达预期时进入独立测量诊断。

42.6 实验输入、结果与测量记录

input: HEAD + dirty diff; hardware configuration; ELF/firmware/OS hashes
work: algorithm, length/shape, types, input hash, independent reference
memory: physical placement, cache state, ownership/completion contract
clock: counter source, unit, frequency/scale, permission, interrupt policy
window: exact start/end events; included preparation/sync/verification
samples: raw values, repetition/warm-up rule, correctness for each run
result: median/range/percentiles, useful bytes/tasks, limitations

本章交付的是可填写实验设计。纸面推演可以立即完成；实际计时依赖已通过正确性验收的目标环境，功耗还需已定义电源轨、板级测量与仪器。不能用网页通过、ELF存在或指令出现替代这些条件。

向量指令少了、mcycle差也变小，是否足以说明论文应用加速？

还需证明相同输入和数值标准、结果完成与可见性、相同计时条件，并比较端到端窗口中的准备、数据移动、调度和同步。两项计数只能支撑其实际测量边界内的结论。
