Linux 启动与用户程序运行

前置：裸机启动与 ZSL、任务和上下文、地址空间与保护。本章选本地 Ara SDK 展开的 Linux v6.5 作为源码教学落点，解释一个用户程序如何获得 CPU、内存与设备服务；不把它选定为产品内核。

裸机与 Linux 用户程序的运行环境

裸机程序通过 crt0 建立自己的一套执行环境，通常直接使用平台库和 MMIO。Linux 中，同样的数组计算在一个用户进程里运行：内核为它建立地址空间和调度上下文，库通过系统调用请求文件和设备服务，程序返回时结束自己的进程，而不是把整个 SoC 的控制权返回 Boot ROM。

引入 Linux 的理由可以是论文实验需要进程管理、文件输入输出、成熟工具或驱动框架；代价是启动、内存、权限和调度条件变多。把裸机 ELF 换一个文件名，并不能使它成为 Linux 应用。普通 Linux 调度也不自动保证硬实时期限，应该先定义实验负载与计时边界，再决定需要什么系统配置。

Linux 软件组成与构建产物

交叉编译器在开发主机上工作；产出的平台固件、内核和用户程序在目标上运行。Linux 内核负责调度、地址空间、系统调用和驱动；根文件系统提供目录、程序、库与配置。设备树提供硬件描述，不能代替驱动代码。Buildroot 这类构建系统组织工具链、内核和用户空间的生成，不是在目标运行时“位于应用下面”的一层。

一个 fw_payload.bin 可以包含两个逻辑阶段；相反，同一阶段可能读取多个文件。因此文件数量不等于启动阶段数量。解释一个镜像时，先问“谁生成、谁加载、谁执行、依赖什么”，再看其扩展名。内核启动后仍可能通过 SBI 调用常驻机器级固件，启动阶段先后也不意味着先前的软件全部消失。

本地固件与内核的候选启动链

本地资料支持讲解的候选链是：Boot ROM 准备早期条件并装入 ZSL；ZSL 将设备树与 firmware payload 放到约定内存；payload 中的 OpenSBI 完成机器级服务及向下一阶段交接；U-Boot 装载/选择内核；内核进入自己的初始化。这里每个箭头都有条件，以下走读是源码关联，不是该链已在当前 VCU118/Ara 配置跑通的报告。

  1. ROM → ZSL：代码从早期可访问区域运行，栈与装载区需先成立。ROM 的具体介质路径见启动章；DDR 尚未准备好时，不能先把后续大镜像放进去再初始化 DDR。
  2. ZSL → payload：本地 zsl.c 读取启动参数，GPT 路径按类型 GUID 找设备树与固件分区，读入 __BOOT_ZSL_DTB 与 __BOOT_ZSL_FW 对应地址，最后调用 fw(0, dtb_address, 0)。这些地址来自链接/平台约定，不是任意找一块空闲 RAM。
  3. OpenSBI → 下一阶段：OpenSBI 提供 Supervisor Binary Interface（SBI）的机器级服务，典型 S 模式内核用它请求某些特权操作。SDK 的 fw_payload 规则把 U-Boot 二进制作为 payload；OpenSBI 与 U-Boot 的职责因此不能都叫“Boot ROM”。
  4. 加载器 → Linux：加载器把内核、DTB 和必要的用户空间启动内容放到彼此不覆盖的可用 RAM，传递启动 hart 和硬件描述，并满足内核入口条件。RV64 常规入口要求核镜像按 2 MiB 边界安排，a0 为 hart ID、a1 为 DTB 地址、satp 为零；常驻固件占用的内存必须保留。
  5. Linux 接管：内核建立自己的栈、页表、异常入口、内存管理与设备服务，然后才有普通用户进程。裸机应用 crt0 不参与每个 Linux 系统调用，也不负责建立整个 Linux 内核环境。

本地 sw.mk 的 Linux GPT 规则消费 ZSL、DTB、fw_payload.bin 与 uImage；SDK 规则说明 fw_payload 中嵌入 U-Boot。根 sw/deps/cva6-sdk/install64 的已有镜像只是产物，不能根据文件名逆推出它们与本次 profile、DTS 和源码一一匹配。本地已有的启动/驱动门槛集中在OS 诊断与证据；本轮不执行镜像生成或介质写入。

本地：ZSL、GPT 规则、SDK 镜像规则。入口条件另参照Linux 6.12 官方启动契约，该文档是补充参考；本地 v6.5 的真实入口仍需核对下文所列 head.S，不能由此声称内核已升级。

Linux 内核初始化与首个用户进程启动

进入内核时，还没有一个可以执行 shell 命令的“Linux 世界”。RISC-V 的 arch/riscv/kernel/head.S 保存启动输入，准备早期执行与页表切换，随后进入 C 初始化。start_kernel 组织体系结构、内存、调度、时间和中断等初始化；这些工作有依赖关系，不能在缺少可用栈或页表时调用普通设备驱动。内核控制台形成后输出的日志，才能帮助观察后续阶段。

内核为 PID 1 准备执行上下文，完成初始化调用和根目录环境后，尝试运行用户态 init。在本地 v6.5 的 init/main.c 中，可以沿 kernel_init、run_init_process 追踪这个边界。使用 initramfs 时，cpio 中的文件先展开到初始根文件系统，若提供可执行的 /init，它可以成为首个用户程序；没有这条适用路径时，内核按配置/参数寻找根文件系统和 init。只有内核镜像，却没有适用的用户程序及其依赖，并不能得到可用 shell。

init 再启动服务或 shell，shell 创建子进程并请求执行数组程序。内核读 ELF，建立代码、数据和栈的映射，按用户 ABI 安排入口环境；动态链接程序还由用户态动态加载器处理共享库。用户 C 运行库的入口最终调用 main。这里再次出现“启动代码”，但它属于单个用户进程，与上电 ROM、内核 head.S、裸机 crt0 是四个不同的生命周期。

在 U 模式里，普通加法和数组访问直接执行；需要写控制台时，库通过系统调用进入内核，内核把请求交给终端/串口驱动，然后返回该进程。进程在等待期间可被阻塞，别的进程获得 CPU；中断仍由内核处理。用户 main 返回通常经库调用退出服务，内核回收该进程资源。PID 1 则承担系统初始化与管理职责，不能把“普通应用退出成功”套用成让 PID 1 正常返回。

设备树的硬件描述与适用条件

内核不能从一段任意 AXI 地址自动猜出这里有 UART、它用哪个时钟、哪根中断线。DTS 以节点和属性描述这些资源，DTB 是其二进制形式。compatible 帮助驱动匹配设备，reg 描述地址范围，interrupts 与中断父节点一起解释事件来源；描述成立后，匹配且启用的驱动才有机会初始化设备。

当前 cheshire.dtsi 声明一段从 0x80000000 开始、大小 0x40000000 的 RAM，CPU ISA 字符串为 rv64imafdc，MMU 类型为 Sv39，CPU/UART 时钟常量为 50 MHz，时间基准为 1 MHz。这些是文件中的描述值，不能反过来证明板上有 1 GiB 已初始化 RAM、当前实际时钟就是 50 MHz，或者 V 扩展已对内核宣布。它们必须与最终平台、CPU profile、复位后频率和保留区核对。

改变 DTS 不会增大 RAM、不建立中断连线，也不会让不存在的驱动出现。对新 IP，硬件资源和驱动绑定应先形成可核对的接口；对已有 UART，先利用现有 binding 和驱动路径。具体调用链在同一设备的 Linux 使用过程继续。文件与源码差异的定位集中在描述与实际硬件。

Linux 用户态数组计算示例

Linux 版本保留 x[i]=3*i+1 与 137 元素，但不直接使用裸机固定 SPM 指针、__base_uart 或 SCRATCH2 退出约定。数组由用户空间的静态对象、栈或分配器提供，串口输出先用已配置的标准输出。下面是完整的标量用户程序教学例，未在本轮构建或运行。

#include <stdint.h>
#include <stdio.h>
int main(void) {
    uint32_t x[137], sum = 0;
    unsigned errors = 0;
    for (unsigned i = 0; i < 137; ++i) x[i] = 3u * i + 1u;
    for (unsigned i = 0; i < 137; ++i) {
        errors += (x[i] != 3u * i + 1u);
        sum += x[i];
    }
    int ok = errors == 0 && sum == 28085;
    if (printf("N=137 errors=%u sum=%u\n", errors, (unsigned)sum) < 0)
        return 2;
    if (fflush(stdout) != 0) return 2;
    return ok ? 0 : 1;
}

完整实验的前提是：已经验证的内核/用户空间启动，匹配的 Linux 交叉工具链与 ABI，可加载的 ELF 和相应库，实际控制台可用。主机编译时核对 ELF 的机器类型和解释器要求；部署到已授权的文件系统后，由普通 shell 启动。观察输出应为 N=137 errors=0 sum=28085，随后检查进程退出状态。printf/fflush 成功表示库和内核接受了相应输出过程，不证明物理串口接收端无误；外部接收另按设备章验收。

本例故意不提供一个假定工具链前缀、设备名和挂载路径都正确的“一键命令”。当前实际产品环境尚未确定，S01 应交付工具链/根文件系统/部署位置与运行清单后，V01 才执行。数学结果是推导值，现有 ELF 是历史产物，本轮只交付文档例子。增加 RVV 时须再核硬件声明、用户能力、上下文支持及向量结果；加速结论还需测量，不能由内核启动或指令出现推出。

本地软件版本与验证边界

本轮定向阅读发现：SDK 的普通 RV64 Buildroot 配置请求 Linux v5.10.7，V 配置请求 v6.5；展开的 buildroot/output/build/linux-v6.5/Makefile 声明 6.5.0；随附 OpenSBI 的版本头声明 0.9。V 配置和展开源码有 FP/RVV 上下文实现。这说明有可阅读的来源及历史软件材料，不说明 install64 中某个镜像必由当前这些文件构建，也不等于已通过本地 Ara 的抢占、缺页和数据一致性测试。

因此本章用 v6.5 解释实际源码结构，用官方发布版本链接便于复查，保留本地副本哈希作为输入快照。未来选用别的内核时，重核 boot ABI、设备绑定、向量上下文和工具链，不能只改页面里的版本号。OS 不是 ASIC 源码提取的强制前置：教学可先学完，具体移植与硬件提取按各自依赖推进。
