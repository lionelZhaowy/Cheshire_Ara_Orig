让两个任务各自继续执行

前置：函数调用与 ABI、异常现场、定时器与设备事件。本章用采样任务 A 和计算任务 B 走完 A→B→A，再解释它们怎样安全共享结果。FreeRTOS Kernel V11.1.0 的 RISC-V port 只作官方教学参考，尚未选作本工程 RTOS。

为什么不把所有工作写进一个循环

设系统每隔一段时间产生一组 137 个整数，计算其总和，然后输出结果。裸机循环可以依次采样、计算、打印；但串口正在等待发送时，下一组数据也可能到达。把所有等待都放在一个循环，需要应用自己安排每一步何时推进。实时操作系统（RTOS）提供另一种组织：任务 A 等待采样时刻，任务 B 等待数据，日志任务等待结果。等待的一方让出 CPU，已经具备工作条件的一方继续运行。

这里的“任务”是可以独立暂停和恢复的软件执行流。它拥有入口函数、栈、保存状态和调度属性；三个任务不代表三个 CVA6，也不代表 Ara 会独立取指。本章先假定单 hart、共享物理地址空间、固定优先级、可抢占调度、整数运算。RTOS 可在没有虚拟内存时工作，任务之间是否有硬件隔离则取决于具体 port 和保护配置，不能从“有 RTOS”推导出来。

实时性要求在规定期限内完成；它不等于平均运行很快。137 次加法即使耗时很短，也可能被长时间关闭中断、较高优先级工作或阻塞式打印延迟。先把执行与等待的关系解释清楚，才有资格给出截止期或吞吐指标。

暂停一个任务，要把什么留在原处

A 正在计算 sum += a[i] 时，程序计数器给出下一条指令，整数寄存器可能保存 i、sum、数组地址；A 的栈中还保存嵌套函数的返回位置和局部对象。任务控制块（TCB）保存调度器需要的元数据，例如状态、优先级以及保存现场后的栈指针。TCB 与栈不是同一个对象，恢复时从 TCB 找到该任务的栈与现场。

普通函数调用的 ABI 只规定调用边界上谁保存哪些寄存器；异步中断可能出现在任意允许的指令边界，任务没有机会先按一次普通调用保存临时值。trap 硬件记录返回位置和原因，但不会自动把全部通用寄存器压入 RAM。port 入口软件必须保存未来恢复所需的状态，再允许调度器改选任务。一个只为“调用 C handler 后返回原程序”设计的裸机 wrapper，不等于任务切换 port。

教学状态图（内存对象，不表示固定地址或固定拍数）
TCB_A.saved_sp ──→ A 栈：[A 的函数帧][A 的保存现场]
TCB_B.saved_sp ──→ B 栈：[B 的函数帧][B 的保存现场]
当前 CPU 寄存器：只装着此刻运行任务的一份状态
就绪队列：可执行、暂未获得 CPU 的任务
事件等待队列：尚未具备继续条件的任务

运行态表示当前占有 CPU；就绪态表示条件满足但尚未被选中；阻塞态表示正在等待队列数据、设备事件或时间。B 等待空队列时应阻塞，而不是反复读取“队列空”占满 CPU。被高优先级任务抢占的 A 若没有等待条件，则仍就绪。图中 A/B 栈同时存在，切换只是改变当前使用哪一份现场，不是把 A 的调用栈改写成 B 的调用栈。

沿 A→B→A 走一遍

为了把调度与算法分开，先让 A、B 具有相同优先级，B 已就绪，A 主动 yield。这个条件很重要：固定优先级系统中的 yield 不保证低优先级 B 获得 CPU。下面六步是机制推演，具体入口、寄存器布局和 ISR 栈由选用 port 决定。

  1. A 运行到 yield。RISC-V port 可以用 ecall 请求内核；这是同步异常，返回点应越过这一条调用指令，和定时器中断保存原恢复点的责任不同。
  2. 入口先保存 A 的整数现场、返回位置及所需状态，把保存区位置记入 TCB_A。此时 A 的 i、sum 仍可以在保存区找回。
  3. 调度器将仍可运行的 A 放回就绪集合，选中 B，更新“当前 TCB”。选择过程处理软件状态，不会自己完成寄存器恢复。
  4. port 取 TCB_B 的保存指针，恢复 B 的寄存器、返回位置和状态，经相应返回路径继续 B。B 如果是第一次运行，其初始现场由创建任务时构造，入口参数和对齐栈也需先成立。
  5. B 完成当前工作后等待队列。若队列为空，B 进入阻塞集合；调度器此时重新选中就绪的 A。
  6. 恢复 TCB_A 指向的现场，A 从 yield 后继续，i 和 sum 保持暂停前的值。这个结果才说明 A→B→A 的状态交接正确。

在官方 V11.1.0 通用 RISC-V port 中，portContext.h 将整数现场存到任务栈，保存指针写入 pxCurrentTCB，处理程序使用独立 ISR 栈，恢复时再取新 TCB 的指针并 mret。该实现假定 gp/tp 在其使用模型中保持不变；这不是所有 RTOS、TLS 模型都可沿用的结论。首次任务启动还有专门路径，不能用“每次都是一次 mret”概括所有入口。

版本依据：官方 V11.1.0 portASM.S、portContext.h。本地 crt0.S 是裸机入口，没有实现这套 TCB/任务调度。

时间到、主动让出与设备到达是三种触发

tick 是内核计时单位，常由周期定时器中断推进。处理定时器中断时，port 安排下一次到期，内核推进时间并检查哪些延时任务可以就绪；随后是否切换，要看优先级和时间片策略。因此“发生一次 tick”不等于“必定切换一次任务”，更不等于每个 tick 执行一次 main。

延时 10 个 tick 是等待至少相应调度时刻的表达，不是“CPU 必须精确在第 10 毫秒开始执行”。tick 周期由 RTOS 配置和平台时间源共同决定，毫秒需按该配置转换。定时器采用哪个时钟、比较寄存器如何更新，仍回到CLINT 的正常过程核对；当前 RTC 参数不能直接当成未来 RTOS tick 频率。

设备事件则可以早于下一次 tick 唤醒任务。ISR 读取/清理必要的硬件状态，将收到的数据或完成事件交给内核，再按 port 规则请求调度；耗时计算和格式化输出留给任务。ISR 不应调用会阻塞等待另一个任务的普通队列接口，因为它不是一个拥有普通任务等待路径的调用环境。FreeRTOS 为此提供 ...FromISR 接口，并通过“是否唤醒更高优先级任务”的结果告知返回前是否请求切换。

把 137 个元素交给计算任务

先做一个不依赖新外设的完整机制例。A 生成 x[i]=3*i+1，B 检查每个元素并求和，日志任务只接收一个小结果结构。为使生命周期容易推演，输入队列按值复制整个 137 元素消息，队列长度为 1；它确实会产生复制成本，但避免让读者一开始就处理共享 buffer 的归还协议。这个选择是教学方案，未来大帧应使用专门的缓冲所有权机制。

机制伪代码；queue_send/receive 等是动作名称，不是本地函数。
初始化：创建长度 1、元素为 {seq, x[137]} 的输入队列；
        创建结果队列；创建 A/B/日志任务及互不重叠的对齐栈；
        安装 RTOS port 的 trap/timer，最后启动调度器。
A：等待采样时刻 → 填 seq 与 x[i]=3*i+1
   → 按值发送消息（队列满时阻塞等待有界时间）
   → 发送成功后才复用本地消息 → 等待下一时刻。
B：阻塞接收消息 → 检查每个 x[i] → 求 sum
   → 发送 {seq, errors, sum} → 再次阻塞接收。
日志任务：接收结果 → 串行输出完整一条记录 → 等待下一结果。
结束：停止生成新消息 → B 消费完已接收消息
     → 日志发送完成 → 在约定停止点报告累计结果。

沿第一次消息跟读：初始时 B 等待队列，A 填好消息后入队；入队解除 B 的等待，调度器在允许的点让 B 执行。B 收到自己的消息副本，因此 A 之后重用局部变量不会改变 B 的数组。B 再把结果交给日志任务，不必在计算路径上逐元素打印。所有接收方等待时，CPU 可运行其他就绪任务或 idle；不需要每个任务都写一个轮询硬件的忙等循环。

官方参考中可把以上队列操作对应到 xQueueCreate(1, sizeof(message))、xQueueSend 和 xQueueReceive。创建返回句柄须非空，发送/接收返回 pdPASS 才表示本次队列交接成功；等待参数用 tick，零表示不等待。xTaskCreate 的栈深度按 StackType_t 个数计，不是字节；具体栈预算要覆盖函数帧、上下文和中断策略，不能照抄任意“256”。

预期数学结果为 sum = 137 + 3×136×137/2 = 28085，errors=0。多轮结果还应有连续 seq，无重复、丢失或互相串用。纸面推演可检查这条数据链；本平台执行则还缺 RTOS port/BSP、配置和目标验证。队列提交成功证明消息进入队列，不证明 B 已计算，更不证明串口接收端已收完；每个完成点都在对应层检查。

真实 API 与单位：task.h、queue.h。此例未编译或运行，不作为本地 FreeRTOS 应用交付。

从一份共享计数理解同步

若 A 与 B 都做 count++，一次自增通常包含读、加、写。A 读到 5 后被切走，B 写回 6，A 恢复又写回 6，就丢了一次更新。volatile 只能约束访问，不会把这三步变成不可分割。上例让一个接收任务拥有数据，先从结构上减少共享写；确需共享时再选择同步原语。

临界区保护很短的共享元数据，例如更新队列索引；具体 port 通过屏蔽相关中断/调度或锁建立排他条件，不能把整段串口等待放进去。信号量表示事件或资源计数；队列同时传递数据与等待关系；互斥锁表达“某任务拥有这个共享资源”，获得后应由该任务释放。用哪个原语，取决于要传一个通知、传一条消息，还是保护一次完整操作。

假定低优先级 L 持有日志锁，高优先级 H 等锁而阻塞，中优先级 M 持续运行，就会推迟 L 释放锁，间接延迟 H。这叫优先级反转。支持优先级继承的 mutex 可以临时提高持锁任务的调度优先级，让它尽快完成受保护区；仍须限制锁内工作和嵌套，不能据此保证任何截止期。本章的独占日志任务是另一种组织法：计算任务发送消息，日志任务独占 UART，但队列容量、服务速度和阻塞时间仍须预算。

官方参考：V11.1.0 信号量与 mutex 接口。产品应采用何种实时策略由任务期限及测量决定，本轮没有冻结优先级或 tick 参数。

整数切换成立后，再增加 FP 与 RVV 状态

FP 任务还使用 f0–f31 和 fcsr（含 frm/fflags）；向量任务还使用 v0–v31、vl、vtype、vstart、vcsr（含 vxrm/vxsat）。FS/VS 表示相应扩展状态的使用/脏状态，不是保存这些数据的容器。VLEN 是硬件能力，vlenb 表达一个向量寄存器的字节数；完整向量寄存器数据区需要 32×vlenb 字节。若取本书示例 VLEN=2048，则仅 v0–v31 数据就有 8192 字节，尚不包含整数、FP、CSR 或对齐开销。

官方 FreeRTOS V11.1.0 通用 RISC-V port 的默认保存范围是基本整数上下文，额外状态通过 chip-specific 宏扩展；本轮未发现本项目提供经核验的 FP/RVV 扩展 port，因此这个版本只能用来解释整数切换。不能把裸机 crt0 设置 FS/VS 或编译器接受 V 指令，视为抢占式向量任务已经安全。

本地 Ara SDK 展开出的 Linux v6.5 源码则可看到另一种实际实现：switch_to.h 在能力允许时调用 FP 和向量切换，vector.h 保存脏向量状态并恢复下一个线程，vector.c 按 32×vlenb 分配数据区。首次使用向量时建立状态，是正常的按需分配机制；其 trap 不应一概被视为硬件出错。

这些源码只证明软件路径存在。Ara 与 CVA6 有解耦执行，请求应答不等于全部访存结束；切换时的精确架构状态、在途操作处理、保存区地址翻译和缓存可见性，还要由该硬件/内核组合实测。顺序与完成语义先读CVA6–Ara 协作及共享数据；具体适用性记录见OS 验证缺口。本章不设计未经验证的“延迟若干拍后切换”方案。

本地 OS 参考路径：Linux v6.5 switch_to.h、vector.h、vector.c。配置模板与生成配置的差异另见证据条目。

读者验收：暂停后 A 的 sum 在哪里？B 等待队列时为什么不占满 CPU？

sum 可能在 A 的保存寄存器区或其函数栈帧，取决于编译结果；恢复必须取得 A 原来的现场。B 等待空队列时被移入阻塞集合，调度器可以选择 A/其他就绪任务。仅改变当前 TCB 而未恢复栈和寄存器，无法完成这个过程。推演入口是 A→B→A，数据验收在137 元素例。
