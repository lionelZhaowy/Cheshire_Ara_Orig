## 2. 项目目标、应用场景与已确认需求

项目最终要形成面向图像采集、校正、异构计算和 ROI 输出的 SoC：CVA6 承担控制与灵活标量处理，Ara 承担适合向量化的辅助计算，NPU/脉动阵列承担主要加速计算；独立 GB 提供片上数据复用，外购 AXI4 DDR Controller/PHY 提供外存。工程最终进入 IC 验证、DFT/MBIST、物理实现及流片流程，同时保留可运行 FPGA 工程用于对照和阶段验证。

### 4.1 三种端口命名及共享关系

| 命名空间 | 在本图中的含义 | 不应混淆的对象 |
|---|---|---|
| 主 Xbar S0～S7 / S_EXT | 接收 master 请求；CPU 为 S0，Ara 为 S2，新增 eMMC Host/DMA 为 S7 | 不是 DDR Controller 的 S 口 |
| 主 Xbar M0～M5 / M_EXT | Xbar 向目标发请求；M2 为主存/SPM，M5 为共享 GB 目标 | M5 是绘图功能出口，真实配置索引及实现方式由 E01/M01 派生 |
| 前端 F0～F3 | 自定义共享压缩前端的四个上游入口 | 四口共享编解码和元数据服务，不是四套独占编解码流水线 |
| DDR.S0～DDR.S3 | 一个 Controller 的四个 AXI slave 入口 | 不是四个控制器、四条物理 DDR 通道或四倍物理带宽 |

| 请求来源 | 连续通路 | 共享与返回关系 |
|---|---|---|
| SoC/LLC | M2→原子适配→LLC→F0→DDR.S0 | 保持主存写回/回填路径，R/B 回原请求者 |
| NPU/GB 搬运 | 搬运器↔F1↔DDR.S1 | 不分配 LLC 行；在 GB 侧与其他访问者仲裁 |
| 帧写入 DMA | DMA↔F2↔DDR.S2 | 返回方向包含 B；双箭头不增加 DMA 读能力 |
| 帧输出 DMA | DMA↔F3↔DDR.S3 | AR 发起读，R 返回；用于二维裁切读取，不因前端有写服务而要求该 DMA 写入 |

CPU/Ara 保持独立输入，共享 M5 的 64-bit 数据出口；eMMC DMA 也使用它。它们竞争同一方向的 GB 出口服务，之后还与 NPU、ISP、搬运器竞争 GB bank/物理端口。不同 Xbar 目标可以并行，但同 ID 跨目标顺序、队列和背压仍可限制并发。设计简化减少 Ara 分流及响应合并逻辑，满足负载的程度仍需测量。

### 4.2 上电到可运行程序

硬件先提供有效 RefClk/安全系统时钟、复位和可取指 ROM。Boot ROM 初始化 LLC/SPM，建立早期栈；随后经官方 Platform ROM 钩子配置安全启动 PLL、必要 PAD/时钟复位和启动必需 IP。该钩子由同一个 CVA6 执行，不能等待它来创造自己的第一个可用时钟。[官方 Platform ROM 说明](https://pulp-platform.github.io/cheshire/tg/integr/#platform-rom)

S01-B01 修复并重新生成 ROM 后，平台代码才能正常返回内置介质启动。启动介质可用后，将可更新早期固件装入已就绪 SPM；按 IP 契约完成 DDR Controller/PHY 配置、训练、ready 检查及不被缓存掩盖的小范围访问，再允许加载 DDR 程序/数据或切到 DDR 栈。现有 ZSL 会先向 DDR 加载后续固件/设备树，DDR 初始化必须在该访问之前完成。

应用 crt0 建立自己的运行环境、BSS/异常入口及所需 VS/FS，然后进入裸机程序；RTOS/Linux 后续另验。最终启动介质未定，eMMC 参数加载不自动成为早期启动依赖。运行时重配置仍走保留控制口，必须先满足受影响事务排空、安全切钟、状态生效与失败回退条件；具体合法工作点和允许调整范围见[03 平台约定](../03_Platform_ROM_Clock_IP_Configuration.md)。

### 4.3 eMMC 参数装入并交给 ISP/NPU

在 GB、Host 和控制接口就绪后，软件选择参数包及目标 GB 分块，设置 Host 命令、源范围、目标地址和长度。**Host 内置 DMA 经 S7→主 Xbar→M5→GB 访问适配写入 SRAM**，不借用 Cheshire iDMA。

模型参数、ISP 非均匀性校正与盲元补偿参数按 GB 可用容量分批装载。驱动核对长度、版本/完整性和任务结果，等待必要传输结束且 GB 可见，再把分块交给 ISP/NPU。参数何时生效必须与帧/任务身份一致；采用帧边界提交或双参数缓冲等具体机制仍待接口设计，不能覆盖正在使用的参数区。消费结束、在途访问已终止后才复用分块；加载报错时保持无效状态并从可靠来源重装。参数包格式和检查机制尚未冻结。

### 4.4 一帧 RAW/ISP 数据写入 DDR

传感器经 LVDS 输出，RX 完成解串/对齐和帧行识别，CDC/FIFO 把像素流送入 ISP/RAW 路径。ISP 按已交接参数处理，并通过 GB 访问适配使用参数或中间数据；RAW 支路绕过 ISP，二者经帧边界选择交给同一帧写入 DMA。v1 表达选择输出，不自动增加 RAW 与处理后数据同时存储的需求。

软件预留合法 DDR 帧缓冲，发布帧身份、尺寸、stride、格式和模式。若该范围曾由 CPU 缓存路径使用，先完成设备写前准备。DMA 按行打包 AXI 写，经 F2→DDR.S2 到 DDR；压缩区执行无损压缩和元数据更新，普通区走旁路。帧末只表示像素生产结束；所有必要写、元数据提交、错误检查和跨口可见条件完成后，才发布帧可消费状态。

若传感器不能背压，FIFO 与 DDR 服务间隔必须满足预算，溢出/丢帧策略由产品/I01明确；不能静默覆盖仍被 ROI/NPU 使用的帧。RAW/ISP 切换和校正参数更新须在约定边界生效，排空旧路径，保证帧、格式、参数版本一致。传感器额外控制总线与电气条件属于待输入，图未画出不代表已实现。

### 4.5 ROI 裁切后 LVDS 输出

源帧完成交接后，软件为该帧提交最多 256 个矩形 ROI 及顺序；调度器驱动**单个二维读 DMA**，按起点、宽高、行跨度读取所需行，经 F3→DDR.S3 取回逻辑像素。压缩区通过共享解压器恢复数据，普通区走旁路，随后由输出 FIFO/像素整理和 LVDS TX 封装子图帧行，发送到后级处理。

纯裁切保持像素值，不缩放。每行请求与压缩块不对齐时可能多读并解码完整块，需分别统计“ROI 有效像素字节、实际 DDR 字节、解码字节”；不默认先读整帧再丢弃。格式、重叠 ROI 的重复输出规则、越界处理、空任务行为和任务表生效协议需明确。最后一个 ROI 的 AXI 读取、FIFO 消费和 TX 发送完成点分别定义；源帧释放需等所有读者结束，不能仅凭读命令出队。背压、欠载和链路错误时保留失败帧/任务身份，按协议中止或重发，不发布完整成功。

### 4.6 DDR↔GB、NPU/Ara 处理与 CPU 后处理

CPU 在 DDR 准备输入时，先完成第 6.2 节输入同步。搬运器经 F1 从 DDR 读取并写入已预留 GB 分块；GB 装入完成后 NPU 计算，Ara 经自己的 Xbar 输入和 M5 对 GB 做向量辅助处理。NPU 计算、Ara 向量指令和搬运命令是不同控制路径，Ara 不作为 MMIO 启动的 NPU 来使用。

若结果回 DDR：设备写前准备输出范围→GB 搬出→DDR 跨口可见→输出最终失效→CPU 消费。若结果留 GB：生产者完成并交出 GB 区间，CPU 经 S0→M5 直接读取小结果、候选表或索引，按需复制到自己的可缓存工作区做多轮排序。这是软件工作流建议，结果规模和时限未定。

CPU 直访 GB 解决片上小结果交接，不撤销 DDR 同步。普通 DDR/GB 地址在 Xbar 处分流，GB 不经过 LLC；GB 也不是 DDR 别名或透明缓存。每块数据经过“装入完成→计算可用→结果可消费/搬出→所有访问终止→可复用”，软件必须能区分每个阶段。失败时执行第 8.3 节恢复流程，不把计算完成或 IRQ 当成数据交接完成。

### 6.2 DDR 共享缓冲的范围维护

**已确认方向**：软件决定交接的 DDR 物理范围与时机，硬件覆盖 L1D、WT 写缓冲、LLC 以及相关读写、回填和替换；建立维护窗口，汇合实际完成与错误状态，再放行依赖设备。缓存数据经 F0 写入 DDR，由设备端口读取，不新增 LLC→GB 直接供数口。

| 阶段 | 必须成立的条件 | 软件/设备允许做什么 |
|---|---|---|
| 建立上下文与窗口 | 保存物理范围、操作和任务身份；软件停新冲突访问，硬件限制冲突请求，同时让已接受事务所需的数据/响应前进 | 接受确认只代表命令已保存；不得提前启动依赖搬运 |
| 输入交设备 | 等 CPU/Ara 生产者；先推进写缓冲与上游旧写，再 clean LLC；确认通过前端和 DDR 后对目标端口可见 | 成功后启动 DDR→GB；干净输入副本可按协议保留 |
| 设备写前准备 | 排空旧写，clean＋invalidate 输出范围，保护部分行未覆盖字节，收束冲突回填/替换 | 输出范围准备成功才允许设备写 |
| 设备持有 | 软件保持完整维护范围的使用约束；GB 装入、计算、搬出有独立完成身份 | CPU 可处理其他数据，不能改同一维护行内邻接对象 |
| 设备写后交 CPU | 写数据和元数据满足跨口可见；排空相关旧读响应，再最终 invalidate L1D/LLC；冲突脏数据作为错误处理 | 最后确认成功才读结果；不得在此把旧脏值 clean 到新结果上 |
| 出错/超时 | 本次及历史相关错误纳入结果；接受不明按可能已启动处理；保留范围与身份 | 停止新提交，隔离资源，确认旧活动终止或受控恢复后再复用 |

维护窗口须覆盖“命令接受→上游排空→所需 L1 更新→LLC 维护→整体同步完成”，具体信号/编码、范围仲裁或短暂全局停顿尚待细化。上游写依赖 LLC 接收时先排上游，再隔离 LLC，防止循环等待。Ara `inval_ready` 是请求接收，不是通用缓存维护完成确认。

当前 32 B L1D 行与 64 B LLC 行需要按公共维护粒度隔离缓冲，范围向外取整后也不能与其他活跃对象重叠；未来配置改变时统一更新。设备持有期间的软件纪律与自动拦截 CPU 违规访问是两种能力；若后者成为需求，必须覆盖 L1 命中路径，LLC 下游挡门不足以实现。

`fence`、`volatile`、一次 B 响应或 IRQ 到达均不能单独证明完整交接。当前 FENCE 有写缓冲完成条件，但没有替代 LLC clean 的系统路径。MMIO 范围命令/HAL 是已有设计建议；Zicbom/自定义指令、CSR、IRQ 和命令粒度未选定。标准 CMO 只提供操作语义参考，不证明本地已实现其跨层传播。[RISC-V CMO v1.0](https://docs.riscv.org/reference/isa/v20240411/unpriv/cmo.html)

维护服务在 v1 全景图中未单独绘出，仍是必须实现的跨层功能。其控制寄存器可经既有控制扩展机制承接，但与 C11/C12/C14 等现有组的归属、独立模块划分和错误汇合位置**尚待 M01/I01/S01 细化**；本总纲不新增 C 编号、不改图。完整协议以[DDR–GB 同步设计 §3～7](DDR_GB_Coherence_Design.md)为主要说明。

### 6.3 共享压缩前端与四口可见性

| 部分 | v1 职责 | 必须落实的边界 |
|---|---|---|
| AR/AW | 区域选择、地址/事务控制、块地址映射 | 地址控制不穿过数据编解码器；长度、边界与元数据访问保持正确 |
| W | 压缩区使用共享压缩器 | 字节选通、部分写、跨块和不可压缩原样块；最坏膨胀/分配容量须有保证 |
| R | 压缩区使用共享解压器 | 返回原始逻辑数据、正确拍数/顺序/ID；独立块解码与 ROI 额外读取 |
| 普通旁路 | 普通区域 W/R 原样传递 | 不能作为绕过压缩区格式解释的暗门；四口对同一地址使用相同属性 |
| 元数据 | 四口共享的区域/块格式、位置和有效状态 | 更新发布原子性、竞争写、错误检测及恢复；通过已有下游路由访问，不凭图增加第五口 |
| B / 响应匹配 | 下游 R/B 与原上游事务关联 | B 不经过编解码；一个上游操作可能有多个数据/元数据子事务，成功条件须聚合 |

四个独立下游接口保留来源和响应归属，共享资源需公平性/服务预算。对缓存 clean 或设备写，目标完成点是：另一个获准端口随后读同一逻辑地址得到新数据，包含前端数据/元数据、CDC、Controller 队列的影响。若供应商 B 语义已包含所需可见性，直接使用其保证；否则按官方能力补完成机制，不能自行假定一个新握手信号就解决问题。

### 6.4 原子、启动存储与故障前进性

当前 LLC 前适配器处理 AMO/LRSC，下游普通 AXI4 DDR 不必因此实现 ATOP。但设备旁路普通写不自动被该 reservation/原子观察点看到；把适配器移到 LLC 后或再加一个原子单元都不能自动修复缓存旧副本。GB 的 M5 支路也不继承 M2 原子支持。

首版按既有建议隔离共享控制与设备数据，不把 GB 或未经验证的旁路区作为 CPU/设备并发 AMO/LRSC 控制区；不支持操作应明确拒绝。若确需共享原子对象，另评所有相关访问的统一观察与缓存协议。CPU 私有、不受旁路写影响的原子域继续回归，不能一概禁用。

LLC 阵列承担 SPM，启动栈及驻留数据必须保护。缓存/全 SPM/混合 way 的切换需要软件迁出受影响对象、排空事务并完成维护。现有 LLC 隔离入口位于 cache/SPM/旁路分流之前，可能阻塞 SPM 栈访问；维护引擎须自主推进，不反过来等被阻塞 CPU 回调。普通有限停顿与故障无限等待分开处理；只有产品规定故障硬时限时，才确定独立监控/恢复主体及预算，不能假定 CPU 轮询总可执行。

### 8.3 所有链路共用的失败与恢复要求

首次维护/提交前建立上下文，保存 DDR/GB范围、实际长度、取整维护范围、帧/参数/任务身份及所处阶段。token/epoch 是识别迟到事件的设计建议，编码和位宽待定，不能靠换编号阻止迟到写。

出错后停止新提交，区分命令未接受、接受不明、部分传输和完成后报错；接受不明按可能已启动处理。保留相关 GB/DDR 和任务上下文，等待已接受事务排空，或按真实 IP 支持的隔离/复位协议确保其不再访问旧地址，随后才归还资源。单侧复位、软件超时、清 DONE 或 IRQ 均不能独立证明安全复用。

停止旧活动与恢复数据是两步。部分输出、坏元数据或失败参数包应标无效，从可靠输入重建；复位不会补齐数据。恢复仍超时则继续隔离并上报平台故障，不能悄悄重复使用相同缓冲。错误状态不能在下一同步命令到来时无条件清零；已丢失定位能力的历史错误需扩大拒绝报成功的范围。详细供应商队列/低功耗/复位覆盖问题仍使用原会议表，不虚构自动回滚或透明重试。
