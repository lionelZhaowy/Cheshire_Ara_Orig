# DDR–GB 数据同步设计：从裸机推理到缓存维护

返回[工程参考](README.md) · [供应商会议问题](DDR_Supplier_Coherence_Questions.md) · [评审与答疑 Q&A](../maintenance/L01/reviews/ddr_gb_coherence_review_qa.md) · [图稿与可编辑源](../diagrams/2026-10-20_ddr_gb_coherence_v1/README.md)

本文沿一次裸机推理解释本项目的数据同步方案：**软件指定要交接的 DDR 数据范围；硬件推进 L1D 内部写缓冲中的相关写入，并维护 L1D／LLC 的缓存副本，使缓存与 GB 通过 DDR 交换正确的数据。** CPU 在其他时间正常使用缓存。

2026-10-20，L01 按已确认的[SoC 架构 v1](SoC_Architecture_v1_Master_Plan.md)同步文档与配图，输入 `mp/ara-pulp-v2` / `c9abbb48`。2026-10-16 的评审与源码发现保留其原始版本；新增 GB、四口 DDR 共享压缩前端和范围维护服务仍待实现及验证。正文 HAL 为概念伪代码，本轮没有修改 RTL 或运行硬件测试。

## 1. 一次裸机推理由 CPU、搬运器和 NPU 共同完成

设 CPU 要对一块输入数据执行推理。程序在 DDR 中准备输入缓冲区 `input`，为结果预留输出缓冲区 `output`。NPU 的计算单元从片上 GB 取得操作数，因此任务还包括两次搬运：先把输入从 DDR 装入 GB，再把 GB 中的结果写回 DDR。CPU 最后读取 `output`，继续后处理。

这里的**输入／输出缓冲区，是软件为数据预留的一段内存**，例如经链接脚本或分配器安排在 DDR 中的输入数组。“缓冲区”描述它的用途，底层存储仍是 DDR。本文涉及的三个相近名称各有明确对象：

| 名称 | 保存什么 | 所在位置与访问方式 |
|---|---|---|
| 输入／输出缓冲区 | 张量、图像块或计算结果 | 本文示例中位于 DDR，软件用指针访问，设备按地址搬运 |
| WT 写缓冲（write buffer） | CPU 写操作的地址、数据及处理状态 | CVA6 的 WT L1D 内部，由缓存硬件管理 |
| Global Buffer（GB） | 搬入的操作数、中间结果和待搬出的输出 | 规划中的独立片上 SRAM，经共享数据代理访问 |

软件缓冲区的地址范围决定同步对象。CPU 访问这些地址时，相关数据可能暂存在写缓冲中，或形成 L1D／LLC 副本；维护服务处理的正是这些硬件状态。

这段程序从 `main()` 看是“准备数据、调用推理、使用结果”；从硬件看，则涉及 CPU 访存、缓存、DDR 控制器、搬运器和 GB。CPU 的普通 DDR 访问经过 L1D、主互连和 LLC。设备经共享压缩前端及 DDR 控制器的独立端口搬运，流量绕过 LLC。两条路径在 DDR 子系统汇合，因此双方交换数据时需要先约定哪一份数据有效。

裸机程序同样会遇到这一问题。C 语言的数组赋值最终产生 CPU 的 load／store 指令，是否命中缓存由硬件配置和地址属性决定，与有没有操作系统是两件事。程序中的指针告诉 CPU 访问哪个地址；设备任务里的地址告诉搬运器去哪里取数。两个地址对应同一块 DDR，只是数据交换的起点，后续还要保证两条路径看到相同版本。

本文先讨论输入、输出分离的一次任务，默认启动阶段已使 DDR 可用，并已配置需要使用的 LLC cache way。LLC 阵列也承担 SPM，启动栈等驻留内容应由平台保留。系统连接的需求依据见[IP／DDR／GB 契约](IP_DDR_Interface_Contract.md)，运行时缓存状态则由具体平台初始化决定。

## 2. CPU 与设备可能读到同一地址的不同版本

**写缓冲是 L1D 的内部硬件结构。** 当前 [wt_dcache.sv](../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/cache_subsystem/wt_dcache.sv)实例化了 `i_wt_dcache_wbuffer`；[向量配置](../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/include/cv64a6_imafdcv_sv39_config_pkg.sv)将 `CVA6ConfigWtDcacheWbufDepth` 设为 8，即八个条目。模块中的 `wbuffer_q` 保存数据及状态，通过 `always_ff` 更新，在 RTL 中表现为寄存器状态数组及配套控制逻辑。它封装在 CVA6 内部，没有供软件直接寻址的独立存储区，因此 SoC 顶层图只在 CVA6 框中标注“L1D／写缓冲”。图 2 为便于跟踪数据，将 L1D 阵列与写缓冲分栏展示。

先看输入中的一个数 `x`。DDR 初值为 1，CPU 把它改成 2。当前向量配置采用 WT（write-through，写直达）L1D：store 的更新进入写缓冲，再送往下层。这个版本允许后续 load 从写缓冲前递新值；写应答返回后，再按命中状态更新 L1D 阵列。因此，在图 2 的第一个时刻，L1D 阵列还可以保存 1，CPU 读取却能通过前递得到 2，而 DDR 仍保存 1。写缓冲让 CPU 与总线传输解耦，也说明“CPU 已能读回自己写的新值”与“设备已能从 DDR 读到新值”有不同的完成条件。[写缓冲实现](../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/cache_subsystem/wt_dcache_wbuffer.sv)的开头说明及写应答处理对应这一过程。

写缓冲排空后，新值进入下层存储路径。这里还有一个 WB（write-back，写回）LLC：它可以接收更新，把对应缓存行标为脏行，等替换或清理时再写往 DDR。此时 LLC 保存 2、DDR 保存 1。设备绕过 LLC 读取 DDR，仍会得到旧输入。**WT 描述 L1D 向下传递写入的方式；下层 LLC 的写回策略决定数据何时继续到达 DDR。**

再看输出中的 `y`。CPU 曾读取过它，L1D 或 LLC 中留着值 0。NPU 算出 9，并通过设备端口写入 DDR。CPU 再读 `y` 时若命中旧副本，就会看到 0。这里缓存行可以是干净的：干净只说明它没有尚待写回的 CPU 修改，外部设备写入以后，这个副本仍可能过期。

还有一种破坏性更强的情况：CPU 先前写过 `y=3`，旧脏行留在 LLC；设备随后把 DDR 更新为 9。稍后 LLC 替换该行，把旧值 3 写回 DDR，设备结果就被覆盖了。因此，输出交接必须在设备写入前处理旧脏数据，而非只在 CPU 读取结果前清除副本。

## 3. 软件确定交接时机，硬件完成缓存维护

模型运行程序知道 CPU 何时写完输入、NPU 何时开始使用，以及 CPU 何时需要输出。利用这些边界，软件可以一次交出整个缓冲区或计算分块，让硬件集中处理该范围的缓存状态。这样，维护成本与实际数据交接次数相关，设备连续搬运期间可以沿既定 DDR 通路工作。

“交出缓冲区”指软件停止 CPU／Ara 对该 DDR 范围的后续访问，等待已有生产者完成，再向维护服务提交物理地址、长度和用途。设备持有期间，中断处理程序和其他设备也遵守这一约定；CPU 可以处理其他独立数据。约束覆盖维护涉及的完整缓存行，包括传输范围外、同一行内的邻接字节。软件停止新访问，硬件负责处理此前已接受的事务。

这里转移的是缓冲区的使用权，DDR 地址和存储容量保持原样。输入同步成功后，程序保留指针但暂停使用这块输入；输出同步成功后，同一个输出指针可以重新用于读取。这种安排把缓存状态变化封装在交接点，应用仍按普通数组处理数据。

三个常见操作分别解决不同问题。**clean（清理）**把脏数据推进到约定的共享位置，本方案要求最终对 DDR 设备端口可见；**invalidate（失效）**清除缓存副本，使后续读取重新取数；**fence（屏障）**约束数据访问与控制命令的先后顺序。例如，要先完成输入准备，再向设备发布启动命令。`flush` 在缓存维护语境通常表示清理后失效，具体接口应明确这两个动作及其完成点。操作语义参考 [RISC-V CMO v1.0](https://docs.riscv.org/reference/isa/v20240411/unpriv/cmo.html) 和 [FENCE 规范](https://docs.riscv.org/reference/isa/v20240411/unpriv/rv32.html)。

对写缓冲所说的“排空”，是推进相关写入并等待其完成，使待处理条目能够正常释放；简单清零条目会丢失尚未送出的数据。写缓冲排空之后，还需按下层状态清理 LLC，才能使新值对 DDR 设备端口可见。软件交出 DDR 缓冲区的使用权、硬件排空写缓冲、搬运器把 DDR 数据复制到 GB，是三个不同的动作。

每次交接设置一个受保护的维护窗口：硬件限制新的冲突请求进入，同时允许已经接受的请求、后续数据和响应继续前进；待相关读写、回填和替换完成，再修改缓存状态、收齐确认并退出窗口。入口限制若同时挡住完成旧事务所必需的传输，就会使排空无法结束。实现时可以选择范围仲裁或短暂全局停顿。设备计算期间由软件维持范围使用约定；若需硬件拦截所有违规访问，还要覆盖 L1D 命中路径。

交接粒度由程序的数据依赖决定。如果模型的各层都在设备内部连续执行，CPU 只在两端提供输入、读取输出，同步可以集中在推理前后。如果中间某层需要 CPU 后处理，再交给 NPU，那么这次交替使用就是新的同步点。用一次整模型同步覆盖所有内部交接，会遗漏中途产生的新版本；逐元素同步又会把本可批量执行的维护拆得过碎。

维护以搬运描述符中的 DDR 侧物理地址为依据，即共享压缩前端上游的软件可见逻辑地址，按缓存粒度向外覆盖；搬运仍按实际数据长度执行。压缩后的块位置及元数据地址由前端管理，不作为软件缓存维护地址。压缩块与缓存行大小可以不同；同块部分写及元数据竞争由前端协调，不能仅按 32/64 B 缓存行隔离就认定压缩块更新安全。GB 保存本次装入的版本，下一轮需要更新后的输入时重新搬运。每个分块都有“装入完成、计算可用、结果可搬出、空间可复用”的生命周期，这些条件由 GB 本地任务调度衔接。

## 4. 输入维护使设备从 DDR 取得最新数据

仍以 `x=2` 为例。CPU 完成输入准备后，首先等待参与生产的 CPU／Ara 工作结束，再提交输入同步。维护服务先推进相关写缓冲及在途写，让这些更新进入下层。应先让依赖 LLC 接收的上游写入排空，再隔离 LLC 并清理；反过来既可能漏掉新写，也可能形成“LLC 等上游排空、上游等 LLC 接收”的循环等待。

下一步清理输入范围内的 LLC 脏行。若 LLC 已有 `x=2`，就沿 F0→共享前端→DDR.S0 把它写向 DDR；若某行保持干净，DDR 已有对应版本，可以省去该行的数据写回。输入交接后设备只读这份数据，因此 CPU 的干净副本也可以保留，减少今后重新读取时的 miss。

然后需要确认设备端口能够看到写回结果。GB 搬运器经 F1 读取，ROI 帧输出 DMA 经 F3 读取；F2 在本项目是帧写入来源，不能把它当作读消费者。普通旁路区由前端原样转发，压缩区还需完成数据和元数据的关联发布，保证其他端口随后读取同一逻辑地址得到新值。成功响应足以证明这些条件时直接使用；否则按前端设计及供应商已有能力补充完成依据，不预设新 DDR 信号。控制器可以通过排序或转发满足可见性，无须等待 DRAM 单元实际更新。已核对的 Datasheet V2.1 支持多端口与 AXI4，但实际四口交付和跨口语义仍待确认。

给供应商的具体例子是：地址 P 初值为 1，DDR.S0 写入 2 并收到成功 B，系统此后才从 DDR.S1 或 DDR.S3 读取 P；无其他写入时，应返回 2。帧写入 DDR.S2 后从 DDR.S0／S1／S3 读取，以及 GB 搬出 DDR.S1 后从 DDR.S0／S3 读取，也需明确保证。供应商说明 Controller 边界的行为；项目还须证明 F0–F3 上游经过前端、CDC 和通知路径后的完整条件。[会议问题](DDR_Supplier_Coherence_Questions.md)保留 Q1–Q7 及待答复栏。

维护引擎汇合缓存操作与 DDR 可见性确认后，返回同步成功，软件才发布输入搬运任务。至此，数据经历了 **CPU 生成 → 先行写推进 → LLC clean → DDR 可见 → 搬入 GB**。GB 装入完成又是 NPU 开始消费该分块的前提。

权重在多轮推理间保持不变时，可维持相应设备使用状态，减少重复同步；GB 容量不足导致的再次搬运仍由调度决定。输入不断变化时，可用两个独立缓冲区，让设备处理上一块、CPU 准备下一块，并在每次交换角色时同步。

## 5. 输出维护保护未覆盖字节，并让 CPU 读取新结果

输出在设备写入前采用 **排空旧写、clean＋invalidate** 的准备流程。排空和清理使 CPU 已有修改落到 DDR，失效清除旧副本；维护期间还要处理正在替换或回填的相关事务。完成后，设备可以获得一块没有旧脏写等待覆盖它的输出范围。

部分行写入说明了清理的必要性。把一行分成四段，DDR 当前为 `[1,2,3,4]`，LLC 中的最新值为 `[10,2,30,4]`，设备只准备把第二段改成 9。先清理得到 `[10,2,30,4]`，设备再用有效字节使能更新第二段，结果为 `[10,9,30,4]`。直接丢弃 LLC 脏行会丢失第一、第三段的 CPU 更新；保留旧脏行则可能在以后把第二段重新覆盖为 2。

即使软件只申请几个字节，维护也会涉及完整缓存行。当前 L1D 行为 32 B，默认 LLC 行为 64 B，一个 LLC 行覆盖两个 L1D 行。因此，缓冲区的分配、交接和保护范围应按公共粒度覆盖；锁、栈或其他仍在修改的对象应放在独立行中。AXI beat 和 `WSTRB` 描述一次传输的有效字节，完整覆盖优化则需要证明整个相关缓存粒度都被覆盖，并处理跨行和失败情况。基线对完整行也采用同样的准备流程。

设备随后从 GB 搬出结果。NPU 算完时，结果还可能停在 GB 或写队列；软件应等待搬出完成，并确认结果通过共享前端后对 CPU 的 F0 读取可见；压缩区包含数据和元数据，普通旁路区包含原样数据传输。任务完成状态必须包含这些依赖，单独的计算结束信号只适合启动下一阶段搬运。

交还 CPU 前，先限制冲突新请求、等已有读响应完成，再最终失效输出范围的 L1D／LLC 副本。优先采用排空后失效的顺序；只有需要更高并发时，才评估响应丢弃或重放。若发现冲突脏数据，进入错误处理，保留现场，避免把旧值清理到设备结果之上。设备写后已经发生过的违规写回，还需靠使用权约束和事务跟踪防止。

迟到响应的风险可用四步说明：①缓存读请求先取得 `y=0`；②响应受背压暂存；③设备把 DDR 改为 `y=9`；④旧响应随后到达，仍携带 0。这里指 CPU 缓存层次的回填响应，其数据在第①步已经确定。若先失效再允许第④步安装，就会恢复旧副本。这是需要防护的条件性竞争，当前路径是否允许该交错尚待验证；完整的写前排空会排除相应的交接前请求，写后维护则收束其余允许发生的在途访问。

成功返回后，CPU 才读取结果。按行维护保证各行的数据版本正确，整个张量何时可用则由任务完成协议确定；这使应用能够在明确的时间点消费一份完整输出。

## 6. 裸机程序用显式同步串起完整推理

下面采用单任务、独立输入输出、物理地址可直接使用的裸机环境。缓冲区按完整维护粒度隔离，权重已准备好。输入与输出向外取整后的维护范围也须互不重叠；两个数组的字节范围不同、却共享一条缓存行，仍不满足本基线。首次维护前建立上下文，记录 DDR／GB 资源、实际传输范围、维护范围、请求身份及阶段；HAL 在提交前登记待提交状态，接收确认后再推进阶段。以下函数均为拟议接口，`limit` 表示各阶段的等待预算。

```c
int infer_one_block(void)
{
    context *ctx = reserve_context_and_buffers();
    int rc;
    if (!ctx) return NO_MEMORY;
    prepare_input(ctx->in.cpu_ptr);
    rc = wait_input_producers(ctx, limit);
    if (rc) goto failed;
    rc = sync_input_for_device(ctx, limit);
    if (rc) goto failed;
    rc = prepare_output_for_device(ctx, limit);
    if (rc) goto failed;
    /* HAL 登记提交状态，再发布参数与启动命令。 */
    rc = submit_inference(ctx, limit);
    if (rc) goto failed;
    rc = wait_result_visible(ctx, limit);
    if (rc) goto failed;
    rc = sync_output_for_cpu(ctx, limit);
    if (rc) goto failed;
    consume_output(ctx->out.cpu_ptr);
    release_after_success(ctx);
    return 0;
failed:
    quarantine_context_and_buffers(ctx, rc);
    schedule_recovery(ctx); /* 上下文继续存活，恢复后才释放 */
    return rc;
}
```

HAL 用编译器屏障及适当的 FENCE 建立数据、MMIO 命令和结果访问的顺序。下面的成功条件是硬件服务的接口要求；每次轮询同时检查完成与错误，超时转入恢复。命令已接收用于确认提交状态，后续阶段等待实际动作完成。

| 等待点 | 成功后具备的条件 | 错误或超时后的处理 |
|---|---|---|
| 生产者完成 | CPU／Ara 已停止生产并交出范围 | 保留资源，确认生产者是否仍活动 |
| 输入同步 | 先行写与 LLC clean 成功，设备端口可见 | 禁止启动搬运，追踪维护请求 |
| 输出准备 | 旧写已完成，未覆盖字节受保护，失效确认齐全 | 保留范围，处理未完维护 |
| 提交任务 | 已明确接受任务及其身份 | 接受情况不明时按可能已启动处理 |
| 结果可见 | 搬入、计算、搬出成功，CPU 端口可见 | 停止新增任务，追踪在途搬运 |
| 输出同步 | 冲突回填已处理，旧副本清除 | 保留输出，等待恢复确认 |

![裸机调用与硬件动作时序](../diagrams/2026-10-20_ddr_gb_coherence_v1/previews/timeline.png)

图 3：时间向下，图中合并输入／输出准备的细部确认。首次维护前已有上下文；维护窗口先限制冲突请求，再排空和更新状态，并保护到最后一次确认。“排空及失效确认”是目标服务的完成条件，Ara 的 `inval_ready` 只表示接收请求。设备期间遵守范围使用约定，CPU 可处理其他数据；最后一次确认之后才消费结果。[SVG](../diagrams/2026-10-20_ddr_gb_coherence_v1/figures/timeline.svg)

从应用层看，主线是：**同步 DDR 中的输入 → 搬入 GB 并计算 → 将结果搬回 DDR → 同步输出后由 CPU 读取。** 输入区是搬运器读取的 DDR 地址范围，输出区是结果写回的 DDR 地址范围。输入同步只需覆盖输入；输出范围另需在设备写入前排除旧脏数据和待处理旧写。图 3 将这项输出准备提前到任务启动前，与输入同步合并展示；两者可以由不同软件调用完成，已经完成且持续受保护的维护无需重复执行。

下表按图中从上到下的顺序为 16 个箭头编号；图像使用相同的 1–16 编号。硬件步骤编号按“输入同步①–④、输出准备与设备执行⑤–⑦、CPU 读取前同步⑧–⑨”组织，因此提前执行的⑤与①–④共用图中的准备阶段。

| 应用层过程 | 硬件步骤 | 图 3 的箭头及含义 |
|---|---|---|
| DDR→GB 前，软件发起输入同步；图中同时申请输出准备 | ① 接收同步命令 | **1** CPU→维护引擎：提交输入同步和输出准备的范围及操作 |
| 推进 CPU／Ara 已产生的相关数据 | ② 排空相关旧访问 | **2** 引擎→L1D：限制冲突新请求、排空旧访问；**3** 写缓冲→LLC：推进待处理写入，LLC 保持接收；**4** L1D→引擎：确认排空，图中还包含输出 L1D 失效完成 |
| 将输入最新数据同步到 DDR | ③ 清理 LLC | **5** 引擎→LLC：对输入执行 clean；**6** LLC→DDR：经 F0／DDR.S0 写回脏数据、检查聚合响应。输入的干净副本可以保留 |
| 设备写 DDR 前，准备写入目标范围；图中提前执行 | ⑤ 处理输出目标范围 | 与 **2–6** 共用这段流程：排空目标范围旧写，完成 L1D 失效及 LLC clean＋invalidate，保存未覆盖字节并防止旧脏写覆盖结果 |
| 软件等待准备完成，允许启动搬运 | ④ 确认同步完成 | **7** DDR 侧→引擎：确认经过共享前端后的跨端口可见，汇合缓存完成和错误；**8** 引擎→CPU：返回准备成功。退出维护窗口后，软件继续保持交接范围的访问约定 |
| DDR→GB→计算→DDR | ⑥ 执行计算和搬出 | **9** CPU→任务控制：提交任务并确认接受；**10** 搬运器经 F1 读 DDR→GB：装入输入，完成后执行图中的 NPU 计算框；**11** GB→搬运器经 F1 写 DDR：搬出结果 |
| 软件等待结果写回 DDR | ⑦ 确认结果可见 | **12** 任务控制→CPU：搬出成功，结果对 CPU 端口可见；随后还需完成缓存同步 |
| CPU 读取前，同步输出 | ⑧ 完成最终失效 | **13** CPU→引擎：申请输出同步；**14** 引擎→L1D：收束相关回填后失效；**15** 引擎→LLC：协调在途事务后失效。发现冲突脏数据时进入错误处理 |
| CPU 读取结果并后处理 | ⑨ 返回同步成功 | **16** 引擎→CPU：收齐确认且无错误，允许读取；实际读取和后处理在图后发生 |

图中既有同步命令与确认，也有实际数据传输；每个箭头并非一次独立的软件调用。图中“前端／DDR／搬运器”泳道合并表达跨模块动作；箭头 7 表示包含前端的跨口可见条件，压缩区需聚合数据／元数据子事务，具体依据由前端与 DDR 契约确定；部分缓存返回确认已合并到整体完成中。上述为目标服务的动作与完成要求，现有机制的可复用范围见第 7 章。

LVDS 输出沿用相同的“生产完成→交接→消费”原则，但不必完整执行推理的 16 步：

| 交接场景 | 必须完成的动作 | 缓存维护与释放条件 |
|---|---|---|
| CPU 修改 DDR 帧后交给 LVDS 输出 | 排空相关旧写、clean LLC，经 F0 发布成功后允许 F3 二维读 DMA 取帧 | 输入干净副本可保留；输出 DMA 只读，读取本身不会使 CPU 副本过期 |
| ISP／RAW 帧 DMA 写 F2，或 GB 搬运写 F1，随后 F3 读取 | 写前排除目标范围的旧缓存写；写及所需元数据发布成功、F3 可见后才启动读取 | 未涉及 CPU 缓存的区域不机械重复 clean；有 CPU 旧副本时按实际交接维护 |
| F3 输出后 CPU 再访问同一帧 | 等待相应数据使用权交接；若帧此前由 F1/F2 修改，CPU 读取前最终失效旧副本 | F3 读取不会修改帧；无需仅因 LVDS 输出而新增失效 |

源帧保持到所有相关 DDR 读取完成，包括其他 NPU/CPU 读者。DMA 读取完成、FIFO 消费完成和 LVDS TX 发送完成是不同状态：仅当数据已完整复制且后续不再读源帧时，源帧才可先于 TX 结束释放；保留重读／重发需求时继续持有。帧末、命令出队或单个响应均不替代整个任务完成。eMMC 参数仍按“DDR 就绪后 eMMC→DDR，运行时 DDR→GB”装入，两个阶段分别确认。

超时表示软件等待预算耗尽，硬件可能仍在执行原任务。例如任务 A 要把 GB 的 4 KiB 结果写到 DDR 地址 P，搬运只完成一部分时软件超时。如果立即把 P 交给任务 B，A 后续发出的写、或已进入互连／DDR 队列的写，就可能覆盖 B 的数据。这里的“旧事务”指属于前一任务而尚未完成的访问；其他来源还包括 CPU／Ara 先前读写及 LLC 发起的写回、回填。软件返回错误不会自动取消这些访问。

恢复流程先停止继续提交任务，查询维护与搬运状态，再等待原任务及其访问完成，或通过经过验证的停止／隔离／复位流程阻止它们继续修改资源。只停止搬运器新增请求，还需处理下游已经接受的请求；更换任务编号只能识别迟到通知。确认旧活动不会再访问 DDR／GB 后，资源才可重新分配和初始化；若要继续使用原内容，还须证明数据完整有效，或从可靠来源重建。停止活动与恢复数据是两个步骤，复位不会补齐半份输出。恢复也超时时继续保留资源并上报平台故障。

基线在启动前一次取得所需范围，避免持有一块再等待另一块；扩展多任务时采用统一获取顺序或一次性预留。维护引擎启动后自主推进，完成过程应避免依赖持锁线程或被暂停的 CPU 回调。

当前 [LLC 入口隔离](../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/axi_llc_top.sv)位于缓存／SPM／旁路分流之前。若栈位于 SPM，CPU 在维护期间执行一次必须走出 L1 的栈读取，例如 L1 miss，该访问就会被隔离入口暂时挡住。正常情况下 LLC 自主完成维护并解除隔离，CPU 随后继续执行，这是有限等待。若下游一直不返回 B、接口被错误关钟／复位，或维护引擎反过来等待被阻塞的 CPU 回调，等待才可能无法结束。状态寄存器在独立路径上，也不能保证 CPU 能越过前面的栈访问去轮询它。

栈和代码的位置由启动、链接及运行时配置决定；例如 [dram.ld](../../sw/link/dram.ld)把栈设在 DDR，不能假定所有程序均使用 SPM 栈。实现时核查代码、栈、状态接口及计时器的完整访问路径。若产品要求故障时也有硬时间上界，就需明确不依赖受阻 CPU 的监控和恢复主体；普通维护的暂时停顿本身无需据此增加复杂恢复硬件。具体超时预算和恢复目标仍待确定。

描述符采用 MMIO 参数或经验证的非缓存存储；使用可缓存描述符时另行同步。中断可替代轮询，完成条件相同。当前[crt0](../../sw/lib/crt0.S)调用 `main()`；[DMA HAL](../../sw/include/dif/dma.h)和[SPM DMA 例程](../../sw/tests/dma_2d.spm.c)提供寄存器提交、任务 ID 和等待结构的参考，新增服务仍需实现。RTOS 可复用底层服务并增加范围管理；Linux 由平台 DMA 后端承接。地址转换、缓存可见性与任务等待各有职责，参见 [Linux 6.5 DMA API](https://docs.kernel.org/6.5/core-api/dma-api-howto.html)。

## 7. 范围维护引擎连接现有缓存与搬运控制

实现上述 HAL，需要把范围命令、缓存维护与搬运准入连接起来。服务在查询前建立维护窗口，并保持到在途事务和状态更新完成，避免检查完 tag 后又建立旧副本。缓存数据继续沿 LLC→F0→共享前端→DDR.S0 流动；新增连接主要承载控制与确认。

| 类别 | 工程依据 | 本轮设计职责 |
|---|---|---|
| 新增同步能力 | 现有 L1D 失效与 LLC way 维护提供局部机制 | 范围匹配、冲突访问协调、回填／替换排空、维护确认与搬运准入 |
| 既有可靠性缺口 | LLC 写回路径未使用 B 响应内容，flush 完成链按描述符计数 | 补齐错误检测与报告，并让同步服务据此判断结果；修复位置待评审 |
| 系统集成契约 | Datasheet 已列多端口、AXI4、错误中断和上电复位流程；完成与恢复细节待补充 | 确认跨口可见性、属性实际行为、错误与事务关联、运行中排空／复位范围 |

**可复用机制。** [WT missunit](../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/cache_subsystem/wt_dcache_missunit.sv)的 `DRAIN` 状态屏蔽新读 miss、继续推进写，等待 `wbuffer_empty_i && !mshr_vld_q`；进入 `FLUSH` 后，待 `flush_done` 才返回确认。这可作为排空再失效的基础。范围筛选、外部命令入口及跨层完成关联仍需扩展。Ara 专用失效依赖既定并发条件；其接收握手需与真正的维护完成区分。

`DRAIN` 排空后先返回 `IDLE`，再检查 flush 请求并进入 `FLUSH`，所以请求应保持有效或被可靠锁存。读控制器还有等待接受、取消后等待响应等状态；实现排空条件时须覆盖这些已接受请求，不能只检查 MSHR。用户已确认维护窗口和握手需要实现，具体职责如下，信号名称及编码留待接口规格确定：

| 确认阶段 | 必须确认的事实 |
|---|---|
| 命令接受 | 范围、操作和请求身份已保存；接受情况不明按可能已启动处理 |
| 上游排空 | 相关旧请求、写缓冲和回填已得到处置；排空依赖 LLC 的写时，LLC 仍可接收 |
| L1 更新完成 | 所需 L1 状态更新结束；仍保持跨层窗口的冲突访问限制 |
| LLC 维护完成 | 所需清理／失效和相关在途事务结束，错误状态已汇合 |
| 整体同步完成 | 相关历史错误及本次错误均已处置，并满足 DDR 跨口可见性；成功后才准许依赖任务 |

这些确认按操作组织，输入 clean 可以保留干净 L1 副本；表格不要求每种操作都执行 L1 失效。失败时转入第 6 章的资源保留与恢复流程。

[LLC config](../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/axi_llc_config.sv)已有按 way 隔离入口、等待在途事务并维护的流程。按范围操作、独立 clean／invalidate、SPM 保护与局部仲裁属于目标服务的实现工作。当前 FENCE 的提交条件包含 WT 写缓冲为空，见 [CVA6 接线](../../.bender/git/checkouts/cva6-20c9d7cbe0dd6995/core/cva6.sv)；向量配置同时设置 `DcacheFlushOnFence=0`。因此屏障有助于写入排序和排空，LLC clean 仍需平台服务。现阶段可评审 MMIO 范围命令，指令入口另核对实现条件。

**等待、报错与重试。** DDR 忙、刷新或端口竞争通常通过背压和响应延迟处理，LLC 等待即可。`DECERR` 可表示地址无法译码，`SLVERR` 可表示下游不支持该访问或检测到内部异常；本次 Datasheet 第 45–49 页已列地址越界等错误中断，但这些错误怎样映射到 BRESP／RRESP、是否伴随部分写入仍待确认；不能把通用协议允许的报错方式直接当作该 IP 的实现。[AXI 规范 A3.4](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)区分成功和错误响应。已返回错误与一直没有返回响应，需要不同的故障处置。

当前 [w_master](../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/eviction_refill/axi_llc_w_master.sv)等待 B，但没有使用 `b_chan_mst_i` 中的响应内容判断成败。收到握手后继续推进，flush 描述符退出时通知 config，后者按计数结束维护。普通替换也走这条路径，这是引入 GB 前已有的错误处理缺口。旁路 B／R 经 mux／demux 返回，须单独分类；[SoC](../../hw/cheshire_soc.sv)已有上游总线错误观察点，但它只能检查实际返回到该处的响应。[回填模块](../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/eviction_refill/axi_llc_r_master.sv)也未把下游 `RRESP` 纳入回填成功判断，应一并核查错误传播。以上为静态源码事实，实际故障影响尚未注入验证。

错误可能早于同步命令：CPU 写 `x=2` 后，LLC 因普通替换写回失败，旧行随后被替换；后来同步 x 时已没有该脏行，只检查本次 clean 就可能误报成功。因此，新增错误记录必须保留跨命令影响，并在恢复确认后才能清除。无法定位受影响范围时应扩大拒绝报成功的范围。这里的“新同步清掉历史错误”是未来实现应避免的设计，当前写回路径并没有这样的错误记录／清零机制。

可以设计重试，但需保存旧地址和数据，错误时阻止后续覆盖，再重新发送并定义持续失败的退出办法。[tag store](../../.bender/git/checkouts/axi_llc-5fb8850caad4fcfa/src/hit_miss_detect/axi_llc_tag_store.sv)在普通 miss 时安装新 tag，flush 时清除旧 tag；这些动作不以写回 B 成功为前提。发送 FIFO 又随 W 握手弹出数据。B 错误刚到时旧数据可能还在阵列中，但当前没有保证它可被重新定位并重发的恢复流程。检测错误、停止旧活动、恢复有效数据各有职责，透明重试及其保存机制尚未选定。

同步成功需汇合维护完成、所需传输无错误及跨端口可见性。若发生写回错误，应阻止后续依赖任务并上报，能否保留数据重试取决于缓存及平台恢复设计。供应商手册第 14 页的属性支持表与第 23、27 页信号表存在差异；第 29 页低功耗确认、第 59–60 页上电复位顺序也尚不能直接作为运行中排空／取消旧写的保证。具体问题与页码统一见[会议问题](DDR_Supplier_Coherence_Questions.md)。接口评审还需定义范围、操作和身份，但 CSR 地址、编码及超时值尚未冻结。LR/SC／AMO 控制对象与搬运数据分行；LR/SC 序列在交接前结束。设备若需修改同一原子对象，另定义旁路写的观察范围。

## 8. 同步范围和交接频率决定维护开销

L1D 纳入探测后，主要成本来自 tag 查询、有效位更新、写缓冲排空和冲突处理。当前缓存行写入／失效与读请求共享资源，维护可能使 CPU 等待。当前向量 L1D 为 8 KiB、4 路、32 B 行，共 256 个驻留位置；旧失效机制清除索引下全部 way，还可能驱逐无关数据。定向匹配可以减少这部分重填成本。

查询策略也影响大块同步。1 MiB 输入包含 32768 个 32 B 块，逐地址探测需要检查许多未驻留地址；扫描 256 个驻留 tag 再筛选范围，可能更经济。实际周期取决于 way 的并行度、端口仲裁和在途事务，扫描期间也必须协调新增驻留。小范围则可能直接逐行查询更简单。

LLC 的脏写回同时占用缓存和 DDR 带宽，现有按 way 维护的入口隔离还会扩大 CPU 停顿范围。范围维护、提前准备下一分块、双缓冲流水和稳定权重复用，分别减少无关维护、暴露等待及重复调用。缓冲区越大，同步次数可能越少，但缓存状态扫描、搬运等待和 GB 容量约束也会变化，需要随负载测量。

| 比较项 | 统一经 DDR：本方案 | 新增缓存直供路径 |
|---|---|---|
| 脏输入供数 | LLC 写回 DDR，搬运器再读取 | 缓存向搬运端返回最新数据 |
| 连接成本 | 复用现有缓存写回和设备端口 | 增加数据响应、仲裁、背压和事务匹配 |
| 主要代价 | DDR 往返及端口竞争 | 缓存端口竞争与更复杂的验证 |

以 64 B 脏输入行为例，在前端上游逻辑接口，经 DDR 交换包含一次 64 B 写回和一次 64 B 读取；缓存直供可省去当次往返，未来的写回责任仍需处理。若输入量为 N、实际需清理的数据量为 D，前端上游逻辑数据量约为 `N + D`，按真实缓存行和传输粒度计。实际下游 DDR 字节数还包含压缩效果、元数据访问、部分块读改写及 ROI 额外读取，不能直接用该式代替外存带宽。干净输入的 D 可以为零。当前方案选择较简单的数据连接，先通过范围和调度优化降低同步成本。

后续验收应同时测正确性和开销：设备必须取得交接版本，旧脏行及迟到写必须无法覆盖结果，部分行未选中字节必须保留。用例覆盖待完成写、干净／脏副本、32/64 B 边界、跨行、并发回填／替换、多设备范围冲突，以及超时后的迟到事务。四口场景覆盖 F0→F1/F3、F1→F0/F3、F2→F0/F1/F3；普通旁路和压缩区分别检查，同压缩块部分写与元数据错误单列。上述方向表示写生产者→读消费者，不新增 F2 读或 F3 写能力。性能记录 CPU 停顿、维护时间、缓存 miss、DDR 字节数及任务尾延迟，比较小块频繁交接、大权重搬运和双缓冲负载。
