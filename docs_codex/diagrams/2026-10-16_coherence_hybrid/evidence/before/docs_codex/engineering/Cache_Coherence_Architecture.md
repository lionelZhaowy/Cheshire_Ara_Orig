# DDR–GB 缓存一致性：条件审查与架构比较

返回[工程参考](README.md) · 配套[IP/DDR/GB 契约](IP_DDR_Interface_Contract.md)

2026-10-16 修订，L01。基于 `mp/ara-pulp-v2` / `322bd6ce9` 的源码静态分析；当前阶段为方案比较，待选型与硬件验证。

**建议优先评估“不分配 LLC 行的逐行 I/O 硬件一致性”。** 它让 CPU 保持日常缓存能力，同时协调设备对共享 DDR 数据的访问。搬运边界维护可作为成本较低的候选；未来若设备增加同地址空间的私有缓存，再评估让这些缓存共同参与一致性协议。

## 1. 两个搬运方向分别需要保证什么

讨论对象是搬运事务的 **DDR 侧物理地址**。GB 是独立 SRAM，搬运描述符把 DDR 地址与 GB 地址联系起来。一次搬运是否安全，取决于相关数据的当前版本和访问次序。

| 原条件 | 更完整的处理过程 |
|---|---|
| GB→DDR：若地址被缓存，失效 LLC/L1D | 先协调目标行的写权限与在途访问，保护需要保留的旧数据，等待旧副本失效确认，再完成新数据写入与发布 |
| DDR→GB：若地址被缓存，先写回 DDR 再读 | 取得按访问顺序应见的最新版本。干净副本可以保留；脏数据可由缓存供出，或先清理到 DDR 再读取 |

这里涉及四种状态：**可缓存**是地址区域的属性，**驻留**表示缓存当前持有副本，**脏数据（dirty）**表示缓存内容比下游更新，**在途事务**则包括写缓冲、回填和替换。一次 tag 查询只反映当时的驻留情况；查询结束后，CPU 仍可能写入或重新填充该行。因此，协调机制需要保护从查询到事务完成的整个过程，安排冲突访问的先后次序。

部分行写入尤其容易出错。假设最新旧行是 `[A,B,C,D]`，设备只把第二段改为 `X`，正确结果应为 `[A,X,C,D]`。如果 A/C/D 的最新值仅在 LLC 脏行中，丢弃该行就会丢失这些值；如果先写 X、再把旧脏行写回 DDR，X 又会被 B 覆盖。

因此，**部分行更新要先保护未覆盖字节的最新值**：可以先清理旧行，再按字节选通 WSTRB 写入；也可以在受保护的缓冲中合并新旧数据。完整覆盖时，若全部新字节有效、覆盖了所有相关一致性粒度且旧事务已妥善处理，就可以省去旧数据回写。覆盖范围应按实际缓存行判断：当前向量 profile 的 L1D 行为 32 B，默认 LLC 行为 `8 × 64/8 = 64 B`；一个 AXI beat 即使所有字节都有效，也可能只覆盖其中一部分。[源码依据见第 5 节](#evidence)。

## 2. 硬件如何协调缓存与搬运

一致性硬件围绕同一物理行完成四件事：确定最新数据来源，安排访问次序，管理副本和写权限，收齐必要的完成确认。冲突请求可以等待或重试，不同地址的请求则可并行推进。目录或探测过滤器能够减少查询，但其记录必须覆盖实际持有者；采用 LLC 查询结果推断 L1D 状态时，还需有可靠的包含关系保证。

![数据存储互连与一致性协调](../diagrams/2026-10-16_cache_coherence/industrial-base/system.png)

图 1：沿用工业版底图的布局与数据连线，在空白处增加一致性协调模块；紫色为新增控制接口。[SVG](../diagrams/2026-10-16_cache_coherence/industrial-base/system.svg) · [三图可编辑 PPTX](../diagrams/2026-10-16_cache_coherence/industrial-base/export/diagrams.pptx)

普通访存沿主 Xbar、原子适配、LLC 到达 DDR 合流处。Ara 的 GB 地址分支则接入**共享数据代理**，与 NPU、ISP 和搬运器共同使用 GB 的适配、仲裁及 bank 调度。图中保留三个 DDR AXI 入口：**S0 接 SoC/LLC，S1 接 NPU/GB 搬运，S2 接图像帧 DMA**。协调模块管理设备请求准入、缓存状态和在途事务，紫色接口需在缓存侧及 DDR 接入适配中实现。主 Xbar 保持 64-bit，三口分组沿用原方案示意，具体 IP 与端口配置待评审。

缓存协调还需要与任务流程配合：

- **访问顺序。** 软件先准备并发布输入，再提交任务；设备完成结果写入后，再发布完成状态。硬件据此确定每次访问应见的数据版本，并等待必须先完成的写操作。
- **整块数据交接。** 多行数据在不同时间完成更新，CPU 可能读到不同阶段的内容。需要整帧一致视图时，可用分块所有权、版本号或双缓冲组织交接；LR/SC、AMO 的观察范围也应覆盖相关设备写。
- **GB 数据生命周期。** GB 保存本次搬运取得的数据。后续计算需要更新后的源数据时，应重新搬运；Ara 向量寄存器中的值同样通过再次加载更新。生产、消费和复用的时机由任务协议约定。

未来设备若拥有同地址空间的私有缓存，还需响应探测、交出脏数据并转移访问权限。MESI/MOESI 等状态协议用于表达这些职责，具体实现涉及缓存控制器与互连的共同配合。

## 3. 两个搬运方向中各部件的动作

![DDR 地址数据搬入 GB](../diagrams/2026-10-16_cache_coherence/industrial-base/read-to-gb.png)

图 2：根据最新数据的位置选择供数路径。缓存直接供数为候选扩展；限定从 DDR 供数时，先将脏数据清理到 DDR。[SVG](../diagrams/2026-10-16_cache_coherence/industrial-base/read-to-gb.svg)

| 情况 | L1D／写缓冲 | LLC／DDR | 搬运器／GB |
|---|---|---|---|
| DDR 已最新，相关在途事务已完成 | 保留干净副本 | 从 DDR 供数 | 接收数据，GB 写入完成后交给消费者 |
| LLC 持有最新脏行 | 协调冲突访问 | LLC 直接供数；或先 clean，等待更新对后续 DDR 读可见 | 沿选定路径取得该版本并写入 GB |
| CPU 有按顺序必须先完成的写 | 建立发布顺序，等待相关写排空 | 协调回填与替换，确定最新来源 | 完成搬运后发布 GB ready |

![GB 数据写入 DDR](../diagrams/2026-10-16_cache_coherence/industrial-base/write-to-ddr.png)

图 3：完整行覆盖与部分行更新都经历“协调—确认—发布”，部分行更新还需保留未覆盖的旧字节。[SVG](../diagrams/2026-10-16_cache_coherence/industrial-base/write-to-ddr.svg)

| 情况 | L1D／写缓冲 | LLC／DDR | 搬运器／GB |
|---|---|---|---|
| 完整行覆盖 | 排序在途写，失效旧副本并确认 | 满足完整覆盖条件时丢弃旧内容，提交新行 | 备妥全行数据，等待约定完成 |
| 部分行更新 | 排序在途写，失效旧副本并确认 | 保护未覆盖字节，完成失效后合并或按选通更新 DDR | 提供地址、长度和字节有效掩码 |
| 并发读、回填、替换 | 对过期回填作废或重试 | 协调点安排冲突事务顺序 | 按事务身份确认实际完成范围 |

这些操作需要配套流控：接收请求、占用行资源和等待响应的顺序应避免循环等待。任务完成条件则要明确如何汇合 AXI B 响应、失效确认和数据可见，再发出 IRQ。出现超时或写错误时，按部分完成处理：记录事务身份和已完成范围，暂停复用相关 GB/DDR 缓冲；确认迟到事务已排空，或完成受控复位后，再恢复使用。

## 4. 架构比较与本项目建议

| 维度 | 搬运边界硬件维护 | 逐行 I/O 硬件一致性 | 所有缓存代理参与的互连 |
|---|---|---|---|
| 并发与 CPU 影响 | 交接范围内排他访问；粗粒度维护可能扩大停顿 | 冲突行短期等待，不同行可并发 | 支持多个私有缓存，承担共享迁移开销 |
| DDR 流量 | 脏数据通常先写回，再搬运读取 | 缓存供数可减少往返；清理式实现仍有回写 | 缓存间可转移数据，收益取决于共享模式 |
| LLC 污染 | 旁路搬运可不分配，维护会影响缓存驻留 | 设备请求不分配，仍探测既有行 | 分配策略需单独设计 |
| 改动与验证 | 范围维护、排空、访问隔离和完成协议 | 逐行探测、响应/数据、冲突处理与公平性 | 增加设备缓存状态、权限转移及更多代理组合 |
| 适用条件 | 分块交接明确，允许传输期排他 | CPU 保持缓存，设备高效共享 DDR | 设备持有同地址的硬件缓存副本 |

**逐行 I/O 一致性最值得优先评估**，因为它兼顾 CPU 缓存效率、设备旁路流量和 GB 显式搬运。搬运边界维护适合交接清晰、成本受限的实现；完整缓存代理互连则面向设备拥有私有缓存的扩展需求。三种方案均需任务级同步。

设计时要分别确定三项能力：设备访问是否分配 LLC 行，如何探测 LLC/L1D，以及是否允许缓存直接供数。前两项决定缓存占用和协调方式，第三项涉及新增数据路径。目前仍需评审缓存供数；若设备数据始终经 DDR，则采用 clean 后旁路读取，并计入额外 DDR 流量。

事务语义可参考 ACE-Lite 的 `ReadOnce`、`WriteUnique`、`WriteLineUnique`：无私有缓存的设备也能发起一致性访问，部分写与整行覆盖采用相应处理。探测、权限与确认由一致性互连及缓存侧实现，下游 DDR Controller 可以继续使用普通 AXI4 接口。[Arm IHI 0022H，D3.1、D6.7、D11](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)

当前工程可复用的机制与需要扩展的职责如下：

| 部件 | 当前机制 | 候选新增／修订职责 |
|---|---|---|
| CVA6 L1D 与 Ara | WT、写缓冲、pending/barrier、Ara 写失效 | 支持普通访问与回填并发的探测；处理冲突、清除旧副本后返回完成确认 |
| LLC | WB、tag/dirty、回填/替换与 way 维护 | 按地址查询、保留/供出脏数据、失效确认及冲突仲裁 |
| 设备入口与协调点 | AXI 通道与 ID 机制 | 访问类型、共享属性、字节有效性及事务身份；统一协调相关访存路径 |
| 原子与软件 | LLC 前原子适配、MMIO/IRQ | 将设备冲突写纳入 reservation/AMO 观察范围，或隔离共享原子域；驱动定义发布、完成与恢复 |
