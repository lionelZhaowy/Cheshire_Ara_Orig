# DDR–GB 缓存一致性：条件审查与架构比较

返回[工程参考](README.md) · 配套[IP/DDR/GB 契约](IP_DDR_Interface_Contract.md)

2026-10-15，L01 源码分析；输入 `mp/ara-pulp-v2` / `322bd6ce9`。本文比较方案，不冻结选型；仅静态核对，未实现或运行硬件。主 Xbar 保持 64-bit、设备 DDR 数据旁路、GB 为独立 SRAM 的既定需求保留。

**建议优先评估“不分配 LLC 行的逐行 I/O 硬件一致性”，同时保留搬运边界维护作为成本较低的候选。** 完整性取决于所有相关访问是否被协调，不取决于协议名称；只有未来设备也保存同一物理地址的硬件缓存副本，才需要把它升级为可被探测的缓存代理。

## 1. 两条条件抓住了什么，还缺什么

讨论对象是**搬运事务的 DDR 侧物理地址**。GB 地址是另一处 SRAM 地址，二者通过搬运描述符关联，不是同一物理位置的别名。

| 原条件 | 审查后的准确条件 |
|---|---|
| GB→DDR：若地址被缓存，失效 LLC/L1D | 先协调同一行的访问，处理在途写、回填与脏数据，等待旧副本失效确认，再让新写成为可见版本；不能只在写完后 invalidate |
| DDR→GB：若地址被缓存，先写回 DDR 再读 | 必须取得按访问顺序应见的最新版本。干净副本不需写回；脏数据可以由缓存供数，也可以先 clean 到 DDR 再读 |

“可缓存”是区域属性，“驻留”是当前是否存在副本，“dirty”表示缓存比下游更新，“在途”包括写缓冲、回填和替换。**缓存查询未命中，不等于不存在更新数据或即将形成的副本。** 软件不应靠事先查询一次 tag 决定安全性；硬件协调必须覆盖查询到事务完成的竞争窗口。

GB→DDR 还要区分覆盖范围。例如最新旧行是 `[A,B,C,D]`，设备只写第二段 `X`，结果必须是 `[A,X,C,D]`。若 A/C/D 仅在 LLC 脏行中，直接丢弃该行会丢数据；先让设备写 DDR、随后再清理旧脏行，又可能把 X 覆盖掉。

**部分行更新须先保留最新的未覆盖字节。** 可先 clean 旧行再按 WSTRB 写，也可在受保护缓冲中合并。只有覆盖完整一致性粒度、全部新字节有效且旧事务已协调，才可能直接丢弃旧内容。一个满选通 AXI beat 不一定是一整行：当前向量 profile 的 L1D 行为 32 B；默认 LLC 行为 `8 × 64/8 = 64 B`，跨层粒度必须对齐。[源码依据见第 5 节](#evidence)。

## 2. 完整硬件一致性要负责哪些事

硬件需为同一物理行协调读写次序、确定最新数据来源、管理副本与写权限，并处理失效确认、回填、替换及在途事务。目录或探测过滤器可以减少查询，但不能漏掉真实持有者；LLC 未命中也不能在未证明包含关系时推出 L1D 未命中。不同地址仍可并行。

![系统与一致性边界](../diagrams/2026-10-15_cache_coherence/system.png)

图 1：推荐评估方向的逻辑结构；虚线框为新增或需扩展职责。协调点的位置不代表只在 LLC 出口加桥即可完成设计。[SVG](../diagrams/2026-10-15_cache_coherence/system.svg) · [三图可编辑 PPTX](../diagrams/2026-10-15_cache_coherence/export/diagrams.pptx)

有三条边界需要保持清楚：

- **一致性不等于顺序。** 发布输入、提交任务、写结果和通知仍需约定排序；不要求外部读观察到尚未按协议发布的任意 CPU 写。
- **逐行协调不等于整块原子更新。** CPU 可能先后观察到不同数据行的不同阶段；整帧快照需分块所有权、版本或双缓冲。LR/SC、AMO 还需覆盖所有冲突写的观察域。
- **GB 不是 DDR 的透明缓存。** 搬入后是显式快照，CPU 后来修改源 DDR 地址不会自动更新 GB；Ara 已装入向量寄存器的数据也不会自动刷新。GB 的生产、消费、复用仍由任务协议管理。

若未来设备使用同地址空间的私有缓存，完整互连还要支持该缓存被探测、交出脏数据和转移权限；MESI/MOESI 一类状态协议服务于这些职责，不是给现有 AXI 端口加几个状态位就能成立。

## 3. 两个搬运方向中各部件的动作

![DDR 地址数据搬入 GB](../diagrams/2026-10-15_cache_coherence/read-to-gb.png)

图 2：按共享地址的版本状态选择数据来源。缓存供数为候选扩展；严格限定从 DDR 供数时使用 clean 后读取路径。[SVG](../diagrams/2026-10-15_cache_coherence/read-to-gb.svg)

| 情况 | L1D／写缓冲 | LLC／DDR | 搬运器／GB |
|---|---|---|---|
| 无更新副本或在途冲突 | 干净副本可保留 | DDR 可供数，无须无条件 flush | 接收本次读取结果，GB 写完成后才可消费 |
| LLC 持有最新脏行 | 协调冲突访问 | LLC 供数；或先 clean，等待后续读能见更新 | 取得相同版本，不重复读取旧 DDR |
| CPU 有必须先完成的写 | 建立发布顺序，等待相关写排空 | 协调接收、回填与替换，确定最新来源 | 不提前发布 GB ready |

![GB 数据写入 DDR](../diagrams/2026-10-15_cache_coherence/write-to-ddr.png)

图 3：完整行覆盖与部分行更新共享“协调—确认—发布”主线，差别在于是否需要旧字节。[SVG](../diagrams/2026-10-15_cache_coherence/write-to-ddr.svg)

| 情况 | L1D／写缓冲 | LLC／DDR | 搬运器／GB |
|---|---|---|---|
| 完整行覆盖 | 排序在途写，失效旧副本并确认 | 满足完整覆盖条件时可丢弃旧脏内容；提交新行 | 备妥全行数据，等待约定完成 |
| 部分行更新 | 同上，不能让旧写迟到 | 保护未覆盖字节，再失效、合并或按选通更新 DDR | 明确地址、长度和字节有效掩码 |
| 并发读、回填、替换 | 不允许旧回填在失效后重新生效 | 由协调点串行化或重试冲突事务 | 完成状态对应确定任务，不把排队当完成 |

硬件必须在协议允许的阶段接收新请求并施加背压，避免持有行资源却等待一条被自己阻塞的响应。B 响应、失效确认、数据可见和 IRQ 是不同事件；任务完成条件要把必要事件连接起来。失败不自动回滚：超时或写错误后保留错误身份与部分完成范围，停止复用相关 GB/DDR 缓冲，排空或受控复位后再恢复。

## 4. 架构比较与本项目建议

| 维度 | 搬运边界硬件维护 | 逐行 I/O 硬件一致性 | 所有缓存代理参与的互连 |
|---|---|---|---|
| 并发与 CPU 影响 | 交接范围内禁止冲突访问；现有粗粒度维护可能扩大停顿 | 冲突行短期协调，不同行可并发 | 可支持多个私有缓存；冲突与共享迁移仍有代价 |
| DDR 流量 | dirty 通常先写回，再搬运读取 | 可由缓存供数，减少往返；清理式实现仍有回写 | 可转移缓存数据；并非天然最省带宽 |
| LLC 污染 | 旁路搬运可不分配，但维护会损失缓存驻留 | 设备请求不分配，仍查询/协调既有行 | 分配策略需另外设计 |
| 改动与验证 | 范围维护、排空、访问隔离与完成协议 | 逐行探测、响应/数据、在途冲突与公平性 | 再增加设备缓存状态、权限转移和更多代理组合 |
| 适用条件 | 分块交接明确、允许传输期排他 | CPU 保持缓存，设备需与其高效共享 DDR | 设备确实保留同地址的硬件缓存 |

**优先评估第二列**：它符合 CPU 保持缓存、设备流量不污染 LLC、GB 显式搬运的目标。第一列适合交接清楚且成本受限的实现；第三列不应仅因名字“最完整”就成为默认选项。三者都要处理任务级同步。

必须分开评审：①设备访问不分配 LLC；②探测 LLC/L1D；③由缓存直接供数。②是协调职责，③可能新增数据通路。现有“绕过 LLC”的用户要求不能自动解释为批准③；若严格要求设备数据只经 DDR，就采用协调 clean 后旁路读取，并承担额外流量。

标准可参照 ACE-Lite 的 `ReadOnce`、`WriteUnique`、`WriteLineUnique` 语义：设备本身无需成为缓存持有者，也能发起一致性访问；部分写与整行覆盖有不同要求。**普通 AXI4 DDR Controller 仍可位于一致性域下游，但 AXI4 桥本身不提供这些语义。** 协议与实现选型仍待评审。[Arm IHI 0022H，D3.1、D6.7、D11](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/IHI0022H_amba_axi_protocol_spec.pdf)

当前需要补足的接口职责如下，不在此指定编码或寄存器偏移：

| 部件 | 当前可复用事实 | 候选新增／修订职责 |
|---|---|---|
| CVA6 L1D 与 Ara | WT、写缓冲、pending/barrier、Ara 写失效 | 能与普通读写、回填并发的探测/确认接口；失效接收不冒充全部动作完成 |
| LLC | WB、tag/dirty、回填/替换与 way 维护 | 按地址协调查询、保留/供出脏数据、失效确认及冲突仲裁 |
| 设备入口与协调点 | 已有 AXI 通道与 ID 机制 | 共享属性、访问类型、字节有效性、事务身份；协调所有相关路径，限制未纳管的旁路 |
| 原子与软件 | LLC 前原子适配、MMIO/IRQ | 设备冲突写纳入 reservation/AMO 顺序，或明确禁止共享原子域；驱动定义发布、完成、错误恢复 |
