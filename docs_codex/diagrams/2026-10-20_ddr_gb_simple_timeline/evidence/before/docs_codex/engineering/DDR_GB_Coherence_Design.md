# DDR–GB 数据同步设计：从裸机推理到缓存维护

返回[工程参考](README.md) · [供应商会议问题](DDR_Supplier_Coherence_Questions.md) · [评审与答疑 Q&A](../maintenance/L01/reviews/ddr_gb_coherence_review_qa.md) · [图稿与可编辑源](../diagrams/2026-10-20_ddr_gb_coherence_v1/README.md)

本文说明：**软件选择数据交接的范围和时机，硬件排空相关事务、维护缓存，并确认下一使用者能读到正确数据。**

2026-10-20，L01；依据 [SoC 架构 v1](SoC_Architecture_v1_Master_Plan.md)，输入 `mp/ara-pulp-v2` / `c9abbb48`。新增 GB、四口 DDR 共享压缩前端和范围维护服务仍待实现及验证；文中 HAL 是概念接口。

## 1. CPU 与设备通过 DDR 交接数据

一次推理从 CPU／Ara 准备输入开始：先把最新输入同步到 DDR，再搬入 GB 供 NPU 计算；结果从 GB 搬回 DDR，完成输出同步后，CPU 读取并进行后处理。同步发生在双方交接数据时，CPU 在其他时间正常使用缓存。

这条流程涉及三种不同的存储对象：

| 对象 | 含义 |
|---|---|
| DDR 输入／输出区 | 软件分配的 DDR 地址范围。输入区供设备读取，输出区接收设备结果，两者在本文示例中分开 |
| WT 写缓冲 | CVA6 的 L1D 内部硬件结构，保存尚待处理的写入及其状态，由硬件管理 |
| GB | 独立片上 SRAM，保存操作数、中间结果和待搬出的输出，由任务调度安排使用 |

图 1：SoC v1 一致性专题图。蓝／绿线表示数据连接，紫线表示维护控制与确认；维护服务是待实现的逻辑职责。[SVG](../diagrams/2026-10-20_ddr_gb_coherence_v1/figures/system.svg) · [三页可编辑 PPTX](../diagrams/2026-10-20_ddr_gb_coherence_v1/export/design/diagrams.pptx)

CPU 的普通 DDR 访问经过 L1D、主 Xbar 的 M2、原子适配与 LLC，再进入共享压缩前端 F0。设备绕过 LLC：GB 搬运读写走 F1，帧写入 DMA 走 F2，ROI 帧读取 DMA 走 F3，并将读出的像素送往 LVDS TX。前端 F0–F3 分别接一个 DDR Controller 的 DDR.S0–S3；F2 接收写响应，F3 接收读数据，方向保持不变。

CPU 与 Ara2 是 Xbar 的独立输入，共享 M5→GB 适配／仲裁→SRAM 的本地路径。该路径不经过 LLC，非缓存属性仍须实际配置。本地数据交接见第 7 章；以下先讲经 DDR 的推理流程，假定 DDR 已就绪，所需 LLC cache way 已配置，SPM 驻留内容受到保护。

## 2. 缓存副本使双方看到不同版本

三个短例子说明同步要解决的问题：

- **设备读到旧输入。** DDR 中 `x=1`，CPU 写入 `x=2`。新值可能还在 WT 写缓冲中，CPU 已能通过前递读到 2；即使写缓冲排空，新值也可能停在写回型 LLC 的脏行中。设备绕过 LLC 读 DDR，仍得到 1。
- **CPU 命中旧输出。** CPU 缓存中留着 `y=0`，设备把 DDR 更新为 `y=9`。CPU 若命中旧副本，仍读到 0。干净行也会过期：“干净”只表示没有待写回的 CPU 修改。
- **旧脏写覆盖设备结果。** LLC 留着 CPU 先前写入的 `y=3`，设备随后写 DDR 为 9。若这条旧脏行以后才写回，结果又被覆盖为 3。因此设备写入前也要准备输出区。

![三种缺少同步时的数据版本变化](../diagrams/2026-10-20_ddr_gb_coherence_v1/previews/versions.png)

图 2：三个独立的数据版本示例。DDR 框表示逻辑数据，省略共享前端和压缩布局；L1D 阵列与写缓冲分栏展示，便于区分状态。[SVG](../diagrams/2026-10-20_ddr_gb_coherence_v1/figures/versions.svg)

以下术语分别描述不同动作：

| 术语 | 本文含义 |
|---|---|
| 排空 | 推进已接受的相关事务，并等其完成。排空写缓冲要送出写入，直接清零会丢数据 |
| clean（清理） | 把脏数据写到约定的共享位置，可以保留干净副本。本方案最终要求对 DDR 消费端口可见 |
| invalidate（失效） | 清除缓存副本的有效状态，使后续读取重新取数；脏数据须先按交接方向处理 |
| flush | 缓存维护语境中通常指 clean 后 invalidate，具体接口须明确动作及完成点 |
| fence（屏障） | 约束前后访问的顺序。当前 CVA6 的 FENCE 提交还等待 WT 写缓冲为空，但不能代替 LLC clean |

WT（写直达）描述 L1D 向下传递写入的方式，WB（写回）LLC 则可暂存脏数据。因而“CPU 已完成赋值”“写缓冲已排空”和“DDR 设备端口可见”是不同阶段。

## 3. 软件选择交接范围，硬件完成维护

软件知道谁生产、谁消费，以及何时交换角色。交接前，软件等待 CPU／Ara 的生产工作结束，停止对目标范围的新访问；中断代码和其他参与者也遵守约定。设备持有期间，CPU 可以处理独立数据。若计算中途需要 CPU 后处理，再交回 NPU，那次角色交换就是新的同步点。

硬件负责此前已经接受的读写、回填和替换。每次维护建立一个**维护窗口**：限制新的冲突请求，允许旧事务及其数据、响应继续前进，完成排空和缓存状态更新后再返回确认。依赖 LLC 的上游写入排空时，LLC 必须保持接收，否则双方可能互相等待。实现可按范围协调，也可采用短暂全局停顿，两者都须保证旧事务能够完成。窗口结束后，软件继续维持设备使用期间的访问约定；若要由硬件拦截全部违规访问，还须覆盖 L1D 命中路径。

维护范围向外覆盖完整缓存行，包括搬运范围外的邻接字节。当前 L1D 行为 32 B，默认 LLC 行为 64 B；输入、输出和仍在修改的栈、锁等对象应按共同维护粒度隔离。两个数组即使字节范围不重叠，共享一条行时仍会相互影响。搬运器只传实际数据长度，不能把维护取整后的范围直接当作搬运长度。

维护地址采用前端上游、软件可见的 DDR 物理地址；相对于压缩存储布局，它是逻辑地址。压缩后的数据位置和元数据由前端管理。**缓存行保护由同步服务负责，同一压缩块内的部分写和元数据竞争由前端负责**，两种粒度不能混用。LR/SC／AMO 控制对象与搬运数据分行，已有 LR/SC 序列在交接前结束；设备修改共享原子对象需另行定义观察范围。

## 4. 输入同步让设备读到最新数据

CPU／Ara 完成输入计算后，软件交出输入范围。硬件先把写缓冲中的相关写入推进到 LLC，再清理 LLC 脏行。确认搬运器能够读到新值后，才允许 DDR→GB 搬运；干净的输入副本可以保留。

具体顺序是：先按第 3 章建立维护窗口、排空上游写入，再对 LLC 进行所需隔离与清理。脏行沿 F0→共享前端→DDR.S0 写回；没有待写回更新的行可省去数据传输。先隔离 LLC 再等上游排空，既可能遗漏更新，也可能阻塞写入完成。

“可见”指后续目标端口读取同一地址能得到新值。GB 搬运器从 F1 读取，帧输出 DMA 从 F3 读取。普通旁路区需确认原样转发的写入成功；压缩区还需确认数据和元数据已关联发布。同步成功汇合缓存、前端和 Controller 的完成及错误结果。

若既有成功响应及契约已经保证跨口可见，就直接使用；不足时再确定补充依据。Controller 可以通过排序或转发保证读取新值，无须等待 DRAM 单元实际写入。供应商负责 Controller 边界，项目负责前端及通知路径；具体待答复事项见[供应商问题](DDR_Supplier_Coherence_Questions.md)。

同步成功后才发布搬入任务，GB 装入完成后才允许 NPU 消费。输入保持不变且使用约定持续有效时，可减少重复同步；CPU 为下一轮修改输入后，则要重新交接。

## 5. 输出写前准备，写后同步

**写前准备**处理设备即将写入的输出范围：排空旧写，clean 脏数据，再 invalidate 旧副本，并处理相关回填和替换。这既排除了以后覆盖设备结果的旧写，也保住设备不会修改的邻接字节。

例如，一行 DDR 为 `[1,2,3,4]`，LLC 最新内容为 `[10,2,30,4]`，设备只把第二段改成 9。先 clean，再按有效字节写入，得到 `[10,9,30,4]`。直接丢弃脏行会丢失 10、30；保留旧脏行则可能把设备写入的 9 覆盖成 2。基线对完整行也使用同样的准备流程。

**写后同步**从结果搬出完成开始。NPU 算完时结果还可能在 GB，必须等搬运写入成功，并满足第 4 章的前端／Controller 可见性条件，确保 CPU 经 F0 能读到新结果。随后再次限制冲突请求，处理已有读响应和回填，最终失效输出范围在 L1D／LLC 中的副本，收齐确认后才交还 CPU。CPU 消费完整输出前须等整个任务成功，不能凭某一行的响应提前读取张量。

这里先处理回填、再最终失效，是为了避免旧响应重新装入缓存。例如读请求已取得旧值，响应被暂存，设备更新 DDR 后该响应才到达；它仍携带原来的数据。这是条件性竞争，具体路径是否允许全部交错仍待验证。完整的写前排空可排除对应的交接前请求，写后维护处理其余允许发生的在途访问。

写后若发现冲突脏数据，应进入错误处理，保留现场，避免把旧值 clean 到设备结果之上。软件使用约定和事务控制还须防止违规旧写提前覆盖结果；最终失效只能清除缓存副本，无法修复已经发生的覆盖。

## 6. 裸机程序串起完整推理

示例采用单任务、轮询及独立输入输出，向外取整后的维护范围也互不重叠。基线一次预留所需资源，避免持有部分缓冲区再等待另一块。首次维护前建立上下文，记录 DDR／GB 资源、传输与维护范围、请求身份及阶段。以下为概念伪代码，`limit` 是各阶段等待预算。

```c
int infer_one_block(void)
{
    context *ctx = reserve_context_and_buffers();
    int rc;
    if (!ctx) return NO_MEMORY;
    prepare_input(ctx->in.cpu_ptr);
    rc = wait_input_producers(ctx, limit);
    if (rc) goto failed;
    rc = sync_input_for_device(ctx, limit);
    if (rc) goto failed;
    rc = prepare_output_for_device(ctx, limit);
    if (rc) goto failed;
    /* HAL 登记提交状态，再发布参数与启动命令。 */
    rc = submit_inference(ctx, limit);
    if (rc) goto failed;
    rc = wait_result_visible(ctx, limit);
    if (rc) goto failed;
    rc = sync_output_for_cpu(ctx, limit);
    if (rc) goto failed;
    consume_output(ctx->out.cpu_ptr);
    release_after_success(ctx);
    return 0;
failed:
    quarantine_context_and_buffers(ctx, rc);
    schedule_recovery(ctx); /* 上下文继续存活，恢复后才释放 */
    return rc;
}
```

输入同步处理输入区，输出准备处理另一块输出区；输入 clean 并不等于输出已准备好。输出准备只需在设备写入前完成，图中为便于展示提前放在启动阶段。若之前已经准备且保护条件持续成立，可以复用该状态。

HAL 用编译器屏障及适当的 FENCE 排序数据、描述符和 MMIO 启动命令。描述符放在 MMIO 或经验证的非缓存存储中；使用可缓存描述符时另行同步。每次等待同时检查完成和错误，失败进入第 8 章的恢复流程。

| 交出输入、准备输出 | 6 | LLC→前端／DDR：经 F0 写回脏数据，检查聚合响应及错误 |

| 等待准备成功 | 8 | 服务→CPU：返回成功、退出维护窗口，软件继续保持范围使用约定 |
| 提交推理 | 9 | CPU→任务控制：提交搬入、计算、搬出任务，确认接受及身份 |

| 等待结果可见 | 12 | 任务控制→CPU：确认任务成功、结果对 F0 可见；CPU 随后申请输出同步 |
| 交回输出 | 13 | CPU→服务：提交输出范围，再次限制冲突新请求 |
| 交回输出 | 14 | 服务→L1D：处理相关旧响应／回填，再最终失效输出副本 |
| 交回输出 | 15 | 服务→LLC：协调相关在途事务，再最终失效；冲突脏数据进入错误处理 |
| 读取并后处理 | 16 | 服务→CPU：收齐确认且无错误，允许读取输出；实际读取发生在图后 |

箭头包含命令、确认和数据传输，各箭头并非独立 HAL 调用。“前端／DDR／搬运器”泳道合并跨模块动作，部分返回确认并入整体完成；表中条件是目标服务的实现要求。

## 7. 其他数据交接复用相同原则

LVDS 输出同样遵循“生产完成、交接、消费”，按实际生产者选择维护动作：

| 场景 | 交接动作 |
|---|---|
| CPU 修改 DDR 帧后交给 F3 输出 DMA | 按输入流程排空并 clean，经 F0 发布成功、F3 可见后启动读取；干净副本可保留 |
| 设备经 F2 写帧或 F1 搬出，再交给 F3 | 写前排除目标范围的旧缓存写；数据／元数据发布成功、F3 可见后再读。未涉及 CPU 缓存的区域，无需机械增加缓存维护 |
| 输出后 CPU 再访问帧 | 等待相应使用权交接；帧若此前由 F1/F2 修改，CPU 读取前失效旧副本。F3 只读，本身不会使副本过期 |

源帧保留到所有相关读取结束，包括其他 CPU／NPU 读者。DMA 读完、FIFO 消费完和 TX 发完是不同状态；只有数据已完整复制、后续无需重读或重发源帧时，才可在 TX 结束前释放源帧。帧末或单个响应不能替代整个任务完成。

GB 本地交接由任务调度安排使用权：生产者写入对消费者可见后，才让消费者访问；全部使用者退出后，才允许覆盖复用。CPU／Ara 经 M5、NPU／ISP 经共享访问逻辑交换驻留 GB 的数据时，在非缓存映射成立的前提下，重点是访问仲裁和完成顺序，无需套用 DDR 往返流程。分区是否允许并行使用由调度与端口能力决定。

eMMC 参数仍分两阶段装入：DDR 就绪后先 eMMC→DDR，运行时再 DDR→GB。两阶段分别确认完成，后者按实际缓存状态执行输入同步。

## 8. 可靠完成后才能消费和复用资源

**接受、完成、成功是三个判断。** 接受表示命令和身份已保存；完成表示规定动作已经结束；成功还要求无影响本次数据的错误，并满足所需可见性。提交状态不明时按可能已启动处理，保留上下文并追查原请求。每个阶段只有满足自己的成功条件，才能启动依赖它的下一阶段。

下游忙或刷新通常表现为背压和延迟，可以继续等待；错误响应则需要报错。一直没有响应时，由等待预算和恢复流程处理。能检测到错误，也不等于仍保有可重发的旧数据。

超时只说明软件等待预算耗尽。例如任务 A 尚有写入在队列中，软件就把同一 DDR 地址交给任务 B，A 的迟到写仍可能覆盖 B。错误或超时后，应停止新增任务、保留上下文及 DDR／GB 资源，等待旧活动结束，或通过经验证的停止／隔离／复位流程阻止其继续访问。只停止源端发请求还不够，下游已接受事务也须处理；任务编号只能识别迟到通知，不能阻止迟到写。

确认旧事务结束或有效隔离后，资源才可复用。继续使用原数据还须检查完整性，必要时从可靠来源重建；复位不会恢复半份输出。恢复也超时时，继续保留资源并上报平台故障。透明重试及数据保存方式尚未选定。

维护应自主完成，不能依赖被它阻塞的 CPU 回调。实现时核查轮询代码、栈、状态接口和计时器的访问路径：LLC 入口隔离位于 cache／SPM／旁路分流之前，即使保留 SPM 内容，也可能暂时挡住栈访问。正常情况下维护完成后 CPU 恢复执行；CPU 无法运行时，软件轮询不能单独提供故障处理的硬时间上界。是否需要独立恢复主体取决于产品要求。

当前已有部分基础：WT 全缓存 flush 可参考其先排空、再失效的机制；LLC 已有按 way 维护；FENCE 的提交等待包含 WT 写缓冲为空，向量配置为 `DcacheFlushOnFence=0`。通用范围入口、范围筛选、跨层确认和搬运准入仍需实现，Ara 专用失效入口也不能直接代替这些职责。源码依据见[架构规划第 5 章](Cache_Coherence_Architecture.md#5-源码依据验收与待定接口)。

既有 LLC 写回路径等待 B 握手，却未使用响应内容判断成败；普通替换也经过该路径，flush 完成计数因此不能独自证明写回成功。这是新增 GB 前的静态源码发现，系统级错误传播、修复位置及实际故障影响仍待核查。错误还可能早于本次同步：先前替换写回失败后，相关行可能已不存在，本次 clean 无错误仍不能保证数据正确。实现须保留历史错误的影响，恢复确认后才能清除；无法定位时扩大拒绝报成功的范围。

详细排空条件、回填错误传播与重试分析见[评审 Q&A](../maintenance/L01/reviews/ddr_gb_coherence_review_qa.md)，前端及供应商边界见[IP／DDR 契约](IP_DDR_Interface_Contract.md)。维护开销与路径比较见[架构规划第 4 章](Cache_Coherence_Architecture.md#4-维护开销与数据路径取舍)；其中 `N＋D` 是逻辑数据量，实际 DDR 流量另计压缩、元数据及部分块处理。CSR、编码、超时值和恢复策略尚未冻结，本次文档检查不替代硬件构建、仿真、板测或故障注入。
