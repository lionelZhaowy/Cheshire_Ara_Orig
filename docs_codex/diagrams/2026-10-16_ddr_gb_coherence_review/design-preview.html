DDR–GB 数据同步设计：从裸机推理到缓存维护

本文沿一次裸机推理解释本项目的数据同步方案：软件指定要交接的 DDR 数据范围；硬件推进 L1D 内部写缓冲中的相关写入，并维护 L1D／LLC 的缓存副本，使缓存与 GB 通过 DDR 交换正确的数据。 CPU 在其他时间正常使用缓存。

1. 一次裸机推理由 CPU、搬运器和 NPU 共同完成

设 CPU 要对一块输入数据执行推理。程序在 DDR 中准备输入缓冲区 input，为结果预留输出缓冲区 output。NPU 的计算单元从片上 GB 取得操作数，因此任务还包括两次搬运：先把输入从 DDR 装入 GB，再把 GB 中的结果写回 DDR。CPU 最后读取 output，继续后处理。

这里的输入／输出缓冲区，是软件为数据预留的一段内存，例如经链接脚本或分配器安排在 DDR 中的输入数组。“缓冲区”描述它的用途，底层存储仍是 DDR。本文涉及的三个相近名称各有明确对象：

名称 保存什么 所在位置与访问方式
输入／输出缓冲区 张量、图像块或计算结果 本文示例中位于 DDR，软件用指针访问，设备按地址搬运
WT 写缓冲（write buffer） CPU 写操作的地址、数据及处理状态 CVA6 的 WT L1D 内部，由缓存硬件管理
Global Buffer（GB） 搬入的操作数、中间结果和待搬出的输出 规划中的独立片上 SRAM，经共享数据代理访问

软件缓冲区的地址范围决定同步对象。CPU 访问这些地址时，相关数据可能暂存在写缓冲中，或形成 L1D／LLC 副本；维护服务处理的正是这些硬件状态。

这段程序从 main() 看是“准备数据、调用推理、使用结果”；从硬件看，则涉及 CPU 访存、缓存、DDR 控制器、搬运器和 GB。CPU 的普通 DDR 访问经过 L1D、主互连和 LLC。设备通过 DDR 控制器的独立端口搬运，流量绕过 LLC。两条路径在 DDR 子系统汇合，因此双方交换数据时需要先约定哪一份数据有效。

裸机程序同样会遇到这一问题。C 语言的数组赋值最终产生 CPU 的 load／store 指令，是否命中缓存由硬件配置和地址属性决定，与有没有操作系统是两件事。程序中的指针告诉 CPU 访问哪个地址；设备任务里的地址告诉搬运器去哪里取数。两个地址对应同一块 DDR，只是数据交换的起点，后续还要保证两条路径看到相同版本。

图中 GB 是独立 SRAM，拥有自己的存储位置。DDR 的输入地址和 GB 的装入位置由搬运任务关联，GB 内的数据随后由计算调度使用。Ara 与 NPU 交换已经驻留 GB 的中间结果时，可以在本地安排生产者与消费者；只有需要通过 DDR 与 CPU 缓存路径交换数据时，才进入本文的同步流程。

本文先讨论输入、输出分离的一次任务，默认启动阶段已使 DDR 可用，并已配置需要使用的 LLC cache way。LLC 阵列也承担 SPM，启动栈等驻留内容应由平台保留。系统连接的需求依据见IP／DDR／GB 契约，运行时缓存状态则由具体平台初始化决定。

2. CPU 与设备可能读到同一地址的不同版本

写缓冲是 L1D 的内部硬件结构。 当前 wt_dcache.sv实例化了 i_wt_dcache_wbuffer；向量配置将 CVA6ConfigWtDcacheWbufDepth 设为 8，即八个条目。模块中的 wbuffer_q 保存数据及状态，通过 always_ff 更新，在 RTL 中表现为寄存器状态数组及配套控制逻辑。它封装在 CVA6 内部，没有供软件直接寻址的独立存储区，因此 SoC 顶层图只在 CVA6 框中标注“L1D／写缓冲”。图 2 为便于跟踪数据，将 L1D 阵列与写缓冲分栏展示。

先看输入中的一个数 x。DDR 初值为 1，CPU 把它改成 2。当前向量配置采用 WT（write-through，写直达）L1D：store 的更新进入写缓冲，再送往下层。这个版本允许后续 load 从写缓冲前递新值；写应答返回后，再按命中状态更新 L1D 阵列。因此，在图 2 的第一个时刻，L1D 阵列还可以保存 1，CPU 读取却能通过前递得到 2，而 DDR 仍保存 1。写缓冲让 CPU 与总线传输解耦，也说明“CPU 已能读回自己写的新值”与“设备已能从 DDR 读到新值”有不同的完成条件。写缓冲实现的开头说明及写应答处理对应这一过程。

写缓冲排空后，新值进入下层存储路径。这里还有一个 WB（write-back，写回）LLC：它可以接收更新，把对应缓存行标为脏行，等替换或清理时再写往 DDR。此时 LLC 保存 2、DDR 保存 1。设备绕过 LLC 读取 DDR，仍会得到旧输入。WT 描述 L1D 向下传递写入的方式；下层 LLC 的写回策略决定数据何时继续到达 DDR。

再看输出中的 y。CPU 曾读取过它，L1D 或 LLC 中留着值 0。NPU 算出 9，并通过设备端口写入 DDR。CPU 再读 y 时若命中旧副本，就会看到 0。这里缓存行可以是干净的：干净只说明它没有尚待写回的 CPU 修改，外部设备写入以后，这个副本仍可能过期。

还有一种破坏性更强的情况：CPU 先前写过 y=3，旧脏行留在 LLC；设备随后把 DDR 更新为 9。稍后 LLC 替换该行，把旧值 3 写回 DDR，设备结果就被覆盖了。因此，输出交接必须在设备写入前处理旧脏数据，而非只在 CPU 读取结果前清除副本。

这也解释了探测时需要关心的四件事：地址是否允许缓存、当前是否驻留、驻留数据是否脏、相关事务是否仍在途。静态地址属性决定“可能缓存在哪里”；运行中的 tag、写缓冲、回填和替换状态，才决定这次交接需要做什么。

3. 软件确定交接时机，硬件完成缓存维护

模型运行程序知道 CPU 何时写完输入、NPU 何时开始使用，以及 CPU 何时需要输出。利用这些边界，软件可以一次交出整个缓冲区或计算分块，让硬件集中处理该范围的缓存状态。这样，维护成本与实际数据交接次数相关，设备连续搬运期间可以沿既定 DDR 通路工作。

“交出缓冲区”指软件停止 CPU／Ara 对该 DDR 范围的后续访问，等待已有生产者完成，再向维护服务提交物理地址、长度和用途。设备持有期间，中断处理程序和其他设备也遵守这一约定；CPU 可以处理其他独立数据。约束覆盖维护涉及的完整缓存行，包括传输范围外、同一行内的邻接字节。软件停止新访问，硬件负责处理此前已接受的事务。

这里转移的是缓冲区的使用权，DDR 地址和存储容量保持原样。输入同步成功后，程序保留指针但暂停使用这块输入；输出同步成功后，同一个输出指针可以重新用于读取。这种安排把缓存状态变化封装在交接点，应用仍按普通数组处理数据。

三个常见操作分别解决不同问题。clean（清理）把脏数据推进到约定的共享位置，本方案要求最终对 DDR 设备端口可见；invalidate（失效）清除缓存副本，使后续读取重新取数；fence（屏障）约束数据访问与控制命令的先后顺序。例如，要先完成输入准备，再向设备发布启动命令。flush 在缓存维护语境通常表示清理后失效，具体接口应明确这两个动作及其完成点。操作语义参考 RISC-V CMO v1.0 和 FENCE 规范。

对写缓冲所说的“排空”，是推进相关写入并等待其完成，使待处理条目能够正常释放；简单清零条目会丢失尚未送出的数据。写缓冲排空之后，还需按下层状态清理 LLC，才能使新值对 DDR 设备端口可见。软件交出 DDR 缓冲区的使用权、硬件排空写缓冲、搬运器把 DDR 数据复制到 GB，是三个不同的动作。

每次交接设置一个受保护的维护窗口：硬件限制冲突请求进入，让已有读写、回填和替换完成，再修改缓存状态、收齐确认并退出窗口。实现时可以选择范围仲裁或短暂全局停顿。设备计算期间由软件维持范围使用约定；若需硬件拦截所有违规访问，还要覆盖 L1D 命中路径。

交接粒度由程序的数据依赖决定。如果模型的各层都在设备内部连续执行，CPU 只在两端提供输入、读取输出，同步可以集中在推理前后。如果中间某层需要 CPU 后处理，再交给 NPU，那么这次交替使用就是新的同步点。用一次整模型同步覆盖所有内部交接，会遗漏中途产生的新版本；逐元素同步又会把本可批量执行的维护拆得过碎。

维护以搬运描述符中的 DDR 侧物理地址为依据，按缓存粒度向外覆盖；搬运仍按实际数据长度执行。GB 保存本次装入的版本，下一轮需要更新后的输入时重新搬运。每个分块都有“装入完成、计算可用、结果可搬出、空间可复用”的生命周期，这些条件由 GB 本地任务调度衔接。

4. 输入维护使设备从 DDR 取得最新数据

仍以 x=2 为例。CPU 完成输入准备后，首先等待参与生产的 CPU／Ara 工作结束，再提交输入同步。维护服务先推进相关写缓冲及在途写，让这些更新进入下层。应先让依赖 LLC 接收的上游写入排空，再隔离 LLC 并清理；反过来既可能漏掉新写，也可能形成“LLC 等上游排空、上游等 LLC 接收”的循环等待。

下一步清理输入范围内的 LLC 脏行。若 LLC 已有 x=2，就沿 S0 把它写入 DDR；若某行保持干净，DDR 已有对应版本，可以省去该行的数据写回。输入交接后设备只读这份数据，因此 CPU 的干净副本也可以保留，减少今后重新读取时的 miss。

然后需要确认设备端口能够看到写回结果。这里的完成条件是：S1／S2 按约定发起后续读取时，能得到这些写入的新值。控制器可通过内部排序或转发提供保证；若成功写响应已包含所需跨口可见性，就可直接作为依据，否则需补充完成机制。具体以供应商契约和跨端口验证为准，数据无须为此等待实际 DRAM 单元更新完毕。

维护引擎汇合缓存操作与 DDR 可见性确认后，返回同步成功，软件才发布输入搬运任务。至此，数据经历了 CPU 生成 → 先行写推进 → LLC clean → DDR 可见 → 搬入 GB。GB 装入完成又是 NPU 开始消费该分块的前提。

权重在多轮推理间保持不变时，可维持相应设备使用状态，减少重复同步；GB 容量不足导致的再次搬运仍由调度决定。输入不断变化时，可用两个独立缓冲区，让设备处理上一块、CPU 准备下一块，并在每次交换角色时同步。

5. 输出维护保护未覆盖字节，并让 CPU 读取新结果

输出在设备写入前采用 排空旧写、clean＋invalidate 的准备流程。排空和清理使 CPU 已有修改落到 DDR，失效清除旧副本；维护期间还要处理正在替换或回填的相关事务。完成后，设备可以获得一块没有旧脏写等待覆盖它的输出范围。

部分行写入说明了清理的必要性。把一行分成四段，DDR 当前为 [1,2,3,4]，LLC 中的最新值为 [10,2,30,4]，设备只准备把第二段改成 9。先清理得到 [10,2,30,4]，设备再用有效字节使能更新第二段，结果为 [10,9,30,4]。直接丢弃 LLC 脏行会丢失第一、第三段的 CPU 更新；保留旧脏行则可能在以后把第二段重新覆盖为 2。

即使软件只申请几个字节，维护也会涉及完整缓存行。当前 L1D 行为 32 B，默认 LLC 行为 64 B，一个 LLC 行覆盖两个 L1D 行。因此，缓冲区的分配、交接和保护范围应按公共粒度覆盖；锁、栈或其他仍在修改的对象应放在独立行中。AXI beat 和 WSTRB 描述一次传输的有效字节，完整覆盖优化则需要证明整个相关缓存粒度都被覆盖，并处理跨行和失败情况。基线对完整行也采用同样的准备流程。

设备随后从 GB 搬出结果。NPU 算完时，结果还可能停在 GB 或写队列；软件应等待搬出完成，并确认 DDR 中的结果对 CPU 所在端口可见。任务完成状态必须包含这些依赖，单独的计算结束信号只适合启动下一阶段搬运。

交还 CPU 前，先限制冲突新请求、等已有读响应完成，再最终失效输出范围的 L1D／LLC 副本。优先采用排空后失效的顺序；只有需要更高并发时，才评估响应丢弃或重放。若发现冲突脏数据，进入错误处理，保留现场，避免把旧值清理到设备结果之上。设备写后已经发生过的违规写回，还需靠使用权约束和事务跟踪防止。

迟到响应的风险可用四步说明：①缓存读请求先取得 y=0；②响应受背压暂存；③设备把 DDR 改为 y=9；④旧响应随后到达，仍携带 0。这里指 CPU 缓存层次的回填响应，其数据在第①步已经确定。若先失效再允许第④步安装，就会恢复旧副本。这是需要防护的条件性竞争，当前路径是否允许该交错尚待验证；完整的写前排空会排除相应的交接前请求，写后维护则收束其余允许发生的在途访问。

成功返回后，CPU 才读取结果。按行维护保证各行的数据版本正确，整个张量何时可用则由任务完成协议确定；这使应用能够在明确的时间点消费一份完整输出。

6. 裸机程序用显式同步串起完整推理

下面采用单任务、独立输入输出、物理地址可直接使用的裸机环境。缓冲区按完整维护粒度隔离，权重已准备好。首次维护前建立上下文，记录 DDR／GB 资源、物理范围、请求身份及阶段；HAL 在提交前登记待提交状态，接收确认后再推进阶段。以下函数均为拟议接口，limit 表示各阶段的等待预算。

int infer_one_block(void)
{
    context *ctx = reserve_context_and_buffers();
    int rc;
    if (!ctx) return NO_MEMORY;
    prepare_input(ctx->in.cpu_ptr);
    rc = wait_input_producers(ctx, limit);
    if (rc) goto failed;
    rc = sync_input_for_device(ctx, limit);
    if (rc) goto failed;
    rc = prepare_output_for_device(ctx, limit);
    if (rc) goto failed;
    /* HAL 登记提交状态，再发布参数与启动命令。 */
    rc = submit_inference(ctx, limit);
    if (rc) goto failed;
    rc = wait_result_visible(ctx, limit);
    if (rc) goto failed;
    rc = sync_output_for_cpu(ctx, limit);
    if (rc) goto failed;
    consume_output(ctx->out.cpu_ptr);
    release_after_success(ctx);
    return 0;
failed:
    quarantine_context_and_buffers(ctx, rc);
    schedule_recovery(ctx); /* 上下文继续存活，恢复后才释放 */
    return rc;
}

HAL 用编译器屏障及适当的 FENCE 建立数据、MMIO 命令和结果访问的顺序。下面的成功条件是硬件服务的接口要求；每次轮询同时检查完成与错误，超时转入恢复。命令已接收用于确认提交状态，后续阶段等待实际动作完成。

超时表示软件等待预算耗尽，已经发出的请求仍需处置。恢复流程阻止新增请求，查询维护与搬运状态，等待旧事务排空，或通过经过验证的隔离／复位使其无法再修改资源，随后才复用 DDR／GB。新任务编号有助于识别迟到完成通知，但停止迟到写仍需硬件保证。恢复也超时时继续隔离资源并上报平台故障，保留上下文供诊断。

基线在启动前一次取得所需范围，避免持有一块再等待另一块；扩展多任务时采用统一获取顺序或一次性预留。维护引擎启动后自主推进，完成过程应避免依赖持锁线程或被暂停的 CPU 回调。计时器、轮询状态、执行代码和栈的访问路径需逐项核查：LLC way 维护的入口隔离可能同时阻塞 SPM 访问，即使 SPM 内容保留。若 CPU 暂时停顿，维护仍应自主结束，恢复后的轮询再检查时间；故障时的硬上界需独立超时监控保障。具体预算由负载和总线最坏延迟评估确定。

描述符采用 MMIO 参数或经验证的非缓存存储；使用可缓存描述符时另行同步。中断可替代轮询，完成条件相同。当前crt0调用 main()；DMA HAL和SPM DMA 例程提供寄存器提交、任务 ID 和等待结构的参考，新增服务仍需实现。RTOS 可复用底层服务并增加范围管理；Linux 由平台 DMA 后端承接。地址转换、缓存可见性与任务等待各有职责，参见 Linux 6.5 DMA API。

7. 范围维护引擎连接现有缓存与搬运控制

实现上述 HAL，需要把范围命令、缓存维护与搬运准入连接起来。服务在查询前建立维护窗口，并保持到在途事务和状态更新完成，避免检查完 tag 后又建立旧副本。缓存数据继续沿 LLC→S0→DDR 流动；新增连接主要承载控制与确认。

错误完成的证据。 w_master声明 b_chan_mst_i 却未使用其内容；收到 B 握手后继续推进，flush 描述符退出时通知 config，后者计数完成即结束维护。普通替换也经过这条写回路径，故问题在引入 GB 前已存在。AXI4 规范说明中的 SLVERR／DECERR 表示错误，握手只能证明响应已被接收。以上为静态源码确认的可靠性缺口；实际故障影响尚未注入验证，系统级报告及恢复位置仍需核查。硬件可以向软件汇总一个可靠的成功／错误状态，软件无需逐笔解析 BRESP。

同步成功需汇合维护完成、所需传输无错误及跨端口可见性。若发生写回错误，应阻止后续依赖任务并上报，能否保留数据重试取决于缓存及平台恢复设计。接口评审还需定义范围、操作和身份，但 CSR 地址、编码及超时值尚未冻结。LR/SC／AMO 控制对象与搬运数据分行；LR/SC 序列在交接前结束。设备若需修改同一原子对象，另定义旁路写的观察范围。

8. 同步范围和交接频率决定维护开销

L1D 纳入探测后，主要成本来自 tag 查询、有效位更新、写缓冲排空和冲突处理。当前缓存行写入／失效与读请求共享资源，维护可能使 CPU 等待。当前向量 L1D 为 8 KiB、4 路、32 B 行，共 256 个驻留位置；旧失效机制清除索引下全部 way，还可能驱逐无关数据。定向匹配可以减少这部分重填成本。

查询策略也影响大块同步。1 MiB 输入包含 32768 个 32 B 块，逐地址探测需要检查许多未驻留地址；扫描 256 个驻留 tag 再筛选范围，可能更经济。实际周期取决于 way 的并行度、端口仲裁和在途事务，扫描期间也必须协调新增驻留。小范围则可能直接逐行查询更简单。

LLC 的脏写回同时占用缓存和 DDR 带宽，现有按 way 维护的入口隔离还会扩大 CPU 停顿范围。范围维护、提前准备下一分块、双缓冲流水和稳定权重复用，分别减少无关维护、暴露等待及重复调用。缓冲区越大，同步次数可能越少，但缓存状态扫描、搬运等待和 GB 容量约束也会变化，需要随负载测量。

脏输入供数 LLC 写回 DDR，搬运器再读取 缓存向搬运端返回最新数据

以 64 B 脏输入行为例，经 DDR 交换包含一次 64 B 写回和一次 64 B 读取；缓存直供可省去当次往返，未来的写回责任仍需处理。若输入量为 N、实际需清理的数据量为 D，相关 DDR 流量约为 N + D，按真实缓存行和传输粒度计。干净输入的 D 可以为零。当前方案选择较简单的数据连接，先通过范围和调度优化降低同步成本。

后续验收应同时测正确性和开销：设备必须取得交接版本，旧脏行及迟到写必须无法覆盖结果，部分行未选中字节必须保留。用例覆盖待完成写、干净／脏副本、32/64 B 边界、跨行、并发回填／替换、多设备范围冲突，以及超时后的迟到事务。性能记录 CPU 停顿、维护时间、缓存 miss、DDR 字节数及任务尾延迟，比较小块频繁交接、大权重搬运和双缓冲负载。
