基础软件实现对接口契约的使用

BSP（Board Support Package，板级支持包）是让软件能在某个具体硬件平台上启动、访问设备和运行的支持集合。本工程没有一个函数调用就能完成全部板级工作的统一BSP入口：相关职责分布在Boot ROM、应用启动汇编、链接脚本、DIF/HAL、寄存器定义及装载调试脚本中。这里用BSP作为职责分类，不把它描述成仓库已经打包好的独立产品。

比较项 软硬件接口层 基础软件层
核心问题 软件可以操作什么？每次操作必须遵守什么规则？ 怎样用代码完成初始化、访问、等待、交接和错误处理？
主要内容 ISA、CSR、地址/寄存器、中断/异常、缓存属性和访问顺序 启动代码、公共库、驱动、HAL/DIF、MMIO/CSR辅助函数、平台支持
UART例子 THR/LSR地址、状态位、访问宽度、FIFO行为 uart_init()、uart_write()、uart_write_flush()
数据共享例子 DMA完成语义、哪些访问可被CPU看到 驱动安排缓冲、提交、等待、必要的屏障/缓存维护和结果校验
修改关系 改地址、字段、副作用或IRQ路由会改变契约 对应宏、初始化、驱动、异常处理和测试必须同步

MMIO（Memory-Mapped I/O，内存映射I/O）机制属于接口层；通过指针产生MMIO访问的reg8/reg32、mmio_region_*是基础软件代码。同理，mstatus的语义属于接口层，封装CSR指令的set_mie()属于基础软件。两层是不同观察角度，不要求所有源码文件只能归到一侧。

lib是组织和复用代码的方式，驱动是控制设备的职责。一份库可装入驱动、启动代码、GPT解析器和printf；它们不会因此变成一个连续调用层。应用可以直接调用DIF或访问寄存器；Ara计算通过向量指令进入处理器，不必经过HAL。

现有分层索引把构建、启动和运行支持另列为横向支撑。本章为建立BSP整体认识，将目标端启动/运行支持一并讲解；编译器、链接器和调试器仍明确放在开发主机侧，不把它们当成目标运行时调用链的一层。

这里要区分SoC支持和板级适配：UART控制器的寄存器驱动可复用，但基址、输入时钟、引脚连接、流控线及实际串口对端由平台决定。SPI控制器DIF可复用到不同器件，Flash操作码、地址模式和上电条件则属于器件HAL及板级初始化。

启动支持为后续驱动建立执行前提

默认路径是复位→Boot ROM汇编→Boot ROM C/加载→应用crt0→main，条件和源码细节见构建启动章。Boot ROM等待LLC自测并准备SPM/早期栈；应用crt0使用链接符号建立或继承栈、设置gp和trap入口、清BSS、初始化浮点状态，随后调用main。应用crt0没有通用的.data从ROM到RAM复制循环，加载初值需要由实际装载路径放到应有位置。

__base_uart等在C侧声明为链接符号，驱动使用&__base_uart取得其地址值；不能把它误改成读取普通指针变量__base_uart，否则可能先访问设备地址处的内容。common.ldh定义地址，params.h提供C声明，生成寄存器头再定义相对偏移/字段，这三者职责不同。

crt0设置了trap包装，不等于安装了每个外设的处理程序。默认弱trap_vector停留在循环，完整PLIC分发需要软件补充；现场包装也不能被当成已具备RTOS的全量上下文切换，尤其不能据此声称支持浮点/向量抢占。

DDR训练、ASIC PLL和PAD配置不是调用任意*_init()就自动完成的公共步骤。现有FPGA控制器/时钟配置、Boot ROM及未来Platform ROM职责需按平台启动约定对接；既有Platform ROM返回路径和ROM C栈对齐疑点仍保留。运行时调频后UART/SPI分频及计时基准也要重新核对，不能沿用过期的core_freq。

HAL、DIF和MMIO分别封装不同的知识

DIF（Device Interface Function，设备接口函数）在本工程通常表示对控制器/IP寄存器的访问；HAL（Hardware Abstraction Layer，硬件抽象层）是更一般的名称，本地hal/主要封装片外器件协议或服务协议。名称不能代替看代码：uart_debug位于HAL，处理的是装载命令；它不是另一块UART硬件。

OpenTitan驱动通常返回dif_result_t，本地HAL常返回int并用CHECK_CALL传播非零值。UART的void uart_write()则没有这种错误通道。调用方必须读实际声明，不能把所有驱动都当成“返回0就是硬件操作全部成功”。

访问辅助函数把地址和偏移变成CPU操作

下面两段摘自当前实现。第一种返回volatile指针，由调用者解引用；第二种直接执行32位访问。offs/offset均以byte计，不是第几个寄存器。

// sw/include/util.h
static inline volatile uint32_t *reg32(void *base, int offs) {
    return (volatile uint32_t *)((uint8_t *)base + offs);
}
// OpenTitan base/mmio.h：非mock路径
inline uint32_t mmio_region_read32(mmio_region_t base, ptrdiff_t offset) {
    return ((volatile uint32_t *)base.base)[offset / sizeof(uint32_t)];
}

对应源码：util.h、mmio.h。reg8用于字节访问，reg32用于32位访问；mmio_region_read32要求正确对齐，源码里的除法不是在帮调用者安全处理任意未对齐地址。将返回类型改成64位不会把硬件寄存器一起变宽。

volatile约束编译器对这些访问的处理，不能单独证明CPU/总线顺序或DMA数据可见性。fence()还发出指令并带编译器memory clobber；缓存维护是另一个问题。OpenTitan头文件的顺序描述需结合本平台CPU属性、桥和外设语义核对，不能直接扩展成“系统硬件一致”。具体路径见MMIO与数据交接。

set_mie()、set_mtie()、get_mcycle()也定义在util.h，但使用CSR指令，不访问外设地址。调用所需特权、MIE/MTIE位语义属于接口层CSR说明；函数包装本身没有赋予低特权代码额外权限。

库归档把实现交给链接器选择

从应用写下#include "dif/uart.h"开始，预处理器让编译器看到函数声明和宏；头文件搜索成功不等于实现已经参与链接。编译器把调用转换成目标代码及尚待解析的符号，链接器再从对象和库中找到实现。static inline辅助函数可能直接进入调用者；dma.h的宏/inline形式则需连同实际编译与链接行为检查，不能凭目录名寻找一个并不存在的dma.c。

sw/sw.mk的CHS_SW_LIB_SRCS_*和CHS_SW_DEPS_SRCS共同组成libcheshire.a：

归档规则将这些.o用ar -rcsv打包；原规则还传LTO插件。链接规则以GCC作为驱动，提供应用对象、链接脚本和libcheshire.a。这不是CPU运行时打开.a文件：归档在主机链接时被使用。--gc-sections以及LTO（Link-Time Optimization，链接时优化）还可能删除未使用代码或内联函数，所以库成员数不等于最终ELF中的函数数。

.a也不携带链接脚本、JTAG连接、板级引脚或供应商DDR训练资料。独立BSP的迁移清单需要同时包含这些依赖和工具条件，不能只复制sw/lib/libcheshire.a。本项目固定配置/静态清单方向不变，本轮只解释现有构建，不实施提取。

工程库、libgcc和libc提供不同服务

  • 工程printf：printf.h把printf重命名到printf_；字符回调接本地UART，不需要据此假定Linux系统调用存在。
  • libgcc：编译器运行支持库，提供编译器可能生成调用的辅助例程；不是外设驱动集合。
  • libc：C标准库实现。本轮工具链能定位libc.a，但这不证明应用已经具备文件系统、堆扩展、锁或所有系统调用适配。要使用这些能力，需检查最终链接map、未解析符号及相应平台实现。

当前链接选项是-nostartfiles，并非-nostdlib：前者抑制默认启动文件，不能解释成禁用全部标准库。链接归档的位置也影响符号解析。这里依据与本机GCC对应的15.2链接选项官方说明，工程实际库选择仍看完整命令和map。

主机工具把源码、布局与平台描述组成产物

sw.mk仍有“TODO: track headers with gcc -MM”的注释，并不自动追踪全部头依赖；改flags也不能默认让所有旧.o失效。验证构建应使用独立、来源明确的输出和匹配库，不能看到旧ELF就推断本次改动已编入。

字符输出把公共库接到控制器驱动

helloworld.c先读RTC_FREQ，经clint_get_core_freq()估算当前时钟，再以uart_init(&__base_uart, reset_freq, __BOOT_BAUDRATE)初始化，之后才调用printf。它还写VS状态，但这不证明执行了向量计算。

调用链为main→printf宏→printf_→_vsnprintf→_out_char→_putchar→uart_write→reg8解引用。printf处理格式与数字转换；_putchar决定默认控制台；UART DIF知道寄存器与等待条件；MMIO辅助函数只处理地址和类型。以下摘自uart.c：

void uart_write(void *uart_base, uint8_t byte) {
    while (!__uart_write_ready(uart_base))
        ;
    *reg8(uart_base, UART_THR_REG_OFFSET) = byte;
}
void _putchar(char byte) {
    uart_write(&__base_uart, byte);
}

__uart_write_ready读取LSR bit5（THRE），随后向THR写一个字节。初始化先关IER、打开DLAB写分频，再恢复8N1、配置FIFO与自动流控；波特率计算使用传入频率，错误的频率不会被函数自动识别。

uart_write()返回void，表示软件已执行字节提交，不表示该字节已经全部从TX引脚移出。uart_write_flush()还等待THRE/TEMT，源码保留顺序TODO且没有超时；printf_返回字符计数，也不是UART错误状态。轮询卡住时要按时钟/基址、LSR、流控和硬件路径排查，而不是仅查看printf返回值。

完整寄存器、总线路径和UART状态机对应见字符案例。历史HelloWorld反汇编中，_putchar已经内联uart_write，实际是lbu轮询和sb提交。源码里有函数调用不保证反汇编还保留同名调用指令；这正是“软件组织”与“最终机器行为”需要对照阅读的原因。

GPT通过回调复用Flash器件HAL

目标场景是从SPI NOR读取启动内容到SPM；本次只分析，不执行Flash擦写或启动。调用链是boot_spi_s25fs512s→HAL init→gpt_boot_part_else_raw→gpt_read_t回调→spi_s25fs512s_single_read→dif_spi_host_transaction→MMIO→SPI控制器。

控制器初始化和器件就绪是两个步骤

Boot ROM C中的Flash handle配置csid=1，spi_freq=MIN(40 MHz, core_freq/4)。这是当前源码值，不是未来板卡或采购器件的冻结要求。spi_s25fs512s.h定义handle包含dif_spi_host_t spi_host、spi_freq和csid，后二者由调用者预先填写。

spi_s25fs512s_init检查参数，将&__base_spih包装成MMIO region，调用dif_spi_host_init建立控制器handle，然后复位控制器、按时钟/模式配置CS、使能控制器和输出。dif_spi_host_init本身在autogen文件中只校验输出handle并记录base；不能仅调用它就认为SPI已经配置完成。

HAL头注释要求后续命令前满足器件上电等待。当前Boot ROM还用CLINT等待基于RTC的启动时刻；clint_spin_until使用绝对mtime门槛，不是从HAL返回起重新计一段延时。芯片上电相对复位的关系和板级连接仍须平台保证。

统一读回调隐藏介质差异

回调类型是：

typedef int (*gpt_read_t)(void *priv, void *buf,
                        uint64_t addr, uint64_t len);

priv携带设备handle，buf是CPU目标缓冲，addr/len是介质中的字节地址/字节长度。GPT先通过回调读偏移0x200的签名，再读取分区条目，按512-byte LBA计算复制范围。它不知道底层是SPI Flash、SD还是I²C EEPROM；更不会把addr自动解释成CPU物理地址。

Flash HAL将priv转为spi_s25fs512s_t*，把读取拆成不超过4 * SPI_HOST_PARAM_RX_DEPTH byte的块，构造三个segment：操作码0x13、4字节器件地址、RX缓冲与长度。这里的4来自FIFO每项的字节数。每块更新缓冲位置和器件地址，最后一块取剩余长度。对应函数为spi_s25fs512s_single_read和__spi_s25fs512s_single_read_chunk。

SPI DIF则写CSID，等待控制器ready，将各segment编码到TXDATA/COMMAND，再从RXDATA读取到缓冲。CPU在这条路径上排命令并搬出RX FIFO中的数据；没有因为API叫transaction就自动使用系统DMA。SPI寄存器语义由DIF与RTL约定，Flash操作码语义由器件HAL与器件约定。

返回值沿调用链传播但不保证所有故障被覆盖

HAL通过CHECK_ASSERT返回本地检查码，通过CHECK_CALL把下层非零返回直接上传；DIF通常返回kDifOk或参数类错误。等待ready/RX的循环并没有因此得到统一超时机制。若器件未接、时钟错误或FIFO始终不满足条件，不能假设一定会及时得到非零返回。

还有一个具体例外：gpt_check_signature在读回调失败时返回“未发现签名”，随后gpt_boot_part_else_raw可能尝试raw读取；它没有把首次读错误原样上传。后续分区读取与最终复制使用CHECK_CALL，复制成功后写SCRATCH信息并调用boot_next_stage，所以该函数不是只读数据后返回的普通文件API。不能把它当作不会跳转执行的介质探测工具。

最小后续验证应先在独立测试中只调用HAL读取已知字节，比较长度、内容和缓冲守卫，再验证跨块边界及错误/超时；确认这些之后才使用带控制转移的GPT启动路径。当前没有新增器件运行证据；EEPROM分块等已登记疑点也不因这一解释而关闭。
